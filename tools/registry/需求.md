# 能力注册表 registry · 开发包(需求与接口)

> 层:基座(供编排 + 未来 Agent 发现调用)· 状态:**规划** · 分支建议:`feat/registry`
> 参考:[架构设计.md](../../docs/架构设计.md) §6.4

## 职责(做什么 / 边界)
- 把每个**能力**登记为 **JSON-in / JSON-out 工具**(name / 描述 / 入参 schema / 出参 schema),供**程序编排**与**未来 Agent** 统一发现与调用。
- **边界**:只做"登记 + 发现 + 调用转发",**不含业务逻辑**(业务在各层模块里)。

## 接口契约
```python
@capability(name, description, in_schema: dict, out_schema: dict)
def some_ability(**kwargs) -> dict: ...

def list_capabilities() -> list[dict]          # name/描述/schema
def call(name: str, args: dict) -> dict        # 校验入参 → 调用 → 校验出参
```
- 待登记能力(示例):`collect_market / analyze_technical / predict_stock / screen_pool / get_stock_record / sentiment_stock / backtest_strategy`。
- 与 `tools/strategy` 的策略注册表**风格对齐**(两者都是"注册+发现+调用"),可考虑共用底座。

## 双模设计(借鉴 benchmark_detection 的 Wrapper/RequestProcessor)⭐
把每个能力做成**双模**:**同一套代码,两种用法**——
- **对内**:被程序/流水线 `import` **直调**(现状,函数即用)。
- **对外**:经一个 `RequestProcessor`(薄壳)暴露为 **HTTP 服务 / Agent 工具**,自动按 in/out schema 校验、转发到能力函数。
- **载体**:每个能力可包成一个 `Wrapper`(标准接口 `run(args: dict) -> dict`,自带 name/描述/schema)。registry 登记的就是这些 Wrapper → 从"注册表"升级为"**双模能力容器**"。
- **好处**:业务类不依赖框架(只吃/吐 dict)→ 既能被本地流水线直调,又能零改造上线成服务/被 Agent 调用。是本模块"供 Agent 发现调用"目标的落地方式。

## 验收标准
- [ ] 注册 / 发现(list)/ 调用(call)闭环。
- [ ] call 时按 in_schema 校验入参、out_schema 校验出参,不合规抛错。
- [ ] 至少登记 3 个现有能力并可调用。
- [ ] 至少 1 个能力走通"双模":同一 Wrapper 既被 `call()` 直调,又能经 RequestProcessor 以 dict-in/dict-out 暴露。

> 用途:支撑"工具化"阶段(架构 §11 C),让 Agent 能自动发现并调用项目能力;双模让能力可无缝上线成服务。
