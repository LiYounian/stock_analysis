# 架构设计(权威版)

> 状态:**生效中** · v1.0 · 更新 2026-08-06
> 定位:本文与 [开发规范.md](开发规范.md) 是项目**两篇必读权威文档**。所有开发(人 / Agent)按本文的**分层、边界、接口契约**进行。
> 产品定位:A 股策略辅助工具(详见 [需求与目标.md](设计/需求与目标.md),非投资建议)。
> 本文描述**当前真实架构 + 规范化的边界与接口**;其中"编排调度""工具化"等为**设计规划,尚未实现**(明确标注),先立规范、暂不开发。

---

## 1. 架构总原则(先读,一切边界的来源)

1. **分层单向依赖**:上层依赖下层,**严禁反向依赖、严禁环依赖**。跨层协作只经两种合法通道:①**数据契约**(中心记录),②**明确声明的函数接口**。模块间**不得**互相 import 对方内部实现。
2. **中心数据契约是"层间 API"**:`data/analysis/{code}.json`(schema 与校验在 `tools/contracts/`)。生产者写它、消费者读它,双方都不需要知道对方代码。→ 这是解耦与并行开发的地基。
3. **采集是唯一的外部 I/O 边界**:只有 `collectors/` 碰网络/数据源。`analysis/` 纯计算(文本侧才调 LLM),`web/` 只读产物、绝不触网/重算。
4. **单一职责**:一个 collector 只管一个数据源;一个 analysis 只算一件事;配置/阈值集中在 `config/`(单一真源)。
5. **诚实性内建**:预测=概率/波动区间,非点位保证;缺失=null 不伪造;全站标"非投资建议"。
6. **可插拔留口子**:未定的业务(选股规则 N1、财报框架 N2、LLM provider)以**接口先行**,实现可替换。

## 2. 分层架构(当前真实形态)

```
┌──────────────────────────────────────────────────────────────────┐
│ 展示/交付层   web/(FastAPI 只读 4 页) · report/(markdown)          │  只读中心契约,不重算
├──────────────────────────────────────────────────────────────────┤
│ 编排层        run.py(CLI 子命令) · [pipeline/registry = 规划,骨架已立] │  串流程,不含业务逻辑
├──────────────────────────────────────────────────────────────────┤
│ 聚合/选股/回测 analysis/portfolio · screener/ · analysis/panel · backtest/(回测) │ 读中心契约/历史数据
├──────────────────────────────────────────────────────────────────┤
│ 组装层        analysis/serialize ★ 产出中心契约(过 contracts 校验)  │  汇总各分析器 → 记录
├──────────────────────────────────────────────────────────────────┤
│ 分析/策略层   analysis/technical·valuation·predict·event(LLM情绪) · strategy/(选股/评分/信号可注册) │ 纯计算(+LLM)
│               financial_report/(留口子 N2)                          │
├──────────────────────────────────────────────────────────────────┤
│ 采集层        collectors/market·fundamental·announcement·fundflow·news·policy·ugc(股吧) │ 唯一外部 I/O → data/raw/
├──────────────────────────────────────────────────────────────────┤
│ 基座          config(参数/策略阈值) · contracts(记录契约) · llm(客户端) · store(数据存取:raw/记录/视图统一读写) │ 被各层依赖
└──────────────────────────────────────────────────────────────────┘
```

**依赖方向(强制)**:`基座 ← 采集 ← 分析/策略 ← 组装 ← 聚合/选股/回测 ← 编排 ← 展示`。箭头即"可依赖"方向,反向即违规。

> **信息流转 + 任务流程 + 每层职责详解**:见 [信息流转与层职责.md](设计/信息流转与层职责.md)(两张流程图 + 逐层"职责/在处理什么/接口/扩展")。
> 其中规划的三个层现已落地骨架/实现:**数据存取层 store**(基座,已建)、**策略层 strategy**(选股/评分/信号可注册,已建)、**回测层 backtest**(信号回测 BT.1 已建,选股回测 BT.2 待做)。

## 3. 模块边界与职责(解耦的清晰边界)

| 层 | 模块 | 职责(边界内) | 明确不做(边界外) | 依赖 |
|---|---|---|---|---|
| 基座 | `config/` | 票池 / 全局参数 / 策略阈值+公式(单一真源) | 不采集、不计算 | 无 |
| 基座 | `contracts/` | 中心记录 schema + 枚举词表 + 校验器 | 不产数据 | 无 |
| 基座 | `llm/` | 统一 LLM 客户端(deepseek-v4-pro)+ prompts | 不含业务判定 | config |
| 基座 | `store/` | 数据存取:raw/记录/视图 统一读写(未来换 DB 只改此层) | 不含业务、不 import 上层 | config |
| 采集 | `collectors/*` | 从**一个**数据源拉数、归一、落 `data/raw/`;失败抛错不静默 | 不做分析判定 | config |
| 分析 | `analysis/technical·valuation·predict` | 纯本地计算(指标/估值开关/止盈止损情景) | 不触网、不落中心记录 | config, 读 raw |
| 分析 | `analysis/event` | 新闻→LLM 抽取+三层归类+情感聚合 | 不改行情/基本面 | llm, collectors.news |
| 分析 | `strategy/` | 策略层:选股/评分/信号 可注册(`@strategy`),复用 screener 预设 | 不采集、不落中心记录 | config, contracts, screener |
| 聚合 | `backtest/` | 回测:历史回放策略→绩效对比基准(walk-forward,防未来函数) | 不触网、不产中心记录 | store, strategy, config |
| 组装 | `analysis/serialize` | 汇各分析器 → **中心记录**,落盘;**产出必须过 contracts 校验** | 不做新计算(只组装) | analysis, collectors(load) |
| 聚合 | `analysis/portfolio·panel` | 读中心记录做跨票聚合/横表 | 不改单票记录 | contracts(读记录) |
| 选股 | `screener/` | 读中心记录,pluggable filters 出候选(规则 N1 留口子) | 不算指标 | contracts(读记录) |
| 展示 | `report/`·`web/` | **只读**中心记录/视图渲染 | **绝不重算、绝不触网** | 中心记录 |
| 编排 | `run.py` | 按依赖顺序串各层;薄壳 | 不含业务逻辑 | 各层入口 |

> **关键规矩**:`web/`、`report/`、`screener/`、`portfolio/` **只认中心记录**,不 import `technical/predict/event` 等分析器内部 —— 分析器怎么变,只要记录契约不变,展示/选股就不用改。这就是解耦边界。

## 4. 中心数据契约(层间 API · 单一真源)

- **物**:`data/analysis/{code}.json`;**契约代码**:`tools/contracts/`(schema + 8 类枚举词表 + 校验器 `validate_record`)。
- **顶层块**:`meta / snapshot / valuation / fundamental / signals / prediction / sentiment / fundflow / events / timeseries_refs / provenance`(可空块表示"数据不可用",=null)。
- **约定**:代码=6 位字符串;日期=`YYYY-MM-DD`;金额默认元(字段含 `_yi`/亿 时为亿);百分比=数值;方向枚举统一取 `contracts.ENUMS`。
- **契约优先(contract-first)**:任何改动记录结构的 PR,**必须先改 `contracts/` 并让 `validate_record` + 全池回归测试通过**,再改 serialize/消费方。→ 防止字段漂移、跨模块错位。
- **已知待统一**:`signals.ob_os.verdict`(英文键)与 `trend.评级`/`买卖倾向.结论`(中文键)命名不一致 —— 契约已按现状固化并标注,建议后续统一(改动跨多模块,单独排期,见 [开发规范.md] 命名规范)。

## 5. 数据流与存储(三层)

```
config(票池/参数)
   │
   ▼
collectors ──► data/raw/{kline,fundamental,announcement,fundflow,news,llm_cache}/   ← 源形态缓存
   │                                              (中间过程全保留:可审计/可重跑/改下游不重复烧钱)
   ▼ (analysis 各分析器独立读 raw)
technical · valuation · predict · event(LLM)
   │
   ▼ serialize 汇总 + contracts 校验
data/analysis/{code}.json (+ sentiment/{code}.json)   ← 中心契约
   │
   ├──► panel(横表 csv/json)   ├──► screen.json(选股)   ├──► web(4页)   └──► report(markdown)
```

**存储分层**:①`data/raw/` 源缓存 → ②`data/analysis/` 中心记录 → ③视图(panel/screen/report)。均 gitignore。
**演进建议(未建)**:规模化(数百票/历史截面查询)后,引 **DuckDB/SQLite** 作查询层,文件仍为真相源;现在文件足够,**不过早上 DB**。

## 6. 模块接口契约(三类统一签名 —— 并行开发 / Agent 调用的依据)

> 定好入参出参,模块间零口头约定。新增/替换模块只要守签名即可独立开发、独立测试。

### 6.1 采集器 Collector
```
fetch_X(codes: list[str], **opts) -> dict[str, Payload]     # 拉数 + 落 data/raw/;失败单票跳过记日志,拉到空抛错(不静默)
load_X(code: str) -> Payload                                # 只读缓存,缺失抛 FileNotFoundError
```
### 6.2 分析器 Analyzer
```
compute/analyze/predict/aggregate(inputs) -> dict           # 纯计算;输出为文档化 JSON;数据不足标 "数据不足"/null 不崩
```
### 6.3 组装/服务 Service
```
serialize.build_record(code, as_of) -> record(过 contracts 校验)   serialize.load_record(code) -> record
contracts.validate_record(record) -> list[str](空=合规)
```
### 6.4 【规划·未建】能力注册表 `registry.py`
把每个能力登记为 **JSON-in/JSON-out 工具**(name / 描述 / 入参 schema / 出参 schema),供**程序编排**与**未来 Agent 调用**统一发现与调用。示例:`collect_market / analyze_technical / predict_stock / screen_pool / get_stock_record / sentiment_stock`。**本阶段只做设计,不实现**。

## 7. 情绪三层建模(政策 / 公司行为 / 舆情)

| 层 | 来源 | 状态 | 处理 |
|---|---|---|---|
| 公司行为 | 巨潮公告 + 东财新闻 | ✅ 公告规则打标;新闻 LLM 抽取(event) | 事件类型→三层映射 + 方向/强度 |
| 舆情 | 东财股吧 UGC(`collectors/ugc`)+ 传闻类新闻 | ✅ 采集+热度已通;情感打分待接 | 热度指标(纯代码)+ 待接 LLM 情感 |
| 政策 | 东财新闻按政策关键词检索(`collectors/policy`) | ✅ 采集+行业打标已通;情绪判定待接 | 命中打标 + 待接 LLM 判方向/强度 |

**情感聚合**走代码(方向/强度由 LLM 的 L1 给出);LLM 结果按输入 hash 缓存。详见 [大模型调用设计.md](设计/大模型调用设计.md) 与 [计划/P2C_新闻情绪LLM.md](计划/P2C_新闻情绪LLM.md)。

## 8. 编排与调度(**设计规划,尚未实现** —— 本阶段只立规范)

> 用户明确:定时任务等细节功能**暂不开发**,先规划成文档。以下为**目标设计**,供后续按此实现。

### 8.1 编排(目标:`pipeline.py` 显式 DAG,替代 run.py 里堆叠子命令)
- 声明阶段依赖:`collect → serialize → {panel, screen, report}`;某步失败**隔离**,下游读上次成功产物。
- run.py 退化为薄 CLI,调用 pipeline。

### 8.2 定时任务分层(目标,cron 触发 `run.py <子命令>`)
| 任务 | 频率 | 内容 | 说明 |
|---|---|---|---|
| T1 盘后全量 | 交易日盘后 | collect→serialize→panel→screen→report | 主链路 |
| T2 情绪/新闻 | 数小时/盘后 | news + event(LLM) | 独立调度**控 LLM 成本** |
| T3 盘中轻量(可选) | 交易时段 | 增量 kline+fundflow→serialize | 近实时 |
| T4 基本面 | 周/财报季 | fundamental | 低频 |
| T5 兜底补数 | 每日夜间 | 重试失败票(如资金流限流) | 补缺 |

**触发原则**:不同 cron = 不同 pipeline;LLM 类任务单独调度以控成本。**当前不实现,仅规范。**

## 9. 目录结构(现状 + 代码顺序调整建议)

**现状**(已就位):
```
tools/
├── config/         stock_pool · settings · strategy(+strategy.json)
├── contracts/      record(schema/枚举/校验) · record.schema.json     ★ 基座契约
├── store/          repo(raw/记录/视图 统一读写)                      ★ 数据存取层
├── llm/            client · prompts
├── collectors/     market · fundamental · announcement · fundflow · news · policy · ugc
├── analysis/       technical · valuation · predict · portfolio · event · serialize · panel · chart
├── strategy/       registry(选股/评分/信号 可注册 @strategy)          ★ 策略层
├── screener/       screen(预设,N1 留口子)
├── backtest/       engine · metrics(信号回测 BT.1;选股回测 BT.2 待做) ★ 回测层
├── financial_report/  analyzer + 需求.md(N2 留口子)
├── pipeline/       pipeline(编排 DAG,规划骨架) · registry/(能力注册表,规划骨架)
├── report/         builder
└── run.py          CLI 编排(现较厚)
web/  data/  docs/  tests/
```

**建议的顺序/结构调整(规范,择机执行,勿与并发窗口抢改)**:
1. **run.py 变薄**:业务编排下沉到 `pipeline.py`(见 §8.1),run.py 只做参数解析 + 调 pipeline。
2. **serialize 落盘前调用 `contracts.validate_record`**:产出即校验,漂移当场暴露(小改动,收益大;需改 serialize.py,避开并发时段做)。
3. **依赖方向体检(已发现 1 处违规)**:`report/`、`screener/`、`portfolio/` 均合规(只读记录)。**`web/data_access.py` 违规**:为画 K线在展示层 `import technical` 重算 MA,违反"展示只读不算"。建议:把 K线所需 MA 预计算进中心记录(或独立的 chart 数据视图),web 只读——**待改**(改 web/data_access.py,择机单窗口执行)。
4. **命名统一**(见开发规范命名规则):`ob_os.verdict` 与其他中文键的不一致,统一到一版(跨模块,单独排期)。
5. 未来新增 `pipeline.py` / `registry.py`(§6.4、§8.1),均属基座/编排层。

> 以上除第 2、3 项为小改动外,均为**规划**;执行时严格按 [开发规范.md] 的分支与冲突规避流程,单窗口操作。
