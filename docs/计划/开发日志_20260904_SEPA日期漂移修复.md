## 1. 现象

SEPA+VCP 三视图(`SEPA合格池` / `SEPA观察池` / `SEPA雷达`,项目**唯一**趋势跟随口径,
其余偏均值回归/位置/量价)在两个交易日**整体零产出**:

| 交易日 | 当日 `data/analysis/<日>/` 有无 SEPA 三视图 | 其余产物(panel/screen 等) |
|---|---|---|
| 2026-08-28(周五) | ❌ 无 | ✅ 全在 |
| 2026-09-03(周四) | ❌ 无 | ✅ 585 文件全在 |

其余大多数交易日(08-25/26/27/29/31、09-01/02/04…)三视图正常。

## 2. 诊断(读日志 → 划范围 → 找根因)

**产出流水线**:SEPA 由**每日盘后主任务** `com.stock.pullrefresh`(launchd,工作日 15:40)
→ `ops/launchd/pull_refresh.sh` **步 ②.6** `python -m tools.run sepa --no-fetch` 产出。
(仓库里另有 `com.stock.sepa.plist` + `sepa_monitor.sh` 是**独立设计但从未安装**——
`launchctl list` 只有 breadth/intraday/pullrefresh/strong,无 sepa;`logs/sepa.log` 不存在。
即 SEPA 的**实际唯一产出路径是 pull_refresh ②.6**,不是那个独立节点。)

**关键日志证据**(`~/.local/state/stock/pull_refresh.log`):

- 09-03 那轮:`==== Thu Sep 3 15:40 pull_refresh 2026-09-03 ====` 开始,
  但 SEPA 步的日志是 `SEPA+VCP 扫描:… (日期 **2026-09-04** session=收盘)`,
  且整轮 `==== done **Fri Sep 4 05:12** ====` 才结束。
- 08-28 那轮:SEPA 步日志 `… (日期 **2026-08-29**)`,整轮 `done **Sat Aug 29 06:08**`。

**根因 = 日期漂移(date drift),不是崩溃/不是调度没触发/不是上游缺失。**
pull_refresh 是长跑任务(① 全A自采 ~73min + ② 全A多策略),**机器睡眠唤醒 / 跨午夜续跑**时,
执行到尾部的 ②.6 时 wall clock 已滚到 D+1。而 `tools.run sepa` 内部默认用
`pd.Timestamp.today()` 定 `as_of`(见 `screen_sepa_vcp._main`),于是把当日产物写进了
**D+1 目录**:08-28 的写进 08-29(周六,非交易日、无后续覆盖,数据至今躺在那)、
09-03 的写进 09-04(后被 09-04 正常轮覆盖,**原数据丢失**)。

**为什么只有 SEPA 中招**:同为尾部步的 forecast 用 `--as-of "$D"`、upload 用 `--date "$D"`,
都吃脚本开头钉死的 `D="$(date +%Y-%m-%d)"`;screenall 在睡眠前(仍是 D 日)已跑完,写对了 D 目录。
**唯独 ②.6 的 sepa 调用既没传 `--date` 也没传 `--session`**,是全脚本里唯一漏钉日期的一步。

**为什么没被发现**:②.6 是 `… || echo "!! sepa 失败(不阻断)"`——但 SEPA 根本没失败(退 0),
只是写错了目录,`|| echo` 那种"看退出码"的守卫**天然抓不到**;而缺口埋在 40MB 长日志里无人扫。

## 3. 修复

### 3.1 治本 — 钉死 `--date $D`(commit `98813c2`)

`ops/launchd/pull_refresh.sh` ②.6:
```diff
- "$PY" -m tools.run sepa --no-fetch
+ "$PY" -m tools.run sepa --no-fetch --date "$D"
```
`cmd_sepa` 早已透传 `--date` 给 `screen_sepa_vcp._main`(该参数一直支持),故只需在调用处补上。
自此 SEPA 与全脚本口径一致,无论睡眠/跨午夜都写对 `$D`。**预期效果**:此后每个交易日
`data/analysis/<当日>/` 必含 SEPA 三视图,不再随机漏天。

### 3.2 护栏 — 产出缺口不静默(commit `478eb5c`)

新增 `tools/ops/output_guard.py`(纯 Python、可单测,呼应确定性节点「文件存在 ⇒ 内容可用」纪律):
- `check_outputs(date)`:**交易日才查**;每个必达视图须**文件存在 + 可解析 JSON + 内部 `as_of == date`**
  (`as_of` 不符正是漂移那类 bug 的指纹,判为缺失,不只查文件在不在);
- `write_marker(report)`:缺口写 `data/analysis/<date>/_GAP_ALARM.json`(marker 自证,供监控扫描);
- CLI:齐全退 0 / 缺口退 2(非零供定时任务 `||` 捕获)、打印 `!!! 护栏告警` 明细。

接入 `pull_refresh.sh` **②.8**(upload 前):
```bash
"$PY" -m tools.ops.output_guard --date "$D" --marker \
  || echo "!!! 护栏告警:当日 $D 趋势跟随口径(SEPA)视图缺失…"
```
best-effort:护栏自身异常不阻断闭环;缺口只告警 + 写 marker,不拦上传。

单测 `tests/test_output_guard.py`(11 项,全 mock):齐全/缺任一/全缺/as_of 漂移/坏 json/
非交易日不误报/marker 只在缺口写/CLI 退出码。实测对真实 09-03(缺)退 2 告警、09-04(全)退 0。

## 4. 评估:SEPA 是否纳入 launchd 确定性节点机制

**结论:本轮先按「留在 pull_refresh + 钉死 $D + 护栏」交付(已止血);是否升格为独立确定性节点
留作后续决策(见下)。**

SEPA 是纯数据、零 LLM、给定 K线主档即确定 → **契合**确定性节点判据(与 `market_breadth` 同类)。
本次根因恰恰是「耦合进超长跑主任务 pull_refresh」带来的漂移。三条路:

| 方案 | 做法 | 优 | 劣 |
|---|---|---|---|
| **A(本轮)** | 留 ②.6,钉死 `$D` + ②.8 护栏 | 改动最小、复用 ① 已推进的主档、无需装 launchd | 仍挂在 pull_refresh 尾部;若整轮失败则不产(但护栏会告警) |
| **B** | 升格独立节点:安装 `com.stock.sepa`(15:35),**并从 pull_refresh 删掉 ②.6** | 与主任务解耦、跑得快(分钟级)、天然免漂移;plist+wrapper 已就绪 | 需人执行 `launchctl bootstrap`;`sepa_monitor.sh` 用 wall-clock 需同样钉死当日;要保证单写者(删 ②.6) |
| **C(反模式)** | 装独立节点但**不删** ②.6 | — | 同日双写同一批 view(幂等覆盖、无害但浪费);两处口径易漂移。**不采** |

**推荐**:若要根治「趋势口径依赖一个 13h 级主任务尾部」的结构性脆弱,走 **B**——但它要求
(a) 人工 `launchctl bootstrap com.stock.sepa`、(b) `sepa_monitor.sh` 也钉死当日、(c) 删 ②.6 保持单写者。
这三步涉及本机 launchd 安装与主链路改动,**留给用户拍板后另起一轮**(已挂 chip)。
A 已让当日产出稳定 + 缺口可告警,不阻塞。
