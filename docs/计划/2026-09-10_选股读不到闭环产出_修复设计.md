## 0. 一句话结论

盘后选股 `daily-stock-selection` 从 09-08 起天天误跳过，**根因不是门控路径写错，而是 c96b10e 把闭环"生产者"整体挪到 dailyjob worktree，却没把"消费者读到的数据根"一起挪**——生产写 dailyjob、消费读主仓，两处脱节。
**推荐两阶段**：Phase-1 用 **方案 B（闭环末尾把当日产出 copy 回主仓）** 立即解堵，单点改动、零 git 风险、不碰 SKILL/launchd；Phase-2 用 **方案 E（settings 级 `STOCK_DATA_ROOT` 数据根解耦 + 并 ①a）** 根治整类问题，另开设计轮。

### 1.1 新发现（统筹未点出，直接决定方案选型）

- **A. 脱节的真机制不是"cwd"，是"代码位置"。** `tools/config/settings.py:9` `PROJECT_ROOT = Path(__file__).resolve().parents[2]`——数据根由**代码文件所在位置**推导，与运行 cwd 无关。生产者代码在 dailyjob（reset --hard origin/main）→ `PROJECT_ROOT=dailyjob` → receipt（`upload.py:60`）、market_forecast（`:114`）、scorecard（`:105`）、analysis 全写 dailyjob；消费者 `web/app.py`、选股 SKILL bash 从主仓跑 → 读主仓。**光改选股任务 cwd 治不了（方案 D 因此不成立，见 §2）。**

- **B. 消费者不止选股一个。** 至少四处读主仓 `data/analysis/<今>/`：① 选股 SKILL（门控＋"读全部策略视图"）；② `daily-stock-eod-review`（`grep` 命中）；③ `web/app.py`＋`web/data_access.py`（合作者看网页）；④ `docs/计划/每日选股分析机制.md:25/58` 白纸黑字把"主仓当天新鲜闭环产出"写成设计前提。**→ 任何"只补选股一处"的方案都会漏掉 web 和复盘（方案 A 因此降级）。**

- **C. breadth 是独立 job 产的，且更棘手。** `ops/launchd/market_breadth.sh` 同款也从 dailyjob 跑；breadth **daily 文件本身被 git 跟踪** → 往主仓写 breadth 会在主仓留"跟踪路径的改动"，正是 ①a"主仓 ff-only 被挡"那一类。但**选股门控只查 receipt＋analysis，不查 breadth**（breadth 消费者是 `midday_q_gate`/`equal_weight_index` 等盘中链路）→ **选股修复不必动 breadth**，breadth 一致性作为次要项单独处理。

- **D. 主仓当前"看似有" 09-08/09/10 daily。** 主仓 `data/analysis/2026-09-10` 有 531 文件、mtime=今晚 21:49 = **统筹连夜手动补做覆盖**留下的，非闭环自动回写。去掉人工干预，主仓 daily = 空 → 误跳过。与 §1 表第 5 行一致。

## 2. 方案比较

评判维度：是否破 git｜是否 band-aid｜是否触 launchd/SKILL（改未来行为需拍板）｜是否修全部消费者｜维护成本｜能否防未来函数。

### 方案 A — 选股/复盘门控改读 dailyjob 位置
把 SKILL 里 `data/...` 改成 `$WORKTREE/data/...`。
- 优：不搬数据、零 git 风险、改动小。
- 劣：**band-aid 且漏修**——(1) 选股第 4 步"读全部策略视图"也在主仓，只改门控没改读取，过了门却读空；要改就得把所有读路径都改。(2) **web＋eod-review＋每日分析机制设计前提**仍读主仓 → 合作者网页当天空白，复盘照样瞎。(3) 把 SKILL 提示词**耦合到部署拓扑**（dailyjob 路径），拓扑再变（路径/worktree 名）SKILL 静默失效——**反防未来函数**。(4) 改 SKILL = 改未来选股行为，**需统筹/用户拍板**。(5) 不解 ①a。
- 判定：**否**（治标不治本，补丁面反而扩大）。

### 方案 B — 闭环末尾把当日 analysis＋receipt（＋breadth）copy/rsync 回主仓 ✅ Phase-1 推荐
在 `pull_refresh.sh` 尾部加一步：产出后，把 `dailyjob/data/analysis/<D>/`＋`market_forecast.json`＋scorecard＋`sync_receipts/<D>.json` **rsync 到主仓绝对路径**；**receipt 最后写**（保住门控"receipt 存在⟹全套就绪"的语义）。
- 优：(1) **恢复 09-08 前的不变量**——主仓重新成为消费侧唯一真源，**一处改、全部消费者（选股门控＋读、web、复盘、机制设计前提）一次性满足**，无需逐个打补丁。(2) **零 git 风险**——往主仓 `data/analysis/<D>/` 塞 daily 文件正是 09-08 前的稳态行为，daily 不进 git、无跟踪文件 churn。(3) **不碰 SKILL/launchd 注册**，只改 wrapper 脚本体。(4) **防未来函数**：将来任何新消费者读主仓即可用。
- 劣：(1) daily 目录两处各存一份（磁盘 2×，量小可接受）。(2) copy 需原子性（先 rsync analysis 完成、receipt 收尾最后落，避免消费者看到半套）。(3) **breadth 若也回写**会触 ①a（跟踪路径变脏挡主仓 ff-only）——但选股不依赖 breadth，**Phase-1 只回写 analysis＋receipt 即可解选股**；breadth 回写留给 market_breadth.sh 单独处理并入 ①a。
- 判定：**推荐（Phase-1）**。最贴合"恢复不变量"、单点、防未来函数；唯一需拿捏的 breadth 与 ①a 耦合，靠"选股不碰 breadth"绕开。

### 方案 C — 只 symlink 安全的 sync_receipts＋另法处理 analysis/breadth
receipt 用 symlink 共享，analysis/breadth 另想办法（实则还得 copy）。
- 优：receipt 共享确实干净。
- 劣：(1) **硬骨头没解**——analysis/breadth 仍得 copy，等于在 B 之外**再叠一层 symlink 机制**，两套机制混用、更难推理。(2) receipt 只是一个小 JSON，B 的一条 rsync 顺手带走，**没有任何收益**。(3) 现有主仓 `sync_receipts` 是有历史的真目录，改 symlink 是额外突变。
- 判定：**否**（多机制无增益，被 B 完全覆盖）。

### 方案 D — 让选股任务从 dailyjob 跑
把 `daily-stock-selection` 的 cwd 改成 dailyjob。
- 优：门控＋读视图一次 cwd 搞定、不搬数据。
- 劣：(1) 选股要**写** `docs/每日分析/选股/<date>.md`——cwd=dailyjob 则写进 dailyjob，`commit_analysis_docs`（从主仓/独立 worktree 提交）看不到 → 文档丢，问题挪到输出侧。(2) **dailyjob 每轮 `reset --hard origin/main`**——选股在里面跑，与闭环并发时 reset 会**清掉选股的未跟踪在途产出**，共享 worktree 写竞争，违反"一分支一写者"。(3) eod/noon/intraday/web 仍读主仓 → 拓扑碎片化。(4) 改任务注册＋SKILL cwd，需拍板。(5) dailyjob 被设计成"读最新代码、可自毁重置"的临时体，**不该当持久分析工作区**。
- 判定：**否**（把持久产出塞进会自重置的 worktree，正确性最差）。

### 方案 E — 与 ①a 合并的系统解 ✅ Phase-2 推荐（另开设计轮）
**系统根因**：主仓同时扮演两个冲突角色——① 活的 git 工作树（要保持干净供 ff-only 自更/部署）＋② 数据服务根（web＋分析师读主仓 `data/*`）。c96b10e 把**代码执行**挪出主仓（对），却把**数据消费**留在主仓（错）。
**系统解**：在 `settings.py` 引入 `DATA_ROOT = Path(os.getenv("STOCK_DATA_ROOT", PROJECT_ROOT/"data"))`，让**生产者与所有消费者读同一个数据根**，彻底摆脱"代码在哪/cwd 在哪"。并与 ①a 合并：把分析师的未跟踪写出移出主仓工作树，主仓退化为纯代码/部署树，数据落 `STOCK_DATA_ROOT`——**一箭双雕**解掉误跳过＋ff-only 被未跟踪文档挡。
- 优：**根因级、防整类未来函数、单一真源、把 git 树干净度与数据服务解耦**。
- 劣（也是为何单列 Phase-2）：(1) 面大——动 `settings.py`、pull_refresh/market_breadth、选股/复盘 SKILL、web/data_access、market_forecast/scorecard，＋4 个定时任务。(2) **迁移与"合作者靠 git 拉数据看网页"要求冲突**：632 个跟踪 fixture 若把数据根移出 git 就断了这条；**E 必须拆分**——已提交的历史 fixture 留 git，当日 live 数据走 data root（分层），复杂度在这里。(3) 风险最高，要分步灰度＋回归测试。
- 判定：**推荐为 Phase-2 方向**，本轮不做，须专门一轮设计 §（含与 ①a 的合并方案、fixture/git 的拆分）。

## 3. "改 SKILL 门控路径"是否可接受？

- **技术上**：改选股/复盘 SKILL 的门控路径 = 改**未来选股行为**（SKILL 是定时任务提示词），按协作守则属**需统筹/用户拍板**的改动。
- **建议上**：**不推荐改 SKILL**。理由：(1) 门控读主仓相对路径本身没错——错的是主仓没数据；(2) 改 SKILL 把提示词耦合部署拓扑、反防未来函数（§2-A）；(3) 修不了 web/复盘。**推荐 B——完全不碰 SKILL**，让主仓重新有数据，门控/读取/网页各安其位。
- 换言之：Q3 的答案是"技术上可接受但需拍板，且**不是推荐路径**"。

## 4. 推荐 · 预期效果 · 工作量

### Phase-1：方案 B（立即解堵）
- **动作**：闭环末尾把当日 `dailyjob/data/analysis/<D>/`＋`market_forecast.json`＋`forward_scorecard.csv` 原子回写到主仓绝对路径，**最后**再落 `sync_receipts/<D>.json`（保门控语义）；配套一条测试：断言回写后主仓 `data/analysis/<D>/` 非空且 receipt 最后写。
- **实现约束（统筹定，实现窗务必遵守）**：回写逻辑**放进闭环已调用的 python 步骤里**（随 dailyjob 每轮 `reset --hard origin/main` 自动生效），**不新增 wrapper bash 行**——新增 bash 行需人工外科部署到生产、赶不上次日 15:40 闭环；放 python 步则 09-11 自动就修好、不再跳过。绝对路径取主仓根（不能用 `PROJECT_ROOT`，那在 dailyjob 跑时=dailyjob 自身；用固定主仓路径或 `STOCK_MAIN_REPO` 类显式来源）。
- **范围收敛（统筹定）**：Phase-1 **只动 pull_refresh 链路、不含 breadth 回写**——breadth 由独立 job `com.stock.breadth` 产、回写它要动那个 job=扩范围；选股 α 基准有 fallback（选股 md 市场表），可接受。breadth 回写归 Phase-2/①a。
- **预期效果**（可验证）：下一交易日（09-11）闭环（15:40 起）跑完 → 主仓 `data/analysis/2026-09-11/`＋receipt 自动就位 → 选股 cron 18:36 门控 ①receipt 存在 ②视图齐 **立即通过**，无 90min 轮询、无误跳过；web 当天有数据。验证命令：次日 `ls 主仓/data/analysis/$(date +%F)` 非空 ＆ receipt mtime 落在闭环窗口内。
- **工作量**（agent 视角）：token ≈ input 30–50K（读 pull_refresh＋settings＋upload＋写测试）/ output 5–8K；agent 工时 ≈ 0.5–1h（含统筹审＋次交易日一次实跑验证）。
- **不改**：SKILL、launchd 注册、门控逻辑、git 跟踪集。

### Phase-2：方案 E（根治，另开轮）
- **动作**：`settings.py` 引 `STOCK_DATA_ROOT` 数据根；生产/消费统一读它；与 ①a 合并把分析师未跟踪写出移出主仓树；拆分"已提交 fixture 留 git / 当日 live 走 data root"以不破"合作者 git 拉数据看网页"。
- **预期效果**：误跳过＋ff-only 被未跟踪文档挡两类问题一并消除；新增消费者零改动。
- **工作量**：设计 1 轮（本文外）；实现 token ≈ input 150–250K / output 20–30K，agent 工时 ≈ 3–5h（多文件＋迁移＋灰度＋①a 合并＋回归测试）。
