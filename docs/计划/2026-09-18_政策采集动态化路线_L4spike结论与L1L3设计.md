## 0. TL;DR（含一个需拍板的决策点）

L4（去关键词化·全量快讯流）**原本是四条路里前置不确定性最高的一条，spike 后变成确定性最高的一条**：源通了、能游标翻页、每条自带东财预打标的板块/个股码、板块名能经现有 `industry_map` 单一真源归申万一级。

**这改变了排序前提**：L1（派生式词表）是在「必须按关键词检索」这个范式下的优化，而 L4 直接取消了这个范式。两者有实质重叠。

→ **§5 给出重排建议，需要你拍板。** §3/§4 仍按你要求把 L1/L3 设计写全。

## 1. L4 Spike：探测结论（全部实测，非推断）

### 1.1 源可得性

| 源 | 接口 | 条数 | 结论 |
|---|---|---|---|
| 财联社电报 | `stock_info_global_cls` | 20（硬编码 rn=20） | ❌ 覆盖太薄 |
| 财联社电报·重点 | `stock_info_global_cls(symbol='重点')` | 0 | ❌ 空 |
| **东财 7x24 全球快讯** | **`stock_info_global_em`** | **200 / 页，可游标翻页** | ✅ **可用** |
| 新浪全球快讯 | `stock_info_global_sina` | 20 | ❌ 覆盖薄 |
| 富途快讯 | `stock_info_global_futu` | 50 | 港美股为主，偏题 |
| 同花顺快讯 | `stock_info_global_ths` | 20 | ❌ 覆盖薄 |

东财 7x24 底层：`https://np-weblist.eastmoney.com/comm/web/getFastNewsList`，
参数 `biz=web_724&fastColumn=102&pageSize=200&sortEnd=<游标>`。**普通 `requests` 直连即可，不吃 TLS 指纹墙**。

> 注意区分：`board.py` 记录的东财指纹墙是**板块名单/K线/成分接口**（`stock_board_*_em`）。本轮复验**仍然被墙**（`RemoteDisconnected`），记录依然成立。但快讯流走的是另一个域名，不受影响。两件事不要混为一谈。

### 1.2 翻页与回溯深度

- `sortEnd` 是游标，用上一页返回的 `data.sortEnd` 续拉，实测 7 页 1400 条无阻，**约 0.25 s / 页**
- `pageSize` 服务端封顶 200（传 500/1000 均只回 200）
- 响应 `data.total = 5000` → **可回溯约 5000 条 ≈ 10 天**
- 实测 **2026-09-18 全天 587 条**（00:00:00 – 17:47:01），即**全天完整流只需 3 次请求、不到 1 秒**

> 这一条顺带回答了你之前否掉 B 的那个问题：**全量流不需要轮询**。一天跑一次、往回翻到当日 0 点，就能拿到全天完整流（当日盘中时效另说，但那是你已经明确不打算用加频次解决的部分）。

### 1.3 决定性发现：每条快讯自带东财预打标

`fastNewsList` 每条含 `stockList` 字段，是东财已经挂好的关联标的/板块码。

2026-09-18 全天 587 条实测分布：

| 指标 | 数量 | 占比 |
|---|---|---|
| 带 `stockList` | 393 | 67% |
| 挂到东财板块（`90.BKxxxx`） | 268 | 46% |
| 挂到 A 股个股（`0.` / `1.`） | 105 | 18% |
| **个股或板块二者有其一** | — | **57%** |

**我们今天漏掉的那两条，恰好都在预打标覆盖内**：

```
16:05:12 美股存储芯片股盘前小幅走高   → ['90.BK1137', '105.SKHY']
16:04:11 美股光通信板块盘前延续昨日涨势 → ['90.BK0448', '90.BK0736']
```

这类「盘面异动快讯」正是**关键词检索最难接住**（不含政策词、不挂个股）、而**预打标最擅长**的一类。

### 1.4 BK 码 → 板块名 → 申万一级：链路打通

板块**名单**接口仍被墙，但**逐码解析**可用（`push2.eastmoney.com/api/qt/stock/get?secid=90.BK1137`）：

```
BK1137 -> 存储芯片    BK0448 -> 通信设备
BK0736 -> 通信服务    BK1036 -> 半导体
```

再经项目现有的行业归一单一真源 `industry_map.to_sw`，20 个常见东财板块名实测 **18 个直接命中申万一级**
（存储芯片→电子、通信设备→通信、软件开发→计算机、光伏设备→电力设备…），
仅「贵金属 / 能源金属」缺别名，补两条即可。

**即：不需要新建映射体系，东财板块名能直接插进现有单一真源。**

BK 码稳定，解析结果可长期缓存，不构成常态请求成本。

### 1.5 Spike 结论

L4 的三个前置风险——**源通不通 / 能否回溯 / 打标成本**——全部证伪或大幅下修：

- 源：通，且只要 3 次请求 / 天
- 回溯：10 天，足够冷启动和回补
- 打标：57% 由东财免费预打标 + 现有 `industry_map` 归一，**LLM 只需处理剩下的部分**，而非「每条都要 LLM」

我之前估「每条都要打标 = LLM 成本跳一个量级」，**这个判断被 spike 推翻了**。

| 层 | 做法 | 治什么 |

## 3. L1 设计：派生式词表

### 3.1 词源（全部已存在，零新增依赖）

1. `data/analysis/sector_universe.json` —— S1 周度产出，全申万一级 29 板块 + 热度档（热/温/冷）
2. `data/sector_roster/<板块>.json` —— S2 每日角色表，成分股 `meta.industry` 细分行业自由文本（"光模块""半导体"这类）
3. `tools/analysis/industry_map` —— 行业归一单一真源 + 别名表

### 3.2 派生规则

```
候选词 = {热门板块的申万一级名}                       # 来自 ①，随热度周更
       ∪ {票池/roster 成分股的 meta.industry 细分文本}  # 来自 ②，随成分变化
       ∪ {industry_map 中这些行业的别名}              # 来自 ③
组合词 = 候选词 × _POLICY_TERMS（保留现有设计）
最终词表 = 候选词（裸）∪ 组合词 ∪ _MACRO_TERMS（宏观词仍手写，它们不随板块变）
```

热度档用于**配额**：热门板块给全套组合词，温/冷板块只给裸词，控制请求预算。

### 3.3 硬性交付项：词表按日期归档 + 版本号

词表动态化会破坏回测的 as-of 语义（今天 58 个词、三个月前 22 个词，同一天的 policy 快照重跑结果不一致）。
照 `sector_universe_history` 的模式：

- 每次生成落 `data/analysis/policy_keywords/<date>.json`，含 `{version, date, keywords, 派生来源快照}`
- 回测/复盘按 as-of 日读**当时的**词表
- 与上次 diff 留痕（新增/退休了哪些词，为什么）

**这不是可选项**——不做就是给回测埋雷。这个项目到处是防未来红线，动态词表不版本化会直接污染 forward-shadow 那条线。

### 3.4 代价

40~60 K token，1~1.5 h。改 `tools/collectors/policy.py` + 新增派生模块 + 归档 + 测试。

## 4. L3 设计：关键词产出率记分卡

### 4.1 记什么

政策落盘时，对每个关键词记一行：

| 字段 | 含义 |
|---|---|
| `召回条数` | 该词检索回来多少条 |
| `入库条数` | 过了 `require_industry_hit` 真正落盘多少条 |
| `独占条数` | **只有这个词捞到、别的词没捞到**的条数（去重后的边际贡献） |
| `下游引用数` | 落盘条目被 `focus.py` / `sentiment_judge` 实际取用的次数 |

`独占条数` 是关键指标——多数词会大量重叠，真实边际贡献要去重后才看得出来。

> 已有线索：当前 22 个词里，存储那条是靠宏观词「芯片管制」模糊命中蹭进来的。
> 说明词的产出分布极不均匀，但**现在我们连「哪个词有产出」都答不上来**。

### 4.2 怎么用

- 滚动窗口（如 20 个交易日）内 `独占条数 == 0` 且 `下游引用数 == 0` → 标记退休候选
- 退休**不自动执行**，先只出报告，观察两周再决定是否自动化（避免刚上线就误杀低频高价值词，如「实体清单」这种平时零产出、出事时极关键的词）
- 记分卡本身是 L2（语料自挖）和 L4 值不值得做的**度量前提**

### 4.3 代价

50~70 K token，1.5~2 h。改动集中在落盘时记 `keyword → 产出` + 一个聚合脚本 + 报告。

## 5. 需要拍板：spike 后建议重排

### 5.1 问题

L1 是「**如何更聪明地选检索词**」，L4 是「**不再需要检索词**」。
对本轮触发事件（盘面异动快讯漏采）而言：

| | L1 能否接住 | L4 能否接住 |
|---|---|---|
| 「美股光通信板块盘前延续昨日涨势」 | 靠裸词「光通信」**大概率**能（实测裸词查得到） | **确定**能（在全量流里，且已预打标 BK0448/BK0736） |
| 未来的新概念（CPO/固态电池…） | ❌ 申万31行业和成分股细分文本里不会凭空出现 | ✅ 全量流里天然有，东财会给它挂上对应 BK 板块 |
| 政策类长文（发改委文件/部委规章） | ✅ 关键词检索的强项 | ⚠️ 7x24 快讯流未必收录长文 |

→ **L4 不是 L1 的完全替代，但对我们实际漏的那类消息是更优解**；L1 的价值收缩到「政策类长文检索」这个更窄的场景。

### 5.2 三个选项

| 选项 | 内容 | 代价 | 风险 |
|---|---|---|---|
| **甲（建议）** | A 止血 → **L4 先做**（全量流并入 policy 池）→ L3 记分卡 → 拿数据再判 L1 是否还值得做 | L4 约 80~110 K token / 2~3 h（spike 后大幅下修，因为免去了自建打标）；L3 不变 | L4 是新链路，需要 as-of 归档设计，首次上线要盯一周 |
| 乙 | 按原排序 L1 + L3，L4 押后 | 90~130 K token / 3~3.5 h | **L1 的一部分投入会在 L4 落地后作废**（派生词表用于检索，而 L4 不检索） |
| 丙 | L1 + L3 + L4 一起做 | 170~240 K token / 5~6 h | 一轮改动过大，违反分步 commit 的初衷；且 L1 的必要性本可由 L3 数据回答 |

### 5.3 我的推荐：甲

三条理由：

1. **L4 的不确定性已经被 spike 消掉了**，而它覆盖的正是我们真实漏掉的那类消息。原排序把 L4 放后面，前提是「源通不通不知道」——这个前提已经不成立。
2. **L1 的必要性应该由数据回答，不是由直觉回答**。L4 上线后，如果全量流已经覆盖了 90% 的有效消息，那 L1 的派生词表就是给一条正在退化的链路做优化。先做 L3 记分卡拿到「关键词到底贡献了什么」的数据，再决定 L1 做不做、做多大。
3. **L4 顺带解决了你否掉 B 时关心的那个问题**：全量流一天 3 次请求拿全天，不是轮询，不是加频次堆资源。

如果选甲，L1 不是取消，是**降级为待定**，等 L3 数据出来再判。

## 6. L4 设计草案（若选甲，下一轮细化）

- **取数**：游标翻页拉到当日 00:00，约 3 页 / 587 条 / < 1 s。冷启动可回溯 10 天
- **打标**：`stockList` → A股码经现有 `board_of` / BK 码经 push2 解析（结果缓存）→ 统一过 `industry_map.to_sw` 归申万一级
- **无 stockList 的 33%**：先走规则词表（复用 `_INDUSTRY_TERMS`），仍无命中再考虑 LLM；**不默认每条过 LLM**
- **契约**：并入现有 policy 契约 `{date, title, source, url, region, summary, industries, keyword}`，`keyword` 槽填 `"7x24流"` 以便与检索来源区分、供 L3 记分卡分组统计
- **as-of 归档**：按日落盘原始流，保证回测可复现
- **降级**：源失败 → 现有关键词检索链路仍在，不构成单点
