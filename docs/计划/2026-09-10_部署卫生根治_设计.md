# 部署卫生根治 · 设计文档（只出设计，不含实现）

> 日期：2026-09-10 · 作者：设计子窗（统筹拉起）· 状态：**待统筹/用户审阅后再开实现窗**
> 基线：origin/main `49c7c89`。本文只诊断 + 比较方案 + 给推荐，**不动任何生产代码/配置/launchd**。
> ⚠️ 非投资建议，研究模拟工程。

---

## 一、问题现象（要根治的痛点）

对 **wrapper 类代码**（`ops/launchd/*.sh`）的改动合入 origin/main 后，**不会自动部署到生产**：
生产 launchd 仍执行旧版 wrapper。近期已两次靠手动 `git checkout origin/main -- <file>`
外科式部署绕过（属一次性止血，非机制）。这是一个**系统性的"部署卫生"缺陷**——
只要主仓工作树被脏文件卡住，任何 wrapper 改动都无法落地。

---

## 二、诊断（根因链）

### 2.1 生产 wrapper 从哪读、主仓工作树凭什么要保持最新

- 多数 `com.stock.*` 的 launchd plist 的 `ProgramArguments`，把 **wrapper 脚本本体的路径**
  指向 **主仓工作副本** `…/stock_analysis/ops/launchd/<名>.sh`（如 pullrefresh / intraday_watch /
  breadth / strong / commitdocs）。launchd 触发时，**读的是主仓工作树里那份 `.sh`**。
- wrapper 脚本内部再对**专用 worktree**（`dailyjob` 等）做 `git reset --hard origin/main`，
  以便用最新 **python 代码**跑业务。**但这只更新了 python 层，没更新"被 launchd 读取的 wrapper 脚本本体"**
  ——脚本本体仍来自主仓工作树。
- 因此：**要让 wrapper 改动生效，必须让主仓工作树前进到最新 origin/main。**
- 而把主仓工作树前进的**唯一机制**，是 Claude "开工/eod" 定时会话（cwd=主仓）在起手时执行
  `git merge --ff-only origin/main`（本机无任何 launchd 直接跑 `claude`，故此步只发生在 Claude 会话内）。

> 观察到的过渡态佐证机制脆弱：部分 plist（intraday_review / intraday_screen）已被**手工改成**
> 把脚本路径指向某个 worktree 副本，且残留了旧的主仓路径作为多余位置参数——这正是"没有统一部署机制、
> 靠临时手改 plist"的症状，本身也是隐患。

### 2.2 谁往主仓工作树写"未跟踪分析文档"

- **Claude 定时/交互会话**（盯盘研判、盘中核实、复盘、经验沉淀、部分选股），cwd=**主仓**，
  把 `docs/每日分析/{选股,复盘,经验沉淀}/*.md`（如 `复盘/日内_<date>.md`、`选股/日内全A_<date>.md`）
  直接写进**主仓工作树**。它们相对主仓 HEAD 是**未跟踪**（`??`）或**已跟踪但本地改动**（`M`）。
- 对照：**launchd wrapper**（如午盘全A选股）写产出到 **dailyjob 生产 worktree**，*不*写主仓——
  所以 commitdocs 要同时扫 dailyjob + 主仓两个源（见 `2026-09-07_分析文档自动提交_设计.md`）。

### 2.3 为什么 commitdocs 提交了同名 tracked 版后，主仓还留着未跟踪副本

- commitdocs 在**独立 worktree**（`commitdocs`，`reset --hard origin/main`）里 add/commit/push 到 origin/main，
  **全程不碰主仓工作树**。于是：该 md 在 origin/main 上变成 **tracked**，但**主仓工作树里那份原始副本仍原地不动**，
  相对主仓 HEAD 仍是未跟踪 `??`（主仓 HEAD 尚未含该提交）。

### 2.4 `merge --ff-only` abort 的**精确触发条件**（已实测复现）

主仓下一次 `git merge --ff-only origin/main` 时，incoming 提交里该路径已是 tracked，而工作树同路径有本地文件：

- **未跟踪同名文件** → `error: The following untracked working tree files would be overwritten by merge: <path> … Aborting`
- **已跟踪但本地改动**（`M`）、且 incoming 也改同文件 → `error: Your local changes to the following files would be overwritten by merge: <path> … Aborting`
- （另有分叉态 `fatal: Not possible to fast-forward, aborting`，非本缺陷主线，但同样会卡住主仓前进）

**净效果**：主仓工作树**停在旧 commit** → launchd 读到的 wrapper 脚本本体是旧版 → **wrapper 改动不部署**。
这条链把"分析文档写入位置"与"wrapper 部署"这两件本不该耦合的事**耦合**在了主仓工作树上。

> 现场快照（2026-09-10）印证：主仓工作树同时存在
> `M docs/每日分析/复盘/2026-09-10.md`、`M docs/每日分析/经验沉淀/_待并入.md`、
> `M ops/launchd/commit_analysis_docs.sh`（**别的会话的 WIP**）+ 大量 `?? data/analysis/*`。
> 其中 WIP 的存在，直接决定了下面对"stash 方案"的风险判断。

## 三、方案比较

> 判据（按重要性）：**A. 能否根治"wrapper 改动不部署"** · B. 是否耦合/误伤别的会话 WIP ·
> C. 是否复用已验证的既有模式 · D. 实施与维护复杂度 · E. 对"分析师会话需要最新 python 代码"这条**同源诉求**是否一并解决。

### 方案① 让写分析文档的会话不再往主仓工作树留脏副本
- **①a 改写入位置**：Claude 定时/交互分析会话不再以主仓为 cwd 写 md，改写到**非仓库目录**或**专用 authoring worktree**；主仓工作树 docs/ 由此保持干净。
- **①b 写完清理**：会话/commitdocs 成功入库后，把主仓工作树对应未跟踪副本删除（幂等、只删白名单三目录的 md）。
- 优劣：
  - ✅ 直击污染源，主仓 docs/ 干净后 ff-only 不再被分析文档挡。
  - ⚠️ **不防一般类**：任何"未跟踪→被 incoming 变 tracked"的路径（如新 plist、新 ops 文件）都会重演；历史 abort 就有 plist 命中。
  - ⚠️ **难以对全体会话强约束**：交互会话、临时会话都可能又往主仓写；靠 prompt/纪律维持，回归概率高。
  - ⚠️ 单独用**不解决 E**（wrapper 部署仍绑在主仓 HEAD 上；主仓因别的原因卡住时照样不部署）。

### 方案② eod/同步前先 `git stash -u` 未跟踪，再 ff-only
- 优劣：
  - ✅ 通用——清空工作树后 ff-only 恒成功，不管谁写了什么。
  - ❌ **高风险，与项目纪律正面冲突**：stash 栈跨 worktree/会话共享，`stash -u` 会把**别的会话的 WIP 一并卷走**（现场就有 `M ops/launchd/commit_analysis_docs.sh` 这类 WIP）；恢复用 pop 可能撞车/丢改。环境明令**禁裸 stash**。
  - ❌ **只是推迟不清理**：stash 恢复后未跟踪副本又回到工作树 → 下轮同样 abort。
  - ❌ 若强行加 unique-tag + apply-not-pop + 事后 drop 的严格协议塞进无人值守 eod job，**脆弱且难自愈**。
  - 结论：**不作为主方案**。

### 方案③ wrapper 部署与主仓 HEAD 解耦（推荐主干）
- **③a 各 wrapper 从专用 deploy-worktree 跑，且脚本本体也从该 worktree 读**：把 plist 的脚本路径统一指向一个**常驻 deploy worktree**；wrapper 顶部先 `git -C <deploy-wt> fetch && reset --hard origin/main` 再 `exec` 该 worktree 内的自身/后续步骤。
- **③b 专职 deploy worktree + 统一 plist 指向**：建一个只用于"部署+运行"的常驻 worktree（沿用 dailyjob 同款卫生），所有 `com.stock.*` 的 plist 脚本路径都指向它；该 worktree 由 wrapper 自身在每次触发时 `fetch + reset --hard origin/main` 保鲜（无需额外刷新 job、无 stash）。
- **③c wrapper 顶部 `git checkout origin/main -- ops/launchd` 自更**：把今天的手动外科动作固化进脚本。
- 优劣：
  - ✅✅ **直接根治 A**：被 launchd 读取、被执行的 wrapper 脚本恒等于最新 origin/main，**与主仓工作树是否脏彻底无关**。
  - ✅ **不误伤 WIP（B 优）**：只对独立 deploy worktree `reset --hard`，从不动主仓 HEAD/工作树/stash 栈。
  - ✅ **复用已验证模式（C 优）**：dailyjob 对 python 代码的 `reset --hard origin/main` 已在生产稳定跑；③把同一手法**从"python 代码"扩展到"wrapper 脚本本体"**，认知与运维成本低。
  - ✅ **顺带解决 E**：同一 deploy worktree 既供最新 wrapper、也供最新 python，分析路径不再受主仓 HEAD 拖累。
  - ⚠️ ③c 会往主仓工作树写 tracked 文件（`checkout origin/main -- ops/…` 覆盖工作树），把主仓弄脏、且只更 ops 不更 plist 指向路径 → 只作应急、不作终态。
  - ⚠️ ③a/③b 需**改 plist 脚本指向**（属 launchd 变更，落在实现窗；本设计不改）。**改 launchd 前必须先查对应 job 是否在跑**（unload 会 SIGTERM 杀正在跑的实例）。
  - ⚠️ **需处理"引导悖论"**：plist 指向的那份 wrapper 脚本自身若要更新，得靠 deploy worktree 先 reset。稳妥做法是 plist 指向一个**极薄的固定 bootstrap**（内容近乎不变：只做 `fetch + reset --hard origin/main` 然后 `exec` worktree 内真正的 `<名>.sh`），把"经常变的业务 wrapper"放进 worktree、"几乎不变的 bootstrap"留在被 plist 钉死的位置。

### 方案④ 终态：主仓退出"运行时源"角色（北极星，分期）
- 把主仓工作树**彻底移出生产/调度关键路径**：wrapper 部署走③的 deploy worktree；Claude 分析会话（含定时与交互）从**各自 authoring worktree** 跑与写（①a 的推广）。此后主仓工作树可以永远脏、永远不需要 ff-only 前进，`部署卫生`缺陷从根上不存在。
- 优劣：
  - ✅✅ 结构上消灭"分析文档写入位置 ↔ wrapper 部署"的耦合，一劳永逸。
  - ⚠️ 范围大：要动多处 Claude 定时任务的 cwd/写入约定 + 全部 plist 指向 → **分期**，不宜一轮做完。

## 四、推荐

**主干采用 ③b，配套 ①a，明确拒绝 ② 作主方案，把 ④ 记为北极星分期推进。**

### 为什么这样组合
1. **③b 直击业务痛点且零 WIP 风险**：让"被执行的 wrapper"恒为最新 origin/main，`部署卫生`的表症（wrapper 改动不部署）当场消失；手法是把生产已信任的 dailyjob `reset --hard` 模式平移到 wrapper 脚本源，运维心智负担最低；且顺带解决"分析师会话要最新 python"的同源诉求（E）。
2. **①a 作配套除根**：让分析会话不再往主仓工作树堆未跟踪 md，使主仓 ff-only（若仍被别的用途依赖）恢复健康，并消除污染源本身。①a 单独不够（不防一般类、难对全体会话强约束），故只作配套不作主干。
3. **拒绝 ②**：与"禁裸 stash/共享 stash 栈/现场就有别的会话 WIP"直接冲突，且只推迟不清理，风险收益比最差。
4. **④ 分期**：终态最干净但范围大，留待③+①落稳后，作为收敛主仓角色的后续轮。

### 推荐落地形态（供实现窗参考，非本轮实现）
- 引入一个**常驻 deploy worktree**（沿用 `worktrees/stock_analysis/<名>` 统一路径约定）；plist 脚本路径统一指向该 worktree 内的**薄 bootstrap**，bootstrap 只 `fetch + reset --hard origin/main` 再 `exec` 真正的 `ops/launchd/<名>.sh`。
- **消除现有 plist 里"多余的第二个脚本路径参数 + 手改指向"的过渡态**，回归"plist=薄指针、逻辑在仓库内 wrapper"的既有约定。
- **①a 侧**：为写分析文档的定时/交互会话约定专用 authoring 位置（非主仓工作树），或在入库确认后幂等清理主仓白名单三目录的未跟踪副本。

## 五、预期效果（改动生效后应观察到的现象）

1. wrapper（`ops/launchd/*.sh`）改动合入 origin/main 后，**下一次该 job 触发即用新版**，无需任何人手动 `checkout origin/main -- <file>`。
2. 主仓工作树是否脏、是否卡在旧 commit，**不再影响任何 launchd job 的部署与运行**。
3. 主仓 `git merge --ff-only origin/main` **不再被 `docs/每日分析/*` 未跟踪副本挡**（①a 生效后）。
4. 现场不再出现"plist 指向某个临时 worktree + 残留旧路径参数"的手改过渡态。
5. 别的会话在主仓工作树里的 WIP（如正在改的 wrapper）**全程不被触碰/卷走**。

## 六、测试 / 验收（锁"为什么改"的语义，防未来回归）

> 断言应表达一般约束，不写具体 case/日期。

1. **wrapper 部署闭环**：在 deploy worktree 源上模拟"origin/main 有新版 wrapper"→ 触发对应 job → 断言执行的是新版（可用 wrapper 内一个可观测标记/日志行版本号验证）。
2. **主仓脏工作树不阻断部署**：构造主仓工作树含未跟踪 md + 别的会话 WIP `M` → 触发任一 job → 断言 job 正常跑最新代码、且**主仓 HEAD/工作树/stash 栈零改动**。
3. **ff-only 不被分析文档挡（①a）**：模拟"某分析 md 先未跟踪、后在 incoming 变 tracked"→ 断言主仓 ff-only 成功（清理/改址生效），或断言污染源不再产生。
4. **bootstrap 引导正确性**：断言 plist 指向的薄 bootstrap 能在 worktree 缺失时 fail-loud（非静默跑旧码）、存在时 `reset --hard origin/main` 后 exec 到最新 wrapper。
5. **WIP 保护回归**：断言部署路径任何一步都不含裸 `git stash`/`stash pop`、不对主仓工作树写。

## 七、风险与实施纪律

- **改 launchd 前必查 job 是否在跑**：`unload` 会 SIGTERM 杀正在跑的实例（现场 pullrefresh 就可能在跑）。实现窗改 plist/reload 前先核 `launchctl list | grep com.stock` 与该 job 状态，避开其运行窗口。
- **绝不裸 stash / 不动主仓 HEAD / 不动别人 WIP**：部署路径只对独立 deploy worktree `reset --hard`；主仓工作树、stash 栈一律不碰。
- **引导悖论**：被 plist 钉死的入口保持"薄且近乎不变"，业务逻辑全部下沉到 worktree 内的 wrapper，避免"要更新入口却又依赖入口"的死锁。
- **统一路径约定**：deploy worktree 放 `worktrees/stock_analysis/<名>`，勿散落。
- **脱敏 / data 边界**：白名单式 add，绝不 `git add -A`；`data/` 属 gitignore/产物边界，部署与清理逻辑一律不碰。
- **分期纪律**：③b + ①a 先落、稳定观察数个交易日后，再评估是否推进④（主仓退出运行时源）。每步独立分支、分步 commit、不自合 main。
