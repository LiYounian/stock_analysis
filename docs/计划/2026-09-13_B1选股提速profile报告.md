# B1 选股提速 · ②screenall 性能 profile 报告（2026-09-13）

> 角色：B1 profile 专窗（**只读诊断 + 出报告，不改选股代码/参数、不合 main**）。
> 依据：`docs/计划/2026-09-13_待拍板事项决策简报.md` 第 3 项。
> 结论一句话：**②screenall 是 I/O 主导（网络采集 + LLM 等待），不是 CPU 主导。** 纯 CPU（全 A 打分 + 深阶段合议）实测仅 **~7–10 分钟/单线程**，占 screenall 墙钟约 15–30%；其余 70–85% 是逐票网络采集 + LLM 情绪/回灌的等待。"CPU 吃满"的粗测为真但只发生在**计算窗口**（screener/合议/因子单核跑满），不能代表总墙钟。

---

## 一、口径与方法（可复核）

- **被测对象**：`tools/run.py::run_screen_all`（`python -m tools.run screenall`，生产经 `ops/launchd/pull_refresh.sh` 以 `--no-fetch` 调用）。
- **CPU 侧（实测，网络隔离）**：本 chip worktree 内，`data/master`、`data/raw` **只读 symlink** 到主仓真实数据（5563 只主档），写只落 worktree 自己的 `data/analysis`（不污染生产）。用 `perf_counter` 逐阶段打点、**不加 cProfile**（避免 2–5× 膨胀），跑全 A `no_fetch=True, no_llm=True`。
- **I/O 侧（生产日志估算）**：`~/.local/state/stock/pull_refresh.log`（75MB/105 万行）。**注意：Python 日志无时间戳**（`basicConfig` 未带 `%(asctime)s`），无法直接对 Python 行求墙钟；改用 (a) shell 阶段标记里的 `$(date)` 与硬编码耗时注释、(b) tqdm 进度条内嵌的 `[MM:SS<...]` 真实耗时、(c) 逐维操作计数 × 典型时延 三路交叉估算，**外推假设已就地标注**。
- **诚实边界**：① 因生产日志缺时间戳，screenall **精确墙钟无法从日志还原**，只能给区间估算；② 深阶段（events/factor/council）在隔离环境里遇冷缓存会触发未缓存网络拉取，其纯 CPU 分量以 serialize（已实测 18s/243 只）+ screener 内合议单价外推，未做完整实测。这两点是本报告不确定性的主要来源。

## 四、②screenall 内部：I/O 侧估算

screenall 段 = 生产日志 663→11418 行（约 **10,755 行**）。step② screener 只占前 ~1050 行；**中段 1712→7072 行（~5360 行）全是 collect_values + 候选富集**（新闻/资金流/财报/**LLM 情绪 ×308**），末段是逐票 record 分片上传 + 龙虎榜。

Sep11 富集覆盖报告（真实产出）：`候选定向富集完成(308 只)：news ok132/stale158/empty18; sentiment ok308; financial ok1/stale307; fundflow ok89/stale219`。即当日 **308 只跑了 LLM 情绪**、~150 只新新闻、~89 只新资金流。

I/O 分量（幅度估算，口径见下）：

| 环节 | 机制 | 幅度估算 | 依据/假设 |
|---|---|---|---|
| `collect_values_missing`（378 候选补缺） | 逐维逐票网络（公告/资金流/筹码/主力/一致预期/行业/融资） | ~2–4 min | Sep11 实采 ~615 项，tqdm 2–6 it/s |
| enrich·新闻 + 舆情 + 百度 | 有界并发 workers=**4** | ~1–3 min | need_news ~150 |
| enrich·fundflow **3 趟扫**（ENRICH_FF_SWEEPS=3） | 每趟墙钟预算 **240s** + 10s cooldown | 源限流时**可达 ~12 min** | 冷却跨失败簇设计，throttle 时吃满预算 |
| enrich·财报三表 + 年报 | 逐票网络 | ~1–2 min | need_fin/need_ar |
| enrich·**LLM 情绪 ×308**（run_sentiment） | 有界并发 workers=**4** | ~5–8 min | 308/4 × ~4–6s/票；注释自证「逐票 analyze_stock LLM 是收盘选股主耗时」 |
| **候选池消息面回灌**（candidate_message，另一轮 LLM） | 并发 workers=**6** | ~5–10 min | `parallel.py` 注释：该节点**原 ~30min 串行**，现线程池并发 |
| `run_events`/`run_factor` 市场/指数拉取 | 一次性网络 | ~1–3 min | 冷缓存实测卡在 293-item 事件拉取 |
| `collect_ticks` / `collect_lhb` / 记分卡 | 逐票网络 | ~2–5 min | 龙虎榜逐票 2–5 it/s |

**日志侧硬证据**：screenall 段 **825 行** LLM/情绪/专家相关；tqdm **已完成的多项进度条**（仅 ≥1s 的）累加就 **≥17.6 min**（209 条）——且这是**严重低估**，因绝大多数逐票条是 `[00:00<00:00]` 亚秒级、未被计入。

**结论**：screenall 内 I/O（网络采集 + 两轮 LLM）稳超 20–30 min，是墙钟主体；CPU ~7–10 min 单线程是次要项。

## 五、CPU vs I/O 判定

- **纯 CPU（screenall 内）**：step② 4.5min + 深阶段 ~2–4min ≈ **7–10 min / 单线程**（占 screenall 墙钟约 **15–30%**）。
- **I/O（screenall 内）**：collect_values + 富集（新闻/资金流/财报）+ **两轮 LLM**（情绪 308 + 候选池回灌）+ 事件/因子市场拉取 + 龙虎榜 ≈ **20–40 min**（占 **70–85%**）。
- **数据线 ①（screenall 外、但属"选股慢"痛点）**：①自采全 A K 线 **~73 min**（生产 screenall `--no-fetch` 不含此步，但整条日更含）。

> "统筹粗测偏 CPU 吃满" = **真**（screener/合议/因子单核跑满），但**误导性**：那是计算窗口的瞬时占用，总墙钟由 I/O 主导。同负载墙钟 2.3× 抖动（6.6h↔15.5h）进一步坐实 I/O 主导。

## 六、提速方向建议（按 ROI 排序，**均不在此实施，待拍板**）

| # | 方向 | 预期收益 | 成本 | 风险 |
|---|---|---|---|---|
| **1** | **调高 LLM/采集并发**（enrich workers 4→8–12、candidate_message 6→12、FETCH_WORKERS 8→12–16） | **削 I/O 主体 40–60%**（两轮 LLM 是大头） | **仅改 config，最低** | 网关 **429 限流**——需配退避/监控；并发上界即限流上界，要试探 |
| 2 | **收盘也裁/降频 策略11**（非 alpha，午盘已裁；页面已诚实标注无超额） | −87s（step② 的 32%） | 改一处 skip | 极低（本就非 alpha） |
| 3 | **并行 step② 的 10 个 screener**（彼此独立、`_safe` 已隔离、只读主档） | 271s→~90s（受最慢 策略11 界定），−~3min | 进程池（pandas GIL-bound 需多进程） | 中：多进程内存/主档只读并发安全需验 |
| 4 | **向量化/numba S05(76s)+council(60s) 的逐票循环** | 各 −50–70% | 中等改造 | 中：须加数值一致性测试锁语义 |
| 5 | **调 fundflow 3趟×240s 预算**（限流时可烧 ~12min） | 峰值 −5–10min | 改 sweeps/budget 或换源 | 中：减趟数可能增缺采率 |
| 6 | **①自采全 A K 线 ~73min**（增量 spot vs baostock 全量、或并行） | 数据线最大单块 | 属 ①数据线、需单独立项 | 中：防除权/未来函数 |

**最值得先做**：**#1（并发 config 调优）**——最低成本、最高 ROI、直击 I/O 主体，且并发基础设施（`tools/parallel.py` 有界并发原语）**已就位，只需调参 + 观测 429**。搭 **#2（收盘裁策略11，白捡 87s）**。#3/#4 是 CPU 侧的中期项，收益绝对值小（step② 本就只 4.5min），排在 I/O 之后。
