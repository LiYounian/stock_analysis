## 0. 总览与设计原则

### 0.1 现状一句话

系统四层:①量化管线(纯 Python,已程序化)②LLM 层(DeepSeek 已接生产,千问配了未接线)③小统计模型 market_forecast(每日滚动重训,但**维间组权重手工固定**)④深度分析层(**逐票研判仍靠 Claude 窗口**)。真正"锁死境外模型 + 非程序化"的只有第 ④ 层的"逐票研判"这一步;真正"会固化"的是第 ③ 层的组权重;真正"乱"的是定时任务(4 套调度基质并存)。

### 0.2 六大设计目标(与用户方向一一对应)

| # | 目标 | 核心痛点 | 本文对应章节 |
|---|---|---|---|
| 1 | 模型可插拔 + 优先千问/DeepSeek + 易升级 | 模型写死一行、路由参数预留未用 | §1 |
| 2 | 谨慎境外模型(Claude 退到兜底) | 逐票研判锁死 Claude 窗口 | §2 |
| 3 | 深度分析 headless 程序化 + 双跑对比 + think 试开 | 无 headless 研判生成器、无双跑框架 | §3 |
| 4 | 小模型文档化(数据源×因子×训练法) | 已有基础但文档与代码不一致 | §4 |
| 5 | 模型实时进化(别固化旧权重) | 组权重手工固定、无漂移监控 | §5 |
| 6 | 统一定时任务框架 | 4 套调度基质、无主动告警、加改任务手工 | §6 |

### 0.3 贯穿全文的设计原则

1. **单一真源(SSOT)**:模型选择、路由、权重、任务定义各有唯一配置出处,代码只引用不散落。
2. **灰度可回退**:任何迁移先"影子模式"并行(新旧同跑、新不作数),达量化闸门才切主;每处切换都保留一键回退到旧行为。
3. **关键路径去外部依赖**:日常自动产出(选股日报/大盘预测)必须能在"无 Claude、无人值守"下跑通;Claude/人退到研发与兜底。
4. **看得见才治得了**:自适应/迁移之前先建"监控与对比"(漂移探针、双跑 diff),用数据而非直觉决定切换。
5. **配置驱动、凭证不入库**:所有 URL/Key/token 走环境变量,注册表/路由/任务表可改配置生效,值与 PII 绝不进 git。

### 0.4 建议实施先后(总览,详见各章路线与 §7)

- **第一波(地基,低风险)**:§1-P1 模型注册/路由骨架(行为零变化) + §4 小模型文档卡(顺手修 README 不一致) + §5-P1 漂移探针(只读历史产物)。
- **第二波(迁移核心)**:§3 headless 逐票研判生成器 + 双跑对比框架(本轮最大块,是"模型迁移"的验证闸门,依赖 §1-P1)。
- **第三波(切换与收编)**:§2 Claude 退出关键路径(闸门达标后) + §5-P2/P3 自适应权重 + §6 统一定时任务框架(可与第二波并行,解耦)。

## §1 模型可插拔 + 路由层(优先千问/DeepSeek,易升级)

### 1.1 现状核查

- **唯一工厂**:`tools/llm/client.py:154 get_client(purpose="extract")` → 恒返回 `OpenAICompatClient(settings.LLM_BASE_URL, LLM_API_KEY, LLM_MODEL)`;`purpose` 参数已预留("未来可路由不同 provider")但**当前完全没用**。
- **模型写死**:`tools/config/settings.py:60 LLM_MODEL = "deepseek-v4-pro"`(换模型改这一行)。
- **路由表已存在但没人读**:`settings.py:77 LLM_ROUTE = {"extract":"openai_compat","sentiment":"qwen","summary":"openai_compat"}` —— 是意向,无任何代码消费它。
- **prompt 集中**:`tools/llm/prompts.py`(各调用点的 instruction/schema 都在此,利于统一治理)。
- **所有程序化 LLM 调用都走 client.py**(统一):event.py(事件抽取/政策打分/UGC 情绪)、news_ai、news_persistence、news_recall(相关性初筛)、financial/llm_text(财报定性)、candidate_message 编排等,均经 `get_client()`。
- **千问配了但完全没接线**:`tools/analysis/sentiment.py:16,24` 的 `score`/`aggregate_score` 全是 `raise NotImplementedError("P4 阶段实现")`,全仓无管线 import;`USE_QWEN_SENTIMENT=True`(settings.py:53)仅意向。
- **think 开关已预留**:`client.py:95` `extra_body={"enable_thinking": False}`,受 `settings.LLM_DISABLE_THINKING` 控(默认关)。

### 1.2 目标

"换成两家(千问/DeepSeek)更新的超级模型只改配置":引入**模型注册表 + 任务路由层**,让"某用途用哪个 provider/model/参数"完全配置驱动;千问、DeepSeek 为一等公民;新模型上引 = 改注册表一行。

### 1.3 设计

**(A) 模型注册表(SSOT,建议新建 `tools/config/model_registry.py`)**

每个 provider 一条声明(dataclass / dict),字段 schema:

```
ProviderSpec:
  id:            "deepseek_v4pro" | "qwen_max" | "claude_opus48" | ...   # 唯一键
  kind:          "openai_compat" | "qwen_delegate" | "anthropic"        # 决定用哪个 client 实现
  model:         "deepseek-v4-pro"                                        # 具体模型名(升级只改这里)
  base_url_env:  "LLM_BASE_URL"     # 只存"环境变量名",不存值(凭证不入库)
  api_key_env:   "LLM_API_KEY"
  params:        {temperature, max_tokens, enable_thinking, timeout}      # 默认参数,可被调用点覆盖
  enabled:       true
  notes:         "内部网关;deepseek 主力"
```

**(B) 任务路由表(SSOT,扩 `settings.LLM_ROUTE` 或并入 registry)**

purpose(任务用途)→ 主 provider + fallback 链:

```
ROUTE = {
  "extract":          {"primary": "deepseek_v4pro", "fallback": ["qwen_max"]},
  "sentiment":        {"primary": "qwen_max",       "fallback": ["deepseek_v4pro"]},
  "summary":          {"primary": "deepseek_v4pro", "fallback": []},
  "relevance":        {"primary": "deepseek_v4pro", "fallback": ["qwen_max"]},
  "financial_verdict":{"primary": "deepseek_v4pro", "fallback": ["qwen_max"]},
  "deep_analysis":    {"primary": "deepseek_v4pro", "fallback": ["qwen_max"]},  # §3 新用途
}
```

purpose 枚举建议覆盖现有全部调用点(见 1.1)+ §3 新增 `deep_analysis`。

**(C) 工厂升级 `get_client(purpose)`**

- 读 ROUTE[purpose] → 取 primary 的 ProviderSpec → 按 `kind` 构造对应 client(`openai_compat`→现 `OpenAICompatClient`;`qwen_delegate`→新 `QwenDelegateClient`;`anthropic`→兜底,见 §2)。
- 保留统一 `LLMClient` Protocol(`client.py:56`,chat/extract/batch_extract 三方法),各 client 实现同接口,业务层不变。
- fallback:primary 抛非瞬时错误或 provider disabled 时,按 fallback 链降级(带日志);瞬时错误仍走现有 `_chat_with_retry` 重试。**fallback 默认行为需拍板**(见 1.7),避免"静默换模型"掩盖故障。

**(D) 千问 client(`QwenDelegateClient`,新)**

两条路线(见 1.7 拍板):①走 内部网关 OpenAI 兼容 API(能复用 `OpenAICompatClient` 骨架,只是不同 base_url/key/model,最省事)②走 `qwen-delegate` CLI(headless、不烧 Bedrock,但要包一层 subprocess + 解析)。**建议优先①**:同 openai 兼容接口,注册表加一条即可,几乎零新代码。

### 1.4 分阶段实施路线(可灰度可回退)

- **P1(地基,行为零变化)**:把 `LLM_MODEL` 单点扩成 registry + ROUTE + 工厂路由;所有 purpose 的 primary 全指向现 DeepSeek。**灰度**:上线即与现状等价。**回退**:ROUTE 全指 openai_compat = 回到今天。
- **P2(千问接线)**:注册千问 provider + 实现/复用 client;把 `sentiment` purpose 路由到千问,先影子跑(与 DeepSeek 双跑,见 §3),达标切主。
- **P3(升级演练)**:接入两家更新模型 = 注册表加一条 + ROUTE 指过去,双跑验证。

### 1.5 风险

- provider 接口语义差异(千问的 `enable_thinking` / `max_tokens` / 温度口径与 DeepSeek 未必一致)→ 由 ProviderSpec.params 吸收差异 + 各 client 内部适配。
- fallback 掩盖真实故障(自动降级后没人知道主模型挂了)→ fallback 必带告警(接 §6 告警)。
- 网关限流:多 provider 并发放大限流风险 → 复用现有 `LLM_EXTRACT_WORKERS` 有界并发 + 退避。

### 1.6 工作量估

- P1 registry + ROUTE + 工厂路由:**~15–25K token / 2–4 agent 小时**(含单测:路由解析、fallback 触发、接口不回归)。
- P2 千问 client + 接线(走①网关):**~15–25K token / 3–5 agent 小时**(走② CLI 再 +10K/+2h)。

### 1.7 待用户拍板点

1. 注册表放**代码常量**(`model_registry.py`,类型安全、随 git)还是 **YAML/JSON 外置**(改不重启、但要防篡改)?——建议代码常量起步,值级开关走 env。
2. 千问走 **内部网关 OpenAI 兼容 API**(推荐,近零新代码)还是 **`qwen-delegate` CLI**(不烧 Bedrock 但要包 subprocess)?
3. fallback **默认开还是显式声明**?自动降级换模型是否可接受(涉及"结果由哪个模型出"的可追溯性)?

## §2 谨慎境外模型:Claude 退到研发/兜底

### 2.1 现状核查

- Claude 窗口在日常闭环里**唯一不可替代的环节 = 逐票深度研判**(方向/类型/操作倾向/进出场/盯点),按 `docs/每日分析/提示词/分析师提示词.md` 的 SOP 手工做。
- `tools/analysis/write_picks.py:12` 头注明确"**一切研判仍是 Agent 的活**",它本身只是**组装器**(客观字段回填、策略 join、防未来交叉核对、schema 校验、md 渲染),不含智能。
- 其余所有环节(量化管线、消息面 LLM 加工)**已 headless、已不依赖 Claude**。

### 2.2 目标

关键路径(日常自动产出)**不锁死 Claude**:日更选股日报 / 大盘预测能在"无 Claude、无人值守"下端到端跑通。Claude 不禁用,退到三个角色:①研发态(SOP/策略迭代、疑难个股深挖)②兜底(headless 失败/低置信/双跑分歧时的人工深度复核)③过渡期对照基准(双跑里的一方,见 §3)。

### 2.3 设计

- **必须去 Claude 化的环节**:日报"逐票研判"(当前唯一 Claude 关键依赖)→ 由 §3 的 headless 生成器接管。
- **去到什么程度**:日常闭环 **100% 可无 Claude 跑通**(headless 研判 → `write_picks` 组装 → 落盘 `每日选股.json` + md)。Claude 从"关键路径必经"变为"关键路径之外"。
- **Claude 兜底怎么接**(两种,可并用):
  - **人工兜底(推荐,零境外程序化调用)**:headless 研判置信低 / schema 校验失败 / 双跑分歧超阈的票 → 标 `待人工复核`,由人在 Claude 窗口深挖。日常不触发时完全不调 Claude。
  - **程序化兜底(可选,需拍板)**:把 Claude 作为一个 provider 注册进 §1 registry(`kind=anthropic`),仅作 `deep_analysis` 的**末位 fallback**,默认不在日更路由。⚠️ 这仍是境外程序化调用,与"将来无法调用"风险相悖 → 默认**不启用**,仅保留接口。
- **分级清单**:
  - P0 关键路径(必须去 Claude):逐票研判、日报生成、大盘预测、数据/消息面管线(后三者已 headless)。
  - 研发/兜底(保留 Claude):SOP 迭代、经验沉淀、疑难票人工复核、多窗编排、本类架构设计。

### 2.4 分阶段实施路线

- 依赖 §3 落地。**P1**:§3 headless 生成器达"影子模式"可用 → 日更同时产出 headless 研判与 Claude 研判(Claude 仍主)。**P2**:双跑闸门达标(§3.3)→ 切 headless 主、Claude 转人工兜底。**回退**:路由/开关切回"Claude 窗口研判"(人工),`write_picks` 链路不变。

### 2.5 风险

- headless 研判质量短期不及 Claude(经验库 65KB 无法整包进 context、叙事深度差)→ 用 §3 双跑闸门 + 人工抽检把关,不达标不切。
- "程序化兜底调 Claude"若被误启用会重新引入境外依赖 → 默认关 + 显式开关 + 文档标注风险。

### 2.6 工作量估

- 本章增量主要是"兜底触发逻辑 + 分级开关"(研判主体在 §3):**~10–15K token / 2–3 agent 小时**。

### 2.7 待用户拍板点

1. headless 研判达到什么**量化门槛**才允许 Claude 退出关键路径?(建议:结构化字段与 Claude 一致率 ≥ X%、picks_schema 校验 100% 通过、人工抽检通过率 ≥ Y%、前瞻收益不劣化——具体阈值见 §3.7)。
2. 是否**保留"程序化兜底调 Claude"接口**(默认关),还是彻底只做**人工窗口兜底**(更符合"谨慎境外")?——建议后者。

## §3 深度分析 headless 程序化 + 双跑对比 + think 试开

### 3.1 现状核查

- **SOP 齐备(最大可复用资产)**:`docs/每日分析/提示词/分析师提示词.md`(v2026-09-03;含硬红线/逐票流程/纪律/**逐票输出格式**)+ 姊妹版 `日内超短线分析师提示词.md`。
- **经验规则库**:`docs/每日分析/经验沉淀/v2026-09-11.md`(最新 ~65KB)逐日累积;SOP 要求"开工先读最新版"。**注意:整包 65KB 不能直接塞 prompt**。
- **报告机读契约齐备**:`tools/analysis/picks_schema.py`(SCHEMA_VERSION=1.0,受控枚举 DIRECTION/TYPE/STANCE/CONF/SENTIMENT_QUALITY,`validate_picks` 校验,如"不给方向时置信必须 '-'" `:103-106`)。
- **组装器齐备**:`write_picks.py` 的 `build_picks_json` / `render_picks_md_tables`,输入 = Agent 逐票研判 JSON(`--analysis` `:335`),输出 `每日选股.json` + `docs/每日分析/选股/<date>.md`。
- **事实输入全部已程序化落盘**:`data/analysis/<date>/<code>.json`(snapshot/signals/prediction/fundflow/chip/holder/financial/tick/council/events/sentiment)+ `news_ai/{code}.json` + `sentiment/{code}.json`,即研判所需事实已备齐。
- **缺口**:**无任何 headless 生成整份逐票研判的代码**;**无双跑对比框架**(仅 `NEWS_PROMPT_NAME_GUARD` 同模型不同措辞的手动 A/B);think 预留但未验证。

### 3.2 目标

用 DeepSeek/千问 headless 跑出**与 Claude 窗口同规格**的逐票研判 JSON(遵循 SOP、通过 picks_schema);建**双跑对比机制**作迁移前闸门;**think 思考模式**作可配开关在时间预算内 A/B 看是否提质。

### 3.3 设计

**(A) 逐票深度研判生成器(新模块,建议 `tools/analysis/deep_analysis.py`)**

- **输入**:某票的 record json + news_ai + sentiment + financial verdict + council/factor 分 + **经验库检索片段**(不整包塞)。
- **prompt**:把 `分析师提示词.md` 的 SOP 结构化进 `tools/llm/prompts.py`(新增 `deep_analysis_instruction` + 输出 schema 对齐 picks_schema 字段);经验库按该票**策略标签/行业/形态**检索相关条目拼入(见拍板:关键词检索 vs embedding)。
- **调用**:经 §1 `get_client("deep_analysis")` → `chat`(自由文本叙事)或 `extract`(结构化字段)。**建议混合**:结构化字段(方向/类型/stance/conf 等,走 extract + picks_schema 强校验)+ 叙事段(理由/盯点/纪律,走 chat)。
- **输出**:符合 picks_schema 的逐票研判 JSON → 喂 `write_picks.build_picks_json`,下游组装/校验/落盘链路**完全复用**。
- **红线继承**:SOP 的防未来函数 / 非投资建议 / 禁反问 / "游资连板不给方向"等纪律必须进 prompt,并由 picks_schema.validate + write_picks 防未来交叉核对兜底。

**(B) 双跑对比机制(新模块,建议 `tools/analysis/dualrun.py`)**

- **并跑**:同一票、同一输入,跑两路(两 provider,如 DeepSeek vs 千问;或同 provider think 开/关)→ 两份研判 JSON。
- **自动 diff**:
  - 结构化字段:方向/类型/stance/conf/sentiment_quality **逐字段一致率**(枚举可精确比)。
  - 叙事字段:关键点覆盖 / 文本相似度(词重叠或 embedding 余弦)作辅助信号(叙事难精确 diff,只作参考)。
- **记录差距**:落 `data/analysis/<date>/dualrun/<code>.json` + 全日一致率汇总报告。
- **裁决**(迁移前闸门):字段一致 → 采纳;分歧 → 按规则(champion 优先 / 标 `待人工复核`);**闸门**=一致率 + 前瞻收益(复用 `tools/backtest/` 底座验证)达标才允许切主(接 §2.2)。
- **复用**:`get_client(purpose)` 的 purpose 路由(§1)使"跑哪两个"配置驱动。

**(C) think 思考模式 A/B**

- `enable_thinking` 提升为 ProviderSpec.params 项(§1);在时间预算内对**同模型开/关**双跑,比一致性/质量/**耗时**;达标(提质且不超预算)再定该 purpose 默认。client.py:95 已预留通路。

### 3.4 分阶段实施路线(可灰度可回退)

- **P1**:建生成器(先单 provider DeepSeek),产出研判 JSON 接 `write_picks`;与历史 Claude 日报**人工比对**校准 prompt。**影子**:产出但不作数。
- **P2**:双跑框架(DeepSeek vs 千问 / think 开关)+ 自动 diff + 一致率报告。
- **P3**:闸门达标 → 切 headless 主(接 §2)、Claude 兜底。**回退**:停用生成器 → 回 Claude 窗口研判。

### 3.5 风险

- 经验库检索质量差 → 研判丢失既往教训(整包塞不下、检索漏召)。用"策略/行业/形态标签检索 + 保留高频通用纪律常驻 prompt"。
- 叙事类字段难自动 diff → 闸门以结构化字段一致率 + 前瞻收益为主,叙事只作辅助 + 人工抽检。

## §5 模型实时进化(别固化旧权重)

### 5.1 现状核查

- **组权重手工常量**:`tools/config/strategy.py:370 "因子权重":{"技术":1.0,"广度":1.0,"消息面":1.0,"资金流":0.0}`(THRESHOLDS["大盘预测"]);读取 `predictor.py:118-120`,合成 `predictor.py:135-139`。不可 env 覆盖。
- **每日重训只训**:标准化 mu/sd、覆盖率缩放 `eff_group_w`(`predictor.py:155-157`,仅对消息面/资金流按训练集覆盖率降权)、定向符号 orient、合成后校准 calib(`_LogReg` `predictor.py:167-168`)。**组权重永不重训**(技术/广度权重恒为配置值)。
- **每日重训机制**:`_fit_predict_asof`(`forecast.py:88-108`)每日/每标的/每 horizon 从零 fit,训练集 = 严格早于 as_of 且标签到期的**全部历史**(expanding window)。
- **回测/评估**:`tools/backtest/market_forecast_backtest.py` walk-forward;`score`(`:85-120`)已算 hit_rate + 三基线(50/多数类/惯性)+ 多空价差 + 分档单调性(Spearman)+ prob_ret_corr(**近似 IC,但全样本单点、非滚动、无 IC 衰减**)。**离线一次性,产物不进日更闭环**。
- **无任何在线自适应/漂移监控/再标定/告警/冻结基线对照**(全仓 grep 确认;market_forecast 目录内零命中)。
- **最大缺口**:**没有脚本把历史 `data/analysis/<date>/market_forecast.json` 的 p_up 对齐事后 fwd_ret** 算滚动命中/校准/滚动 IC。
- **天然接入点**:`eff_group_w` 覆盖率缩放(`predictor.py:155-157`)已是"按某指标缩放权重"的模式;各维分数 `explain`(`predictor.py:176-184`)可追溯;kill-switch 语义(`strategy.py:364-370`,0=关/0.3=激活)+ `--no-fundflow`(backtest)已是 A/B 雏形;日更触发点 `ops/launchd/pull_refresh.sh:114`。

### 5.2 目标

"训练不是一次性、随市场滚动进化":①组权重按近端表现自适应(或定期再标定)②漂移监控(命中/校准/IC 掉了告警并触发再标定)③保留可回退冻结基线做对照,防自适应把模型带偏。

### 5.3 设计

**(A) 漂移监控(先建,只读,`tools/analysis/market_forecast/drift_monitor.py`,新)**

- 对齐历史 `market_forecast.json` 的 p_up 与事后已实现 fwd_ret(`features.build_panel` 的 `fwd_ret/direction` `features.py:194-199`)。
- 算**滚动**近端窗口:命中率(vs 50/惯性基线)、校准误差(Brier / reliability 曲线)、滚动 IC(prob_ret_corr 的滚动版)。**复用 `market_forecast_backtest.score` 与 `_spearman` 指标算子改滚动版**,不重写。
- 阈值告警:近端命中跌破基线 / 校准误差超阈 / IC 转负 → 告警(接 §6 统一告警)+ 触发再标定信号。

**(B) 组权重自适应(challenger)**

- 在 `CompositeModel.fit`(`predictor.py:141-169`)把 `eff_group_w` 从"仅覆盖率缩放"扩成"覆盖率 × 近端表现因子(各维近端 IC/命中)",**技术/广度也纳入**;或更保守:在上层 `_fit_predict_asof` 传入动态 `cfg["因子权重"]`(`forecast.py:106`),不改模型内部。
- 保守约束:自适应权重 = 先验常量 × 近端表现因子,带**上下限 clip** 防极端;设**最小样本门槛**防噪声过拟合。

**(C) 冻结基线对照(champion / challenger)**

- champion = 冻结先验权重集(现 1.0/1.0/1.0/0.0);challenger = 自适应权重集。两者**并行产出**,drift_monitor 对比近端表现;challenger **持续优于**才提拔,防自适应带偏。
- 复用 `--no-fundflow` 式 A/B 开关 + kill-switch 语义作"冻结 vs 激活"载体。

**(D) 滚动进化闭环**

- 日更 forecast 后追加一步 drift 巡检(`pull_refresh.sh:114` 之后);定期(周/月)按 drift 信号再标定组权重先验。

### 5.4 分阶段实施路线(可灰度可回退)

- **P1(看得见)**:drift_monitor(只读历史产物算指标),先让漂移可见,不改模型。**回退**:无风险(只读)。
- **P2(对照)**:champion/challenger 并行产出 + 对照报告(challenger 不作数)。

### 5.6 工作量估

## §6 统一定时任务框架

### 6.1 现状核查(4 套调度基质并存)

| 基质 | 位置 | 运行处 | 状态 |
|---|---|---|---|
| A. launchd | `ops/launchd/*.plist`+`*.sh` | 本地 Mac | 主力,9 job(intraday/intraday_noon/intraday_screen/intraday_watch/breadth/pullrefresh/intraday_review/strong/commitdocs) |
| B. systemd timers | `ops/systemd/*.timer` | 远端 Linux | 在用(midday_q 三段 / sepa 午收 / fetch / autoupdate / nonce / ingest·web 常驻) |
| C. 进程内 APScheduler | `tools/scheduler.py:68-103` | 常驻 python | **默认关**(`SCHED_ENABLED=false` settings.py:153),疑未投产 |
| D. Claude 会话 cron | Claude Desktop harness | 桌面 App | 盘中核实/盘尾复盘/收盘选股,受"挂起漂移"困扰 |

- **重叠冗余**:SEPA 11:35/15:35 在 launchd(已停用)、systemd、APScheduler(默认关)**三处定义**;盘后全量在 APScheduler `full` 与 launchd `pullrefresh` 两处。
- **健壮性缺口**:misfire 补跑**只在没启用的 APScheduler**(`scheduler.py:83,88` misfire_grace_time + coalesce + max_instances=1);launchd plist **均无 misfire/漏跑补偿**(Mac 睡眠错过即丢);systemd 部分有 `Persistent=true`。重试**只在采集层**(`tools/collectors/_retry.py:42`),**调度层无 job 级重试**。**失败/漏跑无任何主动告警**(全仓 grep webhook/飞书/钉钉/smtp/bark 零命中)——只有被动日志 + 退出码 + `output_guard.py`(产出缺口断言 exit 2)。
- **加/改任务极繁琐**:加 launchd 任务要写 plist(每工作日 5 条 StartCalendarInterval Dict)+ wrapper .sh(worktree 卫生/锁/日志/trap 每份手抄)+ `run.py` cmd_* + **手工 launchctl unload/load**(runbook 明确 agent 不执行、须人工);改时间要走完整 unload/load,**无热生效**。
- **可复用地基**:APScheduler `_JOBS` 注册表(已带 `replace_existing` 热更 / coalesce / misfire_grace / cron+interval 两触发)+ `tools/run.py` cmd_* 命令表(所有业务已是 `python -m tools.run <cmd>` 统一形态,天然任务单元)+ `_retry.py`(可上提 job 级)+ mkdir 锁 + `task_guard.sh`(漂移/陈旧锁互斥)+ `output_guard.py`(漏跑判据)。

### 6.2 目标

加任务 = 注册即跑、改任务 = 改完热生效;健壮(电脑睡/卡不漏跑、失败告警重试);收编 4 套基质的乱象。

### 6.3 设计

- **单一任务注册表(SSOT,声明式)**:每任务 `{id, 命令(python -m tools.run <cmd>), 触发(cron 表达式), 超时, 重试策略, 依赖, 告警渠道, enabled}`。以扩展现有 `_JOBS`(`scheduler.py:68`)或独立 `tasks` 声明为起点。
- **执行器 = APScheduler 常驻进程**(已有 misfire/coalesce/热更 replace_existing)为核心;launchd/systemd **退化为"拉起并守护这个常驻进程"的单一 KeepAlive job**,不再逐业务写 plist。
- **加任务** = 注册表加一行 + 热 reload(APScheduler `add_job(replace_existing=True)`);**改时间** = 改 cron 热生效,**无需 launchctl**。
- **健壮性**:
  - 漏跑补偿:misfire_grace + coalesce(唤醒后补跑)；Mac 睡眠保活(caffeinate/pmset,见拍板)。
  - job 级重试:上提 `_retry.py` 为调度原语。
  - 单实例锁:复用 mkdir 锁 + `task_locks` + `task_guard.sh`。
  - **主动告警(最大增量,填全仓空白)**:失败/漏跑 → 飞书/钉钉/mail webhook(凭证走 env);`output_guard.py` 作"当日必达产物"漏跑巡检判据。
  - 守护自身:常驻进程崩溃 = 全线停(单点)→ KeepAlive 拉起 + 心跳告警。
- **与 launchd runbook 关系**:launchd 从"9 个业务 job 逐个手工 load"收敛到"1 个守护常驻调度进程";runbook 从"逐 job 装载"简化为"部署一次守护进程"。远端 systemd 同理收敛或复用同一注册表(适配器分发本地/远端执行器)。
- **收编冗余**:SEPA 三处留一处(注册表单条);盘后全量二处合一。

### 6.4 分阶段实施路线(可灰度可回退)

- **P1(影子)**:定注册表 schema,把现有 9+ 任务声明进去,APScheduler 常驻起来(`SCHED_ENABLED=true`),与现 launchd **并行影子**(记录会不会跑、跑得对不对,不切主)。**回退**:`SCHED_ENABLED=false` 回 launchd 现状。
- **P2(告警)**:补失败/漏跑主动告警(飞书/钉钉,凭证 env)+ 心跳。
- **P3(收编)**:launchd 收敛到守护单 job,下线冗余定义,统一本地/远端注册表。**回退**:plist 保留,可回滚。

### 6.5 风险

- **常驻进程单点**:崩了全线停 → KeepAlive + 心跳告警 + output_guard 兜底;必要时保留关键 job 的 launchd 双保险。

- 单机单点 vs 远端分布式:本地 Mac 与远端 Linux 是否统一到一套注册表需权衡(见拍板)。

### 6.6 工作量估

- 注册表 + 执行器收敛 + 守护:**~35–50K token / 6–10 agent 小时**。
- 主动告警 + 心跳:**~15K token / 3 agent 小时**。
- 收编迁移(下线冗余、统一本地/远端):**~20K token / 4 agent 小时**。

- **外包建议(约法第 13 条)**:本项目重要(见 memory),调研/批量操作起 Claude subagent 自己做,不外包 qwen;真正简单且耗 token 的机械子任务(如批量补文档模板)可考虑外包。

### 7.3 分阶段闸门(迁移不可逆前的把关)

- 模型迁移(§3→§2):**双跑一致率 + 前瞻收益 + 人工抽检**三闸门达标才切主 headless、Claude 退兜底。
- 权重自适应(§5):**challenger 连续 N 期优于冻结 champion** 才提拔,否则 kill-switch 回退。
- 定时任务(§6):**影子并行验证跑得对** 才切执行器,launchd 保留可回滚。
