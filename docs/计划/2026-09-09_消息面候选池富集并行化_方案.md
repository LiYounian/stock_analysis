# 消息面候选池富集并行化 · 方案

日期:2026-09-09  分支:`feat/消息面候选池富集并行化`  基线:`origin/main`(8fb51a6,哲学二财报复用)

## 0. 目标(用户硬要求)

当天选股当天出、要能当天看。「消息面回灌」节点对候选池(约 50–90 只)**逐只串行**富集,实测 ~20–40min,是「当天出不来」主因之一。目标:把这层从 ~30min 压到几分钟,且**结果与串行完全等价**(选股可复现、不因并发乱序而变)。

## 1. 诊断:串行点在哪(耗时占比,墙钟量级)

节点入口 `tools/pipeline/candidate_message.py:run_candidate_message_enrich`:
`build_candidate_pool`(纯数据、不触网,秒级)→ `_default_enrich`(阶段2 采集+LLM)→ `_default_serialize`(组装 record)→ `rescore_pool`(阶段3 回灌打分重排)。

对候选**逐只串行**的循环:

| 循环 | 位置 | 类型 | 每只耗时 | 占比 |
|---|---|---|---|---|
| 新闻采集(东财+新浪+财联社 3 源/票 + `time.sleep`) | `collectors/news.py:fetch_news` `for code` | 网络 IO | ~2–5s | 中(~3–6min/70 只) |
| 舆情(股吧) | `collectors/ugc.py:fetch_ugc` `for code` | 网络 IO | ~1–2s | 小 |
| 百度新闻(前向滚存,多数被新鲜度门控 skip) | `collectors/baidu_news.py:fetch_baidu_news` | 网络 IO | 门控后≈0 | 小 |
| **三层情绪 LLM**(每票 新闻/舆情/政策 多次 LLM 调用) | `run.py:run_sentiment` `for code` → `event.analyze_stock` | LLM | ~10–30s | **大(~12–35min,主因)** |
| news_ai 视图(复用情绪阶段 LLM 缓存,近乎免费) | `analysis/news_ai.py:write_news_ai` `for code` | 缓存命中 | ~0 | 极小 |
| record 组装 | `analysis/serialize.py:serialize_all` `for code` | CPU/读盘 | ~1–2s | 小 |
| 回灌打分(每票 council.convene ×2,CPU、无 LLM/网络) | `candidate_message.py:rescore_pool` `for code` | CPU | 秒级 | 小 |

**非逐候选**(不并行、保持一次):`run_events`(全市场按季度)、`event.score_policy()`(全局一次)、`ff.fetch_fundflow`(批量)。

网关限流:`tools/llm/client.py` 实测会 429(client 已有自动重试退避)。→ 并发**必须有界**,不能无脑全开。

## 2. 并行方案

**核心手法**:给每个逐候选叶子循环加 `workers` 参数(默认 1 = 原串行,**全A 等其他调用方不受影响**);候选节点按 config `消息面回灌.并发数` 一键开并发。用 `concurrent.futures.ThreadPoolExecutor`(IO/LLM 型适合线程)。

- **共享有界工具** `tools/parallel.py:pmap(fn, items, workers)`:`fn(i, item)`,**按输入顺序回填**结果(index 对齐,与完成顺序无关);`workers<=1` 或单元素退化串行;`max_workers=min(workers, n)` 天然把在飞数 ≤ workers(尊重 429)。
- **确定性**:每个叶子把 per-code 产出**按 code 收集进 dict / 按输入序回填 list**,汇总/排序用稳定键(code / 完整分),**只改「怎么算」不改「算什么」**;`rescore_pool` 末尾既有的完整分降序排序保证输出与完成顺序无关。
- **线程安全**:
  - LLM 磁盘缓存 `event._cached_extract` / `financial/llm_text._cached_extract` 原「直接 `write_text`」改**原子写**(同目录**唯一** tmp 名含 pid+线程 id → `os.replace`),杜绝并发同键写坏文件 / 读到半截。
  - store 落盘本就 `_write_json` 原子写、各 code 独立文件,无共享可变;各叶子的累加器(stats/list/dict)改「先各自算、后汇总」。
- **并发度可配 + kill-switch**:config `消息面回灌.并发数`(默认 6,稳妥值;**设 1 = 退回串行**)。保留 client 现有重试退避;ThreadPool 上界即限流上界。

**改动清单**:`tools/parallel.py`(新增)、`config/strategy.py`(加 `并发数`)、`collectors/{news,ugc,baidu_news}.py`(加 workers)、`run.py:{collect_message,run_sentiment}`、`analysis/{news_ai,serialize}.py`、`analysis/event.py`+`analysis/financial/llm_text.py`(原子缓存写)、`pipeline/candidate_message.py`(读并发数、传参、rescore 并行)。

**不动**:合议主排序、全A 主排序、回灌口径(w0.3 / base 剔除 msg / 资金流留 base)、财报哲学二逻辑——只改「并行执行」,不改业务口径。防未来红线不变(只用 ≤as_of 信息,由被复用采集/合议层各自 as_of 锚定保证,并发不放宽口径)。

## 3. 预估提速

串行 ~30min(主要卡在三层情绪 LLM 逐票 ~12–35min + 新闻采集 ~3–6min)。并发数 = 6 时,LLM/网络 IO 型近似线性提速(受网关 429 与单票内已有的 news-item 级并发叠加影响):

- 三层情绪:~12–35min → ~2–6min
- 新闻采集:~3–6min → ~1min
- 合计:**~30min → ~3–6min**(墙钟,理论上界;真实受 429 冷却影响,见风险)。

## 4. 风险 / 回滚

- **429 限流**:无法真烧 token 实测。理论上界:每票内 news-item 已用 `LLM_EXTRACT_WORKERS`(默认 4)并发,叠加候选级 `并发数=6` → 峰值在飞 LLM 请求可达数十。**稳妥并发数建议 6–8**;若真实跑观察到大量 429,调低 `并发数` 或 `LLM_EXTRACT_WORKERS`。client 退避已在,并发只提高吞吐不改单请求重试。
- **回滚**:config `消息面回灌.并发数 = 1` 一键退回串行(行为逐值等价旧路径,测试锁死)。所有 workers 参数默认 1,其他调用方零影响。
- **确定性回归**:`test_并行结果与串行一致` 锁 workers=1 vs 8 逐值相等;`test_缓存并发安全` 锁多线程压同键缓存不坏。

## 5. 测试(mock LLM/采集,不烧 token)

`tests/test_并行富集.py`:并行==串行(评分/重排逐值)、并发有界(≤ 配置值)、缓存并发安全(多线程压同键)、开关退回串行、防未来不破(并发下仍只用 ≤as_of)。
