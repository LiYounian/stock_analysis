## 0. 一句话

已上线的每日兜底（`ops.backfill_turnover`，volume 比率估算）是**治标**；
本设计做**治本**：让 turnover 换源补齐网所依赖的 **baostock 会话在坏掉时能被检测→主动重建→重试**，
使一次登录态失效不再毒化整批补齐、且不再天天复发。

## 1. 诊断（读码定位 → 范围 → 根因）

### 1.1 热路径与相关文件

| 环节 | 位置 | 职责 |
|---|---|---|
| 采集编排 | `tools/collectors/master_sync.py::sync_master` | 主档全量 / spot 增量 / 失败回退 |
| 回退推进主档 | `master_sync._advance_master_from_raw` | 腾讯 fqkline 抓到的尾部 bar append 进主档 |
| **换手补齐网** | `master_sync._enrich_turnover_amount` | 回退源不带额/换手 → 用 baostock 按日期补齐（**本设计核心**）|
| baostock 源 | `tools/collectors/baostock_src.py::session` / `fetch_one` | 登录上下文 + 单票查询 |
| 通用重试 | `tools/collectors/_retry.py::retry_call` / `is_transient` | 瞬时网络错误指数退避 |
| 消费聚合 | `tools/run.py:106-115` | 落 `turnover_enrich` 视图 + 按严重度告警 |
| 每日止血 | `ops/backfill_turnover.py` | 治标兜底（保留不动）|

### 1.2 结构性缺口：回退源不带换手

`_advance_master_from_raw` 的数据来自 `market.fetch_kline`（腾讯 fqkline 端点），
该端点**结构性不返回**成交额/换手率。于是每个走回退的交易日，主档里 amount/turnover 整段 NaN。
补齐网 `_enrich_turnover_amount` 就是为堵这个口子而生——它是**近端换手是否可用的唯一在线来源**。
它一旦失效，下游筹码集中度 / 单日放量类信号大面积降级。

### 1.3 baostock 会话的生命周期与两类失败

`baostock_src.session()`（`baostock_src.py:50-62`）在**每次** `_enrich_turnover_amount` 调用里
做**一次** `bs.login()`，把整个 `for code in need` 循环包在同一个登录态里，退出时 logout。
baostock 的登录态是**进程级模块状态**、且**会超时失效**（源文件头注释已声明）。由此两类失败：

- **登录直接失败**：`session()` 抛 `ConnectionError` → `_enrich_turnover_amount` 外层
  `except` 捕获 → `session_failed=True`、`need` 里全部记 failed、全部保持 NaN。
- **会话中途坏掉**（login 成功，随后某次 `query_history_k_data_plus` 返回
  `error_code != "0"`，如网络接收错误；或底层 socket 断）→ `fetch_one` 抛
  `ConnectionError` → 被**单票** `except` 捕获、`failed += 1` + warning →
  **循环带着一个已死的会话继续跑** → 其后每只票都以同样方式失败。

### 1.4 根因（三点复合）

1. **无会话健康检测 / 无坏会话重建**：一次登录贯穿整批；中途失效后不 logout+重登，
   死会话把**批内其后全部票**一起拖成 NaN。这是"整批塌陷"和"天天复发"的直接原因。
2. **补齐循环里根本没有重试**：`fetch_one` 是裸调用，未过 `retry_call`。即便瞬时抖动
   （baostock 对连接偶发重置/超时）本可一次重试救回，现在也直接判失败。
3. **瞬时错误分类器对 baostock 失明**：即便接上 `retry_call`，`is_transient`
   （`_retry.py:25-39`）只匹配 curl/requests/urllib3 的**英文**特征串
   （"connection reset" / "timeout" / "curl: (56)" …）。baostock 的接口错误以
   **error_code + 中文 error_msg**（如"网络接收错误"）呈现，命中不了任何英文特征串 →
   被判为**非瞬时**、原样抛、不重试。且 `retry_call` 只重试**同一调用**，从不**重登**——
   死会话重试多少次还是死。

> 小结：补齐网把 baostock 会话当成"登录一次、脆弱、坏了也接着用"的黑盒，
> 既不体检、坏了不重建、抖动不重试、且分类器读不懂它的报错。任一登录态老化都会
> 毒化整批并每日复发。**当前的"有声化"（session_failed/filled==0/ratio>0.5 升 error）
> 只做到"坏了能被看见"，没做到"坏了能自愈"。本设计补的正是自愈。**

### 1.5 明确不在本设计范围（避免范围蔓延）

- 腾讯 fqkline 端点本身不返回换手：**结构性、无法在该源内解决**，正是补齐网存在的理由，不改。
- 每日止血 `ops.backfill_turnover`（volume 比率估算）：**保留不动**，作为 baostock 真正全挂时的纵深兜底。
- 下游"现算兜底/熔断"（strategy 侧）：契约不变、阈值不动，退化为最后一层纵深防御。

## 2. 方案（检测 + 重建 + 重试）

### 2.1 设计原则（硬约束，实现窗必须守）

- **纯基础设施改动**：不换数据源、不引新字段、不改补齐口径（turnover 仍走
  `units.to_percent` 百分数真源）。同样的数据、同样的按日期对齐填充。
- **不改 best-effort 契约**：`_enrich_turnover_amount` **绝不向上抛**；坏到底也只是保持 NaN。
- **不改聚合契约**：返回 dict 现有键 `{need, filled, failed, session_failed, still_missing, ratio}`
  **语义不变**（`run.py` 消费 + 既有测试依赖它）。可**追加**只读诊断键（如 `rebuilds`），加了也向后兼容。

### 2.2 三件事

**① 检测（错误分类：会话级 vs 数据级）**

把 baostock 的失败分成两类，用**一般性判据**、不写死具体 error_code 清单于业务层：

- **会话级 / 网络级**（可重建可重试）：登录失败；socket/连接类异常；接口返回
  网络接收/连接类错误。判据集中在 baostock_src（它最懂自己的报错形态），
  对外暴露一个"是否会话级错误"的谓词。
- **数据级 / 源不支持**（**绝不重建、绝不重试**，按单票 skip）：空数据
  （`ValueError`）；北交所/非A股不支持（`fetch_one` 已显式抛 `ValueError`）；
  代码未标识类错误。这类是"这只票本就没有数据"，重建会话是**误伤**（无意义的登录churn）。

> 分类器扩展遵循守则3（描述性一般约束）：判据表达"网络/连接/接收类 → 瞬时可重建；
> 空数据/代码不支持 → 终态跳过"，不塞具体 trace/case。是否复用并扩展共享
> `_retry.is_transient`（补中文/error_code 维度）还是在 baostock_src 内置一个
> `is_session_error`，见 §5 开放口径。

**② 重建（坏会话 → logout + 重登）**

- 补齐循环遇到**会话级**错误时，主动 logout 当前会话、重新 `login()`，再对**当前失败票重试一次**。
- 重建**有上界**：整批 rebuild 次数封顶（如经 env 可调，默认小值）。达到上界仍会话级失败
  → 判定 baostock 真正不可用，走既有 `session_failed` 语义、保持 NaN、升 error、交每日止血兜底。
  （`_retry.py` 的教训：全挂的冷却窗重试也救不了——故必须封顶，避免无意义登录churn 被 baostock 限流。）
- 重建只由**会话级**错误触发；健康会话对某只票返回"空数据"**不得**触发重建（防误伤，见①）。

**③ 重试（单票瞬时抖动 → 指数退避）**

- 单票 `fetch_one` 过一层退避重试（复用 `retry_call` 的退避/jitter 语义），
  前提是**分类器认得 baostock 的瞬时错误**（否则退化为不重试，无收益）。
- 区分两个层次：**同会话内单票瞬时重试**（网络抖动，会话仍活）vs **跨会话重建后重试**
  （会话已死）。实现上先按错误分类决定走哪条：数据级→skip，网络级→（本会话重试耗尽后）触发重建。

### 2.3 幂等 / 无未来函数 论证

- **无未来函数**：baostock 仅按 `[tail.date.min, tail.date.max]` 窗口查询（现状即如此，不放宽窗口），
  只回填**已存在 bar** 的 amount/turnover，不引入任何前视/跨日推断。重建/重试改变的是
  **"补上了几只"**，从不改变**"补成什么值"**——故无未来函数风险。
- **幂等**：补齐是对 tail 就地按 date 对齐 fillna；同批/同日多跑，结果一致（同一 baostock 值覆盖同一 NaN）。
  主档落盘幂等仍由 `append_master_kline` 按 date 去重保证，本设计不触碰落盘路径。
- **口径不变**：turnover 仍经 `units.to_percent("baostock")`（百分数真源），无二次换算。

## 3. 预期效果（生效后应看到的现象）

- **中途坏会话不再毒化整批**：登录态在循环中途失效时，重建+重试后其余票从新会话补上，
  `turnover_enrich` 的 `still_missing` / `ratio` 在"瞬时/老化型"故障下回落到 0 或接近 0
  （对比现状：中途一坏、其后全 NaN）。
- **不再天天复发**："登录态老化"这一最常见的复发类被自愈闭环消化，日志里由
  "连续多日 error（session_failed/filled==0）"转为偶发、且多数自愈后为 info。
- **真正全挂时行为不变**：baostock 彻底不可用（重建到上界仍失败）时，仍
  `session_failed=True`、保持 NaN、升 error、由每日止血 `backfill_turnover` 兜住——纵深防御不塌。
- **对下游透明**：`run.py` 落的 `turnover_enrich` 视图键语义不变（可能多一个 `rebuilds` 诊断键），
  下游现算兜底/熔断契约与阈值不动。

## 4. 测试锁语义（守则6：断言锁住"为什么改"）

在 `tests/test_turnover_unit.py` 增补（既有 4 个 enrich 测试保持通过 = 契约未破）：

1. **坏会话中途→重建后补齐**：mock `fetch_one` 第一次抛会话级 `ConnectionError`、
   重登后成功；断言最终 `filled` 补满、`still_missing==0`、且 **login 被调用 ≥2 次**（发生了重建）。
   → 锁住"中途坏会话能自愈"这一核心动机。
2. **数据级错误不触发重建（防误伤）**：mock `fetch_one` 抛空数据 `ValueError`；
   断言 **login 恰好被调用 1 次**（未重建）、该票记 failed/skip、其余票正常补齐。
   → 锁住"健康会话不被无数据票误拖去重登"。
3. **真正全挂→有界重建后仍失败**：mock 登录/每次调用恒会话级失败；
   断言 **login 调用次数 ≤ 重建上界**、`session_failed` 契约成立、**不抛**、升 error。
   → 锁住"封顶、不无限 churn、纵深兜底不塌"。
4. **瞬时分类器认得 baostock 报错**：单测分类谓词，对 baostock 中文/error_code 形态的
   网络类错误判为**可重建/可重试**、对空数据/代码不支持判为**终态跳过**。
   → 锁住根因1.4-3（分类器失明）不被未来重写悄悄改回。
5. **回归**：既有 `test_enrich_fills_from_baostock` / `_is_best_effort_on_source_failure` /
   `_all_single_failures_escalate_error` / `_switch_off` 全绿 = 聚合契约与 best-effort 不变。

> 断言锁的是**语义**（重建发生/未发生、封顶、不抛、契约键不变），不锁具体 error_code 字面，
> 以免未来 baostock 换措辞就误红。

## 5. 风险与实施纪律

**风险**

- **误伤正常会话**：把"某票无数据"错判成会话级 → 无意义重登、拖慢。缓解：分类器默认保守
  （只把明确的网络/连接/接收类判会话级，其余一律数据级 skip），并有测试2 锁死。
- **登录 churn 被 baostock 限流**：无上界重建可能触发对方登录频控。缓解：rebuild 封顶 + 退避。
- **拖慢采集**：重试/重建增加耗时。缓解：单票重试次数小、重建封顶小、沿用短超时；
  补齐本就 best-effort、只查 tail 几天，增量可控。
- **契约漂移**：改动外溢到 `run.py` 消费或 strategy 熔断。缓解：聚合键只增不改，测试5 回归锁死。

**实施纪律**

- 改动面**仅限** `collectors`：`master_sync._enrich_turnover_amount`（重建/重试编排）+
  `baostock_src`（会话级错误谓词，可选一个"重登"辅助）+（若复用）`_retry` 分类器扩展。
  **不动** `run.py` 消费、**不动** `ops/backfill_turnover` 止血、**不动**下游熔断。
- 可调项走 env（沿用 `FETCH_RETRY` 既有风格）：如 rebuild 上界、单票重试次数——不改代码调激进/保守。
- 分步 commit（守则9）：先分类器 + 单测 → 再重建/重试编排 + 集成测 → 文档。无 AI 署名。
- 守 `data/` gitignored 勿碰；push 前脱敏（本设计无敏感字段）。

## 6. 待统筹拍板的开放口径

1. **rebuild 上界默认值**：建议小值（如 2~3 次/批）。是否可接受，或要更保守/激进？
2. **主动体检 vs 被动重建**：是否在进补齐循环前先对会话做一次轻量健康探针（一次极小查询），
   还是纯"坏了再重建"（reactive）？建议**纯 reactive**（更省、无多余触网），但可讨论。
3. **分类器归属**：扩展共享 `_retry.is_transient`（加中文/error_code 维度，惠及其他源）
   vs 在 `baostock_src` 内置 `is_session_error`（隔离、不影响他源）？倾向后者（隔离、低耦合），请裁。
4. **spot 增量路径是否同源问题**：常规当日增量走 `update_master_from_spot`
   （腾讯/akshare spot），其是否也丢换手、要不要纳入同一韧性设计或**另起一轮**？
   （本设计仅覆盖回退补齐网，建议 spot 路径另评估，避免范围蔓延。）
