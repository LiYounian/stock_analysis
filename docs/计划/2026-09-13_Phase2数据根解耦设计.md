## 0. 一句话结论

Phase-1(方案 B)用「闭环末尾把当日产出 copy 回主仓」**止了血**,但它是**事后补偿**:生产者仍写在 dailyjob、消费者仍读主仓,靠一趟拷贝弥合;且**只回写 analysis＋scorecard＋receipt,不含 breadth**——breadth 至今分裂。

Phase-2(方案 E)**根治整类**:引入 `settings.data_root()` 单一出处,用 **`STOCK_DATA_ROOT` 环境变量**把「数据根」与「代码根」彻底解耦,让 **producer 与全部 consumer 读写同一个数据根**,不再依赖「代码在哪 / cwd 在哪」,也不再依赖事后回写。同时并掉部署卫生 **①a**(分析/回测会话不污染生产 `data/`)。

**核心难点**(决定成败,也是为何 Phase-1 先行):`data/analysis` 有 **632 个 git 跟踪文件**(合作者靠 git 拉数据看网页),不能整体移出 git;所以 E **必须分层**——已提交的历史 fixture 留 git,当日 live 数据走 `STOCK_DATA_ROOT`,读取时二者叠加(overlay)。复杂度全在这条拆分线上。

**推荐**:分 6 个可灰度的小阶段推进(E0→E5),每阶段独立可回退(env 开关);先落 E0/E1/E2/E3(统一注入 ＋ breadth 归位)拿掉分裂根因,E4/E5(会话隔离 ＋ fixture/live overlay)作为收尾。**本轮只出设计,不动代码。**

## 2. 方案 E 设计(STOCK_DATA_ROOT 统一数据根)

### 2.1 核心:单一出处 `settings.data_root()`,读写都从它取

在 `settings.py` 引入**唯一**数据根解析函数,把 1.4 已验证的优先级上收:

```python
# settings.py（示意,非最终实现）
def data_root() -> Path:
    """数据根单一出处。优先级:显式注入 > env > 软链推断 > 默认(代码根/data)。"""
    # 1) 显式(供实验/测试注入,进程级 set_data_root 覆盖)
    if _EXPLICIT_ROOT is not None:
        return _EXPLICIT_ROOT
    # 2) 环境变量(生产 dailyjob / 展示端 / 实验会话各自设)
    env = os.getenv("STOCK_DATA_ROOT")
    if env:
        return Path(env).expanduser().resolve()
    # 3) 软链推断(dailyjob:data/master 是 symlink → 用其目标的祖父作数据根,
    #    与 mirror_to_main.resolve_main_repo 同源,避免两套推断)
    inferred = _infer_from_master_symlink()
    if inferred is not None:
        return inferred
    # 4) 默认:代码根/data(现状,零行为变化)
    return PROJECT_ROOT / "data"

DATA_RAW      = property → data_root()/"raw"      # 全部派生根改成从 data_root() 取
DATA_MASTER   = ... data_root()/"master"
DATA_ANALYSIS = ... data_root()/"analysis"        # ← 新增,收编 store 里散落的定义
DATA_BREADTH  = ... data_root()/"breadth"
DATA_RECEIPTS = ... data_root()/"sync_receipts"
REPORT_DIR    = ... data_root()/"reports"
```

> 实现注意:settings 里现在是**模块级常量**(import 时求值一次)。要么保留常量但改由 `data_root()` 求值(接受 import 时定根),要么改成函数/惰性属性以支持运行期 `set_data_root()`(实验/测试更灵活)。**推荐惰性**——测试和实验会话必须能在 import 后改根(现有 `dataroot.apply_to_store` 就是 monkeypatch 私有变量的临时招,Phase-2 应扶正)。这是一个**待拍板的实现取向**(见 §5)。

**优先级设计**(沿用并统一 1.4):

1. **显式注入** `set_data_root(p)` / CLI `--data-root`:实验、回测、单测用,进程级最高优先。
2. **env `STOCK_DATA_ROOT`**:生产各角色在启动脚本里各设各的(dailyjob 设成主仓 `data`;展示端设成自己的库;实验会话设成 scratch 根)。
3. **软链推断**:dailyjob 的 `data/master` 已是指向主仓的 symlink → 复用 `mirror_to_main.resolve_main_repo` 同一套推断得主仓 `data`,**无需改任何启动脚本即可让 dailyjob 生产直接写主仓**(平滑迁移的关键钩子)。
4. **默认** `PROJECT_ROOT/data`:env/软链都没有 → 完全等同现状,**向后兼容**。

### 2.2 producer 与 consumer 统一注入

- **producer**(upload / market_breadth / write_picks / panel / strategy_scorecard / midday_q_screen …):落盘路径全部从 `settings.DATA_*` 取,而非 `PROJECT_ROOT/"data"/...`。dailyjob 通过②env 或③软链推断把根指向主仓 → **直接写主仓,不再需要事后回写**。
- **consumer**(选股 SKILL 读取层 / eod-review / web `data_access` / midday_q_gate / equal_weight_index):同样从 `settings.DATA_*` 取。主仓侧 env 不设 → 默认 `PROJECT_ROOT/data` = 主仓 data → 与 producer 指向同一处。
- **store 收编**:删掉 `store/repo.py:37` 硬写的 `_ANALYSIS_DIR`,改引 `settings.DATA_ANALYSIS`;`dataroot.py` 的 `apply_to_store` 退化为薄封装(或直接 `settings.set_data_root`),消除「monkeypatch 私有变量」这种脆招。

### 2.3 breadth 回写统一(P2)

三选一,**推荐(a)**:

- **(a) breadth 纳入统一根**(推荐):`market_breadth.OUT_ROOT` 改 `settings.DATA_BREADTH`;dailyjob 根指向主仓 → 直接写主仓 breadth,消费者同根读到。**先把 `data/breadth/2026-09-03.json` 取消跟踪并加 `.gitignore: data/breadth/`**(与 sync_receipts 同待遇,daily breadth 是运行态、不该入库)——这一步清掉 P4 地雷。
- (b) 沿用 Phase-1 补偿式,给 mirror 加 breadth 回写:治标,不推荐(违背「根治」目标,且 breadth 跟踪状态不清时回写会脏主仓)。
- (c) breadth 也 symlink:**禁止**——它当前部分跟踪,symlink 会重演 analysis 的删跟踪坑。

### 2.4 fixture / live 分层(核心难点,P1 与 git 要求的冲突)

**矛盾**:632 个跟踪 fixture 要留 git(合作者拉数据看网页),但当日 live 数据要走 data root、且不该进 git。

**设计:读取 overlay(live 覆盖 fixture)**

- **写**:producer 一律写 `data_root()/analysis/<date>/`(live)。
- **读**:consumer 读某 `<date>` 时,**先看 data_root 的 live,再回落到代码根的 git fixture**——即
  `read(date) = data_root/analysis/<date>  if exists  else  PROJECT_ROOT/analysis/<date>(git fixture)`。
- 默认根 = `PROJECT_ROOT/data` 时,两层重合,行为等同现状(零回归)。
- dailyjob/展示端根≠代码根时,当日 live 走 data root、历史 fixture 仍可从 git 代码树读到 → **两个需求同时满足**。
- **展示端上线后**(见 `计划/展示端与数据同步.md`,数据改走 DB/上传):fixture 层可整体退出 git(`.gitignore` 注释已预告「届时再移出」),overlay 退化为单层 data root。**Phase-2 不做这一步**,只把 overlay 结构搭好,为它铺路。

> overlay 落点:集中在 `store/repo.py` 的 `_resolve_read_date` / `_record_path` / `_view_path` 一层(读路径已收敛在 store),**不散落到各 consumer**。这是把 store「基座层」职责用到位。

### 2.5 实验/回测会话独立命名空间(P5 / ①a)

- 实验会话(人或 Claude 起的回测 / 临时分析)启动时设 `STOCK_DATA_ROOT=<scratch>`(如 `/tmp/stock_scratch/<session>` 或 `data/_scratch/<session>/`,后者加 `.gitignore`)→ 所有 `write_picks`/`panel`/`scorecard` 落 scratch,**读侧靠 overlay 仍能读到主仓 master/raw/analysis fixture**(master/raw 本就共享;analysis 走 §2.4 回落)。
- 好处:实验产物**永不落生产/跟踪目录** → 主仓工作树恒净 → `merge --ff-only` 不再被未跟踪实验数据挡(①a 根治)。
- `output_guard.py` 从「事后拦截」升级为「校验 data_root 已隔离」的护栏(断言实验会话根≠生产根),语义锁进测试。

### 2.6 向后兼容矩阵

| 角色 | STOCK_DATA_ROOT | data_root() 解析 | 效果 |
|---|---|---|---|
| 主仓(默认) | 不设 | `PROJECT_ROOT/data` | 完全等同现状,零回归 |
| dailyjob 生产 | 不设(靠软链推断) | 主仓 `data`(经 master symlink) | 直接写主仓,回写可退役 |
| dailyjob 生产(显式) | 设成主仓 data | 同上 | 不依赖软链,更明确 |
| 展示端 | 设成展示端库根 | 展示端 data | 各自独立 |
| 实验/回测会话 | 设成 scratch | scratch(读回落 fixture) | 不污染生产 |
| 单元测试 | `set_data_root(tmp)` | tmp | 隔离,可断言 |

## 3. 风险与迁移步骤

### 3.1 分阶段迁移(每阶段独立可灰度、可回退)

| 阶段 | 内容 | 风险 | 回退 |
|---|---|---|---|
| **E0** 审计 ＋ 单一出处 | settings 加 `data_root()`/`DATA_*`;**全仓审计** 45 个 `PROJECT_ROOT/data` 引用点,列改造清单;不改行为(默认根=现状) | 极低 | 纯新增 |
| **E1** consumer 收敛到 store | 读路径全走 `settings.DATA_*` / store overlay;store 收编 `_ANALYSIS_DIR` | 低(默认根不变) | env 不设即旧行为 |
| **E2** producer 统一注入 | upload/write_picks/panel/scorecard 落盘走 `settings.DATA_*`;dailyjob 靠软链推断写主仓 | 中(改生产写路径) | env 强制回退旧根 ＋ 保留 Phase-1 回写做双保险 |
| **E3** breadth 归位 ＋ 清地雷 | breadth 走统一根;`data/breadth/2026-09-03.json` 取消跟踪 ＋ 加 gitignore | 中(动跟踪状态) | 单文件可 `git checkout` 复原 |
| **E4** overlay 读回落 | store 读路径加 live→fixture 回落 | 中(读语义变化) | 开关 `DATA_OVERLAY=off` 退单层 |
| **E5** 实验命名空间 ＋ ①a | scratch 根 ＋ output_guard 升级护栏 | 低 | env 不设即旧行为 |

**推荐节奏**:E0→E1→E2→E3 一轮拿掉分裂根因(此后 Phase-1 回写可观察退役);E4→E5 收尾。每阶段一个 commit,跑回归后再进下一阶。

### 3.2 回退方案

- **总开关**:不设 `STOCK_DATA_ROOT` + 默认根=`PROJECT_ROOT/data` → 任何阶段都能瞬时退回现状。
- **双保险窗口**:E2 上线后**保留 Phase-1 回写一段时间**(源==目标时它自动 no-op,零成本),确认 producer 直写主仓稳定 ≥ N 个交易日后再退役(见 §4)。
- **git 层**:E3 动跟踪状态是唯一不可 env 回退的改动 → 必须**独立 commit、单独验证**,便于 `git revert`。

### 3.3 测试策略(锁住「为什么改」的语义)

1. **同根不变量**:构造 producer 写 + consumer 读,断言二者解析出**同一个 `data_root()`**(P1/P2/P3 核心)。参数化覆盖:默认根 / env 根 / 软链根。
2. **跟踪文件不被误删**:测试或 CI 断言迁移脚本执行后 `git ls-files data/analysis` 计数不减(≥632),`data/breadth` 地雷文件被显式取消跟踪而非批量误删。
3. **overlay 回落**:live 缺某 date 时读到 fixture、live 有则 live 优先、默认根下两层重合(§2.4)。
