# A股行情/K线「持续监测·近实时获取」技术调研

> 日期：2026-09-17　类型：技术调研（非投资建议，研究/模拟用途）
> 目标：为「盯盘」功能选型——持续/近实时拿到分时与 K 线，替代频繁打离散快照。
> 现状锚点：项目现用 `tools/pipeline/intraday_snapshot.py`（launchd 定点抓一次落盘），
> 实时源为腾讯 gtimg（`tools/collectors/gtimg_quote.py`，web 盯盘与 pipeline 共用），
> 另有 baostock / tushare / mootdx(通达信 L2) 采集器。**东财 spot 对本机有 TLS 指纹墙**。
> 场景边界：单机、Python、非高频，盯「十几只自选票」，秒级~分钟级刷新即可。

---

## 0. 结论速览（TL;DR）

| 需求档位 | 推荐方案 | 频率/延迟 | 免费 | 改造量(agent视角) |
|---|---|---|---|---|
| **最省事马上能上** | 复用现有 gtimg 采集器，做**自适应轮询循环**（3~6s 一轮拉全自选池 1 个 URL） | 3~6s / 秒级 | ✅ | ~8~15K token，0.5~1.5h |
| **次优增强** | 新浪 `hq.sinajs.cn` 作为**第二源做交叉校验/降级**，同为批量 HTTP | 秒级 | ✅ | +5~8K token，0.5h |
| **最理想长期** | 轮询循环 + **本地行情缓存网关**（进程内环形缓冲/内存 store，供 web 与分析层订阅），分钟 K 由 tick/秒级 quote 本地合成 | 秒级采集、分钟K本地聚合 | ✅ | ~30~50K token，3~6h |
| 备选(付费) | tushare pro 分钟线积分接口 / 券商 L1-L2 / 第三方付费(如 QMT/掘金/Wind) | 分钟~逐笔 | ❌ | 视源而定 |

**一句话建议**：先用「**轮询 + 现有 gtimg**」把盯盘跑起来（几乎零新依赖、零成本），
把新浪源加成第二腿做冗余；把「持续获取」的复杂度收敛到一个**本地缓存网关**里，不要让上层
每个消费者各自轮询。**不要上 websocket**——A股免费源没有官方稳定的行情 websocket，
第三方 ws 网关合规与稳定性都不如"批量 HTTP 轮询"这条项目已验证的路。

## 1. 数据源与接入方式盘点

> 频率/延迟指"能拿到的最新行情距真实成交的滞后"；免费源均为 L1（含现价/涨跌/量额/五档，
> **无逐笔 tick 流**，逐笔只能 mootdx 盘后或付费 L2）。

### 1.1 腾讯 gtimg（`qt.gtimg.cn/q=`）——★项目在用，首选
- **接入**：HTTP GET，一次 URL 逗号拼多只（项目 `_BATCH=50`），返回 GBK `~` 分隔文本。
- **更新频率/延迟**：源方约 **3s 刷新**级；轮询侧秒级可拿到。含五档、量比、换手、开高低、成交额。
- **免费**：✅ 完全免费、无需 key。
- **rate-limit**：无官方额度，但**批量拉**（1 个 URL 拉完 15 只）比"每只一请求"友好得多；
  高频单票轮询才会触发风控/限流。项目已用批量，天然安全。
- **稳定性**：项目已长期依赖，稳定；偶发服务波动靠 `_retry` 兜底。
- **合规**：公开网页行情接口，研究用途；非官方 SLA，勿商用分发。
- **K线**：gtimg 另有分钟/日 K 接口（`web.ifzq.gtimg.cn/appstock/app/...kline`），
  可拿分钟 K；但**盯盘的分钟 K 更适合本地由秒级 quote 聚合**（见 §2.3）。

### 1.2 新浪 `hq.sinajs.cn/list=`——★免费第二源，做冗余/校验
- **接入**：HTTP GET，`list=sh600000,sz000001` 批量，返回 GBK `var hq_str_...` 文本。
- **频率/延迟**：秒级刷新，字段含五档/量额；口径与腾讯基本一致，可交叉校验。
- **免费**：✅ 无 key。
- **rate-limit**：历史上对**高频/无 Referer** 请求会短时封 IP；需带 `Referer: https://finance.sina.com.cn`
  且**批量+适度间隔**（≥3s）。比腾讯略敏感。
- **稳定性/合规**：同 gtimg，公开接口、非官方 SLA、研究用途。
- **定位**：不建议作主源（比腾讯敏感），**作第二腿**：主源异常时降级、或双源不一致时告警。

### 1.3 东方财富（push2 / `push2.eastmoney.com`）——⚠️本机被墙
- **接入**：HTTP，字段最全（含资金流、盘口更细），支持批量 `secids`。
- **本项目现实**：`gtimg_quote.py` docstring 明确"**东财 spot 对本机有 TLS 指纹墙**"，
  requests 直连会被 TLS 指纹拦截。绕过需 `curl_cffi`/`tls-client` 伪装指纹——**引入新依赖 +
  与源方风控军备竞赛**，不划算。
- **结论**：**不推荐**。除非未来必须要东财独有字段（如更细资金流），再评估 `curl_cffi` 方案。

### 1.4 akshare（聚合库轮询）
- **接入**：`ak.stock_zh_a_spot_em()` 全A快照 / `stock_zh_a_hist_min_em()` 分钟K 等。
- **频率/延迟**：底层多走东财，**同样吃 TLS 墙**；且全A快照单次拉 5000+ 只，**重、慢、浪费**，
  不适合"盯十几只秒级刷"。
- **免费**：✅ 但接口常因上游改版而漂移，稳定性弱于直连 gtimg。
- **结论**：**不作盯盘主链路**；可留作盘后校验/补数的便利封装。

### 1.5 tushare pro（付费/积分）
- **接入**：`pro.rt_min` / `pro.rt_k`（实时分钟）需较高积分；`pro.stk_mins`（分钟K）积分门槛。
- **频率/延迟**：分钟级（实时接口）；日线/分钟历史稳定。
- **免费**：⚠️ **积分制**——注册送基础分够拉日线，但**实时/分钟实时接口需充值或高积分**。
- **rate-limit**：按积分定每分钟调用次数；实时接口配额紧。
- **稳定性/合规**：官方商业化、稳定、有文档；**成本换稳定**。
- **结论**：**备选**。项目已有 `tushare_daily.py`，若要"权威分钟历史回补"可复用；
  盯盘实时不必为它付费。

### 1.6 baostock（免费）
- **接入**：项目已有 `baostock_src.py`。
- **频率**：**仅历史**（日/周/月/5-60分钟历史 K），**无盘中实时**、盘后更新。
- **结论**：盯盘用不上；分钟K**历史回补**可用（免费、稳定）。

### 1.7 mootdx / 通达信（TCP 7709，`tdx_l2.py` 已接）
- **接入**：项目已有 `tdx_l2.py`，`Quotes.factory` 走通达信服务器池 TCP。
- **能力**：**免费源里唯一能拿逐笔/五档实时快照**；分钟 K、盘口。
- **频率/延迟**：盘中五档实时快照可拉；逐笔当日 `transaction()` 盘后常空（项目已记此坑，
  回退 `transactions(date=当日)`）。
- **rate-limit/稳定性**：走公共服务器池，**盘中波动/失败率高于 HTTP 源**，单票 try/except 降级。
  逐笔数据量大，**建议只对自选池、勿全A**。
- **合规**：非官方公开协议，研究用途；勿商用。
- **结论**：**盯盘的"深度"腿**——若盯盘要看五档盘口/逐笔微观，用 mootdx 补 gtimg 拿不到的深度；
  但作**主心跳**不如 HTTP 稳。分钟 K 也可由它取，但仍建议本地聚合。

### 1.8 券商 L1/L2 行情（QMT/miniQMT、掘金 GM、Ptrade 等）
- **接入**：需**开券商实盘/仿真账户**并开通对应量化终端；Python SDK 订阅推送（真 websocket/回调）。
- **频率/延迟**：**L1 秒级推送、L2 逐笔+千档委托队列**，专业级、低延迟。
- **免费**：⚠️ QMT/miniQMT 多数券商**免费**（有的要求资产门槛，如 ≥50万或月活）；
  L2 数据有的额外收费。掘金/Ptrade 类似。
- **rate-limit**：推送模式无轮询限流问题；订阅标的数有上限（够十几只自选）。
- **稳定性/合规**：**最正规、最稳、最低延迟**，官方授权数据；缺点是**绑定账户、要装 Windows 端
  QMT 客户端**（miniQMT 可后台），对"单机 Mac + 纯 Python"的本项目部署侵入大。
- **结论**：**长期最理想的实时源**，但**部署门槛高**（券商账户+Windows/QMT 常驻）。
  若未来盯盘要"真低延迟 L2 盘口/逐笔"，这是正解；当前阶段不必上。

### 1.9 第三方付费源（Wind/万得、聚宽 JQData、天软、恒生等）
- **能力**：分钟/逐笔/L2/Level-2 十档，专业 SLA。
- **成本**：Wind 年费数万元级；JQData 有免费试用+付费档。
- **结论**：**机构级**，个人研究项目不推荐，仅列备选。

### 盘点小结表

## 2. 持续获取范式：轮询 vs websocket vs 本地缓存网关

### 2.1 轮询（Polling）——★本场景首选
- **做法**：一个常驻循环，每 N 秒把**全部自选票拼进 1~2 个 URL** 批量拉一次，落内存/store。
- **优点**：复用项目已验证的 gtimg 批量接口；**无新依赖、无协议风险**；十几只票 1 个 URL 一轮，
  网络开销极小；自然幂等、易容错重试；交易时段外自动静默。
- **缺点**：非事件驱动，有固定轮询间隔的"时间粒度"；但秒级足够本项目"秒级/分钟级"目标。
- **关键设计**：
  - **批量而非单票**：N 只票 = 1 个请求，不是 N 个请求（避免限流、省带宽）。
  - **自适应间隔**：交易时段 3~6s；集合竞价/开盘首 5min 可加密到 2~3s；午休/非交易时段停轮询。
  - **礼貌退避**：连续失败指数退避 + 换源（gtimg→sinajs）降级。
  - **只在交易时段跑**：复用 `tools/collectors/calendar.py` 判交易日 + 交易时段闸门。

### 2.2 websocket 长连——⚠️A股免费源不具备，不推荐
- **现实**：A股**没有官方免费的行情 websocket**。市面上的"行情 ws"要么是券商终端(QMT/掘金,
  需账户)、要么是第三方付费网关、要么是**逆向抓包的非官方 ws**（东财/同花顺 web 端的 ws，
  合规与稳定性差、随时改版失效、易触发风控封禁）。
- **结论**：**不为盯盘上非官方 ws**。真要事件驱动低延迟，直接走 §1.8 券商 SDK（那才是正牌推送），
  否则轮询已够。websocket 的复杂度（心跳、断线重连、鉴权、协议解析）不值当。

### 2.3 本地行情缓存网关（Local quote gateway/cache）——★长期架构落点
- **动机**：盯盘 web、盘中分析、告警可能都要"最新行情"。若各自轮询源方，会**放大请求数、
  各持一份漂移的状态**。正解：**一个采集循环 → 写本地缓存（内存环形缓冲 + 可选落 store）→
  所有消费者读本地缓存**（订阅/查询），源方请求收敛到一处。
- **能力**：
  - 持有每票最新 quote + 当日秒级/分钟序列（内存 ring buffer）；
  - **分钟 K 本地合成**：把秒级 quote 聚合成 1min OHLCV（避免额外拉分钟K接口、口径自控）；
  - 供 web 走 SSE/内部接口拉增量，供分析层直接查内存；
  - 落盘按现有 store 分区（`data/intraday/`），断电可恢复。
- **契合项目**：与现有 collector→store→analysis 分层一致；把 `intraday_snapshot.py` 的
  "定点一次"升级为"常驻连续 + 定点仍可落权威快照"。
- **成本**：改造量最大（见 §3），但一次到位、后续盯盘/告警/回放都受益。

### 范式选型结论
> **轮询 = 现在就上；本地缓存网关 = 演进目标；websocket = 不走（除非上券商正牌 SDK）。**
> 三者不冲突：轮询循环正是缓存网关的"采集腿"，先做轮询再把它收进网关即可平滑演进。

## 3. 落地建议（结合本项目现状）

### 阶段 A：最省事马上能上——「gtimg 自适应轮询盯盘循环」
- **做什么**：新增一个常驻脚本/服务（如 `tools/pipeline/intraday_watch.py`），循环调用现有
  `gtimg_quote.fetch_quotes(自选池)`，每 3~6s 一轮，写内存 + 可选追加 `data/intraday/` 分时序列；
  web 盯盘页从这里读，替代"手动点一次快照"。
- **复用**：`gtimg_quote`(采集)、`calendar`(交易日/时段)、`stock_pool`(自选池)、`store`(落盘)、
  `_retry`(退避)。**几乎零新依赖**。
- **交付形态**：CLI 常驻（前台/launchd 常驻）+ 交易时段闸门 + 优雅退出。
- **改造量**：**~8~15K token 输入、0.5~1.5h**（含小测试：交易时段闸门、批量拉、退避降级断言）。
- **风险**：低。唯一注意"礼貌轮询"别把单票拆多请求。

### 阶段 B：加第二源冗余——「sinajs 交叉校验/降级」
- **做什么**：新增 `sinajs_quote.py` 采集器（对齐 gtimg 字段口径），轮询循环里主源失败降级到它，
  或双源比对（价差超阈值告警，抓源方异常）。
- **改造量**：**+5~8K token、~0.5h**。
- **收益**：单源故障不瞎；数据质量有交叉验证。

### 阶段 C：长期——「本地行情缓存网关 + 分钟K本地合成」
- **做什么**：把阶段 A 的循环封成网关服务：内存 ring buffer 存秒级序列，本地聚合 1min OHLCV，
  web 走 SSE/内部 API 订阅，分析/告警层直接查；mootdx 作"深度腿"按需补五档/逐笔。
- **改造量**：**~30~50K token、3~6h**（含网关接口设计、聚合正确性测试、断线恢复、web 对接）。
- **触发条件**：当"多个消费者都要实时行情"或"要盯盘内做实时告警/回放"时再做，不必现在。

### 明确不做/暂缓
- ❌ 东财直连（TLS 墙）、❌ 非官方 websocket（合规/稳定差）、❌ 为实时充 tushare、
  ❌ 全A秒级轮询（只轮自选池）。
- ⏸ 券商 L1/L2 SDK：长期"真低延迟"选项，但要券商账户+QMT 常驻，部署侵入大，按需再评估。

### 与"防未来函数/幂等/准点"纪律的衔接
- 连续轮询用于**盯盘展示与实时告警**；`intraday_snapshot.py` 的**定点权威快照仍保留**（下游分析
  流水线的确定性节点不变），两者互补：网关喂"活"数据给盯盘，快照喂"准点"数据给分析。
- 落盘仍写 `captured_at` 真实抓取时刻，盯盘序列不参与"防未来"的分析口径，避免污染回测。

## 4. 一句话推荐

**现在**：用「腾讯 gtimg 批量 + 3~6s 自适应轮询 + 交易时段闸门」把盯盘跑起来（阶段A），
新浪源作第二腿（阶段B）。**免费、零新依赖、复用现有采集层、当天能上**。
**长期**：演进成「本地行情缓存网关 + 分钟K本地合成」（阶段C），把源方请求收敛到一处；
真要 L2 逐笔低延迟再上券商 SDK。**不碰非官方 websocket，不为实时付费。**
