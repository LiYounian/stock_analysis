# ff-sync 根治设计（主仓 local main 反复被伪冲突挡住无法快进）

> 分支 `fix/ff-sync-root`。⚠️ 研究模拟，非投资建议。
> 落地物：`tools/ops/safe_ff.py`（安全 ff 辅助）+ `tests/test_safe_ff.py`（9 项语义锁）
> + `ops/launchd/commit_analysis_docs.sh` step7（commitdocs 收尾自动安全 ff 主仓）。

## 1. 现象（长期运维痛点）

主仓工作树（`/Users/yqg/Documents/projects/stock_analysis`）在开工/加载新 launchd job 前执行
`git merge --ff-only origin/main` **反复被撞挡**，报：

- `untracked working tree files would be overwritten by merge`（未跟踪撞车），或
- `Your local changes ... would be overwritten by merge`（已改跟踪文件撞车）。

撞车文件几乎都是**每日分析 docs / 每日 data 产出**，逐字节核验**与 origin/main 一致或本地更旧
（0 独有行）**——是**伪冲突**，不是真改动丢失。结果：主仓 local main 长期落后 origin/main
十几~几十提交；每次 load 新 `.sh`/plist/代码前，用户都得手动 `git checkout --`（M 文件）+ `rm`
（未跟踪撞车）再 ff，**极烦、且每次都要人工判断哪些能删**。

## 2. 根因诊断（已核实，引具体文件/代码）

### 2.1 谁把文件推到 origin/main（绕过主仓 local main）

- **`ops/launchd/commit_analysis_docs.sh`（commitdocs job，工作日 11–22 点每小时:20）**：
  - 在**独立常驻 worktree** `~/Documents/projects/worktrees/stock_analysis/commitdocs` 里操作
    （step2 `reset --hard origin/main`）；
  - step3 把**主仓工作树** + dailyjob worktree 的白名单目录 `docs/每日分析/{选股,复盘,经验沉淀,策略建议}`
    的 `*.md` **拷进该 worktree**（`cp -f "$MAIN_REPO/$p/"*.md ...`，见脚本 32–39 行）；
  - step6 `git commit` + `git push origin HEAD:main`（60–61 行）。
  - **关键缺陷**：push 完成后**从不回头把主仓 local main ff 上去，也不清主仓工作树里那些被采走的
    未跟踪/已改副本**。于是主仓 local main 落后了这些提交，而工作树仍留着同名文件 → 下次 ff 撞车。
- **分析师 Claude 会话（在主仓交互产出）**：把 `data/analysis/<日期>/*.json`、`data/reports/*`、
  `data/breadth/*`、`docs/每日分析/*` 作为产出写进**主仓工作树**。这些目录**在 git 里是被跟踪的**
  （`.gitignore` 第 23 行注释：「data/analysis 与 data/reports 暂保留跟踪——合作者靠 git 拉取数据看网页」）。
  它们经人工/会话提交进 origin，或被 commitdocs（docs 部分）采走推上去。

### 2.2 撞车的判据（哪些未跟踪文件真的挡 ff）

一个未跟踪文件只有当 **origin/main 的入向提交在同路径新增/改动了被跟踪文件**时才挡 ff。
实测（`git ls-tree origin/main` ∩ 主仓 `??`）：`data/analysis`(632)、`data/reports`(53)、
`data/breadth`(1)、`docs/每日分析`(94) 均被 origin 跟踪 → 主仓同名未跟踪副本都是潜在 ff 阻挡项。
而**新日期**的 `data/analysis/<新日期>/`（origin 尚未跟踪）**不挡 ff**，ff 不会覆盖它们。

### 2.3 为什么「没有一步把 local main ff 上去」

因为**推送方（commitdocs / 独立 worktree job）与主仓 local main 解耦**——它们只 push origin，
主仓 local main 的追平一直**依赖人工在开工时手动 ff**，而手动 ff 又被伪冲突挡住形成死循环。
（佐证：`docs/日志/开发日志.md` 多条「主仓本地 main 追平 N 提交」「ff-sync 卡住根因诊断」记录，
以及 `docs/每日分析/**` 里十余处「未同步到最新 origin：ff-only 被未跟踪计划文档 abort」留痕。）

## 3. 方案比较

| 方案 | 做法 | 优 | 劣 |
|---|---|---|---|
| **(a) commitdocs 收尾自动安全 ff 主仓**（推荐） | push 后在主仓跑 `safe_ff --apply`：逐文件核伪冲突→清→`merge --ff-only` | 命中根因（推送方顺手把 local main 追平）；每工作日多次自愈，主仓常态保持可 ff；复用同一安全辅助也能给「手动 load 前」「开工」用 | 需要一个「只清伪冲突绝不丢真改动」的谨慎实现（已用 9 项单测锁死） |
| (b) 让写主仓 docs/data 的任务改写到 dailyjob worktree | 主仓不再留副本 → 无撞车 | 从源头消灭副本 | **产出方是交互式分析师会话 + 选股 SKILL**，天然在主仓工作、用户要在主仓读产出；改它=动 SKILL/工作流（本轮禁区），且 data 产出改道成本高、易漏 |
| (c) 开工/load 前 ff 前置自动 stash/clean 伪冲突 | 在每个 ff 前先清伪冲突 | 覆盖手动/开工路径 | 「开工 ff」在**交互 SKILL / 人工**里，没有单一脚本可改；且每处各写一遍易漂移 |

### 推荐：(a) 为主 + 把安全逻辑抽成可复用辅助，天然兼顾 (c)

- **(a)** 直接补上缺失的「推送方追平 local main」这一步，且**只由自动 job 自愈**，用户无感。
- 安全逻辑抽成独立模块 `tools/ops/safe_ff.py`，**同一条命令**也可用于「手动 load 前」和将来「开工」
  （见 §5 运维说明），即 (c) 的收益用**零额外代码**顺带拿到。
- **不采 (b)**：会碰选股 SKILL / 分析师工作流（本轮禁区），且收益不比 (a) 大。

## 4. 实现与安全不变量

`tools/ops/safe_ff.py`：
- **撞车集** = `git diff --name-status HEAD origin/main`（入向改动）∩ 工作树脏文件（未跟踪/已改）。
  origin 侧删除的路径、以及 origin 不跟踪的本地新增，**都不在撞车集，永不触碰**。
- **伪冲突判据**（满足其一才清）：本地副本与 `origin/main` 版本**逐字节一致**，或**本地无独有行**
  （`local_unique_lines==0`，即本地是一致/更旧子集）。
- **铁律**：撞车集里**任一**文件不满足伪冲突判据（本地含 origin 没有的行 = 真改动），
  **整体拒绝**——不清任何文件、不 ff，记 refused 明细留人工（退出码 2）。
- 分叉（HEAD 非 origin/main 祖先）**拒绝**，绝不 `reset --hard`。
- best-effort：内部异常退出码 3，`commit_analysis_docs.sh` step7 捕获后只记日志、不外溢。

`tests/test_safe_ff.py`（9 项，真 git 仓）锁死：伪冲突（一致/更旧）清+ff、真改动（未跟踪/已改）
拒+零丢失、混入 1 个真改动整体拒、origin 不跟踪的新增免触、already-synced/diverged 边界。

**真实环境冒烟**（dry-run 对主仓）：命中 `config/strategy.json`「本地已改但与 origin 逐字节一致」，
正确判 pseudo——正是典型伪冲突。

## 5. 运维说明：以后主仓怎么保持可 ff

1. **常态自愈**：commitdocs（工作日每小时:20）push 后自动跑 `safe_ff --apply` 把主仓 local main
   追平。正常工作日主仓几乎总是可 ff，无需人工。
2. **手动 load plist / 开工前**：若想手动确保可 ff，跑（**替代**旧的 `checkout -- + rm + ff` 手工活）：
   ```bash
   # 先看诊断（不改动）
   ~/.conda/envs/stock_analysis/bin/python -m tools.ops.safe_ff --repo ~/Documents/projects/stock_analysis
   # 确认只有伪冲突后执行清理+ff
   ~/.conda/envs/stock_analysis/bin/python -m tools.ops.safe_ff --repo ~/Documents/projects/stock_analysis --apply
   ```
   - 退出码 0=已 ff 或已同步；2=检出真改动被拒（**这时别手动 rm**，先核那几个文件是不是你/别的会话
     在做的活，是就先提交/挪走，不是再清）；3=内部异常。
3. **绝不 `git reset --hard` / `git clean -fd` 无脑清**：真改动可能混在未跟踪文件里（别的会话 WIP）。
   `safe_ff` 只清逐字节一致或 0 独有行的伪冲突，天然守住这条线。
4. **launchd 配置不由本轮改**：commitdocs plist 仍指向 `commit_analysis_docs.sh`（脚本内部新增 step7），
   launchd 运行时读脚本即生效，**无需 reload**。若脚本尚未随 ff 落到主仓路径，按 §5.2 先手动跑一次
   `safe_ff --apply` 把它 ff 进主仓即可。
