## 二、目标与非目标

**目标**
1. 远端交易日常驻自采全A 主档(Phase 1,代码已就绪 → 部署验证)。
2. 远端对**自选池**做实时报价采集(分钟/秒级快照),供盘中查看。
3. 远端盘中实时监控自选票的形态/阈值(如 VCP 进行中、突破/回踩、涨跌幅告警),触发通知。
4. 本地 ↔ 远端双向:远端供常鲜原始数据(本地 `pull`),本地回推 LLM/情绪增值产物(现有 `upload`);名单双向对齐(复用方案2)。
5. 本地可以**不常开机**——远端自给自足产出"data-only + 实时 + 盯盘",本地开机时才补 LLM 层。

**非目标**
- 远端不跑 LLM(成本/额度考量,`远端数据仓库_...` 已定 LLM 留本地;远端 LLM"未来再说")。
- 不追求毫秒级 tick 级行情(A股免费源做不到,也无必要);目标是"秒级~分钟级快照够盯盘"。

## 三、设计

### 3.1 远端部署采集 + raw 缓存(Phase 1,复用已有代码)

- 部署 `stock-fetch.timer`(交易日每 30min/1h 触发 `ops.remote_fetch`)→ 远端持续推进 `data/master/kline/*.parquet` + raw。
- **关键前置**:首次全A baostock 全量回填(`remote_fetch --backfill`),远端常驻无所谓耗时(~40–60min)。
- 本地 `tools.sync.pull`(已存在)按水位增量拉 → 本地不必自己慢采(现状本地闭环 `pull_refresh.sh` 里 `PULL_FETCH=1` 自采 ~73min 单进程,可改为"从远端 pull"省这 73min)。
- **panel 收缩问题在方案3 里自然消解**:远端有了 `data/master`+raw,`rebuild_artifacts` 就有料可算,不再塌陷。但仍需决策"远端算 data-only 还是只存数据等本地回推"(见 `远端数据仓库_...` Phase 2 的两段式合议,本文不重述)。

### 3.2 远端实时报价采集器(新建)

现状**无任何实时能力**,唯一准实时是资金流页前端直连东财 push2 每 30s 轮询(`web/app.py:114` 注释,纯前端、不落库)。方案3 要一个后端实时采集器。

- **数据源**:复用现有 spot 快照思路(`master_sync` 用的 spot 增量取当日快照),盘中改为**高频轮询**自选池(几十只,非全A → 轻量)。源用腾讯/新浪/东财实时接口(境内远端可达性大概率好,**须真机确认**)。
- **形态**:新建 `ops/remote_spot.py`(oneshot,由 `stock-spot.timer` 盘中每 N 秒/分触发;或常驻 daemon 带内部循环——两者取舍见下)。
- **落地**:实时快照写一张 DB 表 `spot_quote(code, ts, price, pct, volume, ...)`(或内存环形缓冲 + 定期落库),供 web 实时页与监控器(§3.3)读。
- **oneshot timer vs 常驻 daemon**:
  - timer(每 30s 触发一次进程):与现有 systemd timer 风格一致、崩溃自愈简单;但每次冷启动有开销,30s 粒度尚可,秒级偏重。
  - 常驻 daemon(进程内 sleep 循环):秒级轻,但要自己管保活(`Restart=always`)+ 交易日/收盘自动休眠。
  - **推荐**:盘中常驻 daemon(带交易日守卫 + 收盘自动退出),`Restart=always` 保活——秒级盯盘更顺,与 §3.3 监控器可合进同一进程。

### 3.3 盘中实时监控 / 告警(零基础新建)

现状**零基础**(全是日线盘后批,SEPA/VCP 也是收盘判定,`sepa` 子命令注释"15:40 就绪、无实时")。方案3 要"盘中触发"。

三件套:**调度 → 触发规则 → 通知渠道**。

- **调度**:与 §3.2 实时采集器合进同一盘中进程(拿到新快照就评估),或独立 `stock-monitor` timer 读 spot 表评估。推荐前者(数据新鲜、少一次 IO)。
- **触发规则(可配置,别 hardcode)**:一张规则表 `monitor_rule(code, kind, params, enabled)`,kind 如:
  - 价格阈值(突破 N 日高/跌破均线/涨跌幅超 X%);
  - 形态实时化:把现有收盘 VCP/SEPA 判定的"最后一根 K"换成盘中实时价 → "VCP 收缩中(盘中)接近突破";
  - 量能异动(分时量突增)。
  - **复用**:形态判定逻辑复用 `tools.screener`/SEPA 模块,只把输入从"收盘 bar"换成"实时快照拼当日 bar"。
- **触发去抖**:同一票同一规则一个交易日/一段时间只告警一次(状态表记 last_fired),防刷屏。
- **通知渠道**:项目已有 webhook 告警惯例(`docs/参考/远端自动更新与自愈.md` §告警接入用 `curl -X POST <webhook>`)。复用同款——飞书/企业微信/Server酱 机器人 webhook,地址走 env 不入库。**发送消息属"代本人发消息",需用户先授权渠道配置**(见风险 §五)。

### 3.4 双向数据同步:谁权威、如何避免双写冲突

这是方案3 最需要拍板的一致性问题。建议按"**数据分层、各有单一权威**"划清,避免同一份数据两端都写:

| 数据类别 | 权威方 | 流向 | 冲突风险 |
|---|---|---|---|
| 全A 主档 K线 raw | **远端**(自采) | 远端 → 本地(`pull`) | 低(远端单写,本地只读副本) |
| 实时快照 spot | **远端**(盯盘) | 远端自持(本地按需 pull) | 低(远端单写) |
| 分析产物(data 段) | 待定:远端算 or 本地算(Phase 2 决策) | 若远端算→本地补 LLM 覆盖 | 中(两段式合议,`远端数据仓库_...` 已设计弃权/覆盖) |
| LLM/情绪/事件增值 | **本地**(不搬远端) | 本地 → 远端(`upload`) | 低(本地单写) |
| 自选名单 | **本地为真源**,远端 pending 提案 | 双向(复用方案2 §3.3 并集+时间戳裁决) | 中(方案2 已给策略) |

- **核心原则**:**每类数据只有一个"写权威",另一端持只读副本**。杜绝"同一张表两端都 upsert"。
- **产物层**若走 Phase 2 两段式(远端 data-only + 本地 LLM 覆盖),用 `generated_at` 新旧裁决(`ingest.py:167` 已有"旧盖新拒绝 409"机制)+ 合议弃权,天然支持"先 data 落地、后补 LLM 重算覆盖"。

### 3.5 远端阿里云抓行情的网络可行性(需实机验证,列清单)

推断"境内远端比本机稳"(本机有东财 TLS 墙),但**必须真机确认**,验证清单:

- [ ] baostock 全量回填在远端能跑通(Phase 1 首次 backfill)。
- [ ] 腾讯/新浪/东财**实时快照**接口在远端可达、限频可接受(中高频轮询会不会被封)。
- [ ] 东财 push2(资金流)在远端服务端(非浏览器)调用是否可用。
- [ ] akshare 交易日历在远端可达(`remote_fetch` 交易日守卫依赖它,失败回退工作日近似)。
- [ ] 高频轮询下阿里云出网带宽/被限流风险。

## 五、风险

1. **双写一致性**(最大):任何"两端都写同一类数据"都会埋 bug。必须严守 §3.4 的"每类数据单一权威"。评审时逐类核对。
2. **远端资源**:全A 主档 parquet(几百 MB)+ 实时轮询进程 + 监控进程,阿里云实例的 CPU/内存/带宽是否够(本地实测全A 采集峰值 ~414MB;实时轮询自选池几十只很轻,但监控 + web 叠加需压测)。
3. **运维复杂度陡增**:从"1 个 web + 自动更新"变成"web + ingest + fetch + spot + monitor + 多 timer",故障面变大。需 §七 的分模块日志 + 告警兜底,否则难维护。
4. **实时源被封/限频**:高频轮询免费实时源有被限风险,须退避 + 降频兜底 + 陈旧标识(现有 pull 已有"陈旧保留旧数据"范式可借鉴)。
5. **告警渠道 = 代发消息**:接入飞书/企业微信 webhook 属"代本人发消息",**须用户显式授权渠道 + 提供 webhook**(不入库);且要防"监控刷屏"(去抖)。
6. **成本/额度**:LLM 坚持留本地(已定);远端只做 data + 实时 + 盯盘,不烧 LLM 额度。

## 七、工作量估算(agent 视角,分阶段)

| 阶段 | 内容 | 预估 token(in+out) | agent 执行(含审阅+人工上机) |
|---|---|---|---|
| Phase A | 部署已有 Phase 1(运维为主 + 少量配置改) | 低(agent ~30–50K)+ 人工上机 | 0.5–1 天(多为人工) |

## 八、推荐决策路径

- **先决条件**:方案3 只有在"**本地经常不开机、又想要常鲜数据 + 盘中盯盘**"时才划算。若本地能在盘中开着,方案1(本地盯盘)成本低得多,方案3 的远端实时/监控是重复投资。
- **分步走,别一把梭**:
  1. **先只做 Phase A**(部署已就绪的 Phase 1)——低成本验证"远端自采 + 本地 pull"闭环,顺带确认 §六 的网络可达性。这一步做完,本地就能省掉 73min 自采,收益立现、风险最小。
  2. Phase A 稳了、且确有"离开本地也要盯盘"的强需求 → 再上 **Phase B(实时报价)**。
  3. 盯盘看数据不够、要主动告警 → 才上 **Phase C(监控告警)**,并先把通知渠道授权/去抖设计清楚。
  4. Phase D 的名单双向直接复用方案2;产物两段式(远端 data-only)是可选的"锦上添花",非必需,最后再议。
- **与方案2 的关系**:若你其实只想"远端能加名单",别上方案3——方案2 用零新增服务就够。方案3 是"要把远端变成能独立干活的第二个生产节点"才值得的重投资。
