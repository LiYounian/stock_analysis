## 1. REVS 阶段2：R 宏观择时 + 新建 macro.py 宏观数据线

**① 是什么**
给已上线的选股加一层"看大盘环境决定要不要多出票、出多少"的宏观开关（R = Regime 择时），并为此新建一条采集宏观数据（PMI/CPI/信用利差）的数据线 `macro.py`。

**② 目的 / 解决什么痛点**
现在选股只看个股本身好不好，不看大盘冷热。R 层的作用是"大盘差的时候少出票/降仓位、大盘好的时候放开"，是一个**整体择时闸**，不改个股排序，只控总量与仓位。

**③ 谁做 + 工作量**
角色：数据线做 `macro.py`（采集+落盘），策略线做 R 择时逻辑+回测。分两段。
- macro.py 采集线：约 **150K–300K token**、agent 执行 **3–5 小时**（含 akshare 宏观接口实拉验证、发布日对齐防未来函数）。
- R 择时+回测：约 **300K–500K token**、**5–8 小时**（回测闸门验证 R 是否真带来收益）。

**④ 你要在什么之间选 + 各选项差异**
- A. **现在立项**（先做 macro.py，再做 R）——多一条能力，但要占用数据/策略两条线的档期。
- B. **暂缓、排到后面**——先把"选股快、结构化落地、数据根解耦"这些更贴日常痛点的做完再回头。
- C. **只先做 macro.py 数据线**（宏观序列本身有复用价值，大盘预测等其它模块也能用），R 择时以后再说。

**⑤ 统筹推荐 + 理由**
推荐 **B（暂缓立项）**，若一定要动则退而取 C。理由：REVS 四因子合成已被回测证伪，只捞出"估值位"这一个真因子（已进生产）；R 是"轨道二 overlay 择时"，价值不确定且要新接一整条宏观数据（脏活多、要防未来函数）。相比之下第 2/3/4 项都更贴"选股要快、要当天出、要能自动闭环"的日常痛点，优先级更高。

**⑥ 拍板后能否立即执行 + 预期收益**
拍"立项"后需先重开数据窗写 macro.py，不能秒执行。预期收益：**不确定**——R 是否真提升收益要回测证明，可能又是一个"做了发现没 alpha"的结果。建议把档期让给确定性更高的事项。

## 2. 方案B 接生产 P2：让每日选股产出"机器可读"的结构化结果

**① 是什么**
选股结果现在是给人看的 Markdown；把它同时产出一份**结构化 JSON**（含代码/名称/行业/价格），接进每天的选股流程。

**② 目的 / 解决什么痛点**
现在下游（web 展示、复盘对应、回测）要靠"解析人读的文字"来拿选股结果，容易解析错、脆弱。有了 canonical JSON，下游直接读机器格式，稳、可程序化。

**③ 谁做 + 工作量**
角色：一个实现窗/子 agent。工作量**小**：约 **80K–150K token**、agent 执行 **1.5–3 小时**（改选股 SKILL 调 `write_picks.py` + 跑一个交易日 dry-run 验证）。

**④ 你要在什么之间选 + 各选项差异**
- A. **现在接线**——选股 SKILL 里加一步调 `write_picks`，跑 dry-run 确认无误。
- B. **继续搁置**——工具已经写好但没人用，等于沉没成本继续躺着。

**⑤ 统筹推荐 + 理由**
推荐 **A（现在接线）**。核实结论：`tools/analysis/write_picks.py` 已合入生产（72d6edc），但全仓 grep **零生产调用**——工具建好了没接上。这是典型"最后一公里没走完"，成本很低、杠杆很高，接上后下游全部受益、还为后续（结构化复盘/自动对应）铺路。

**⑥ 拍板后能否立即执行 + 预期收益**
可**立即执行**（工具就绪、只差接线+dry-run）。收益：下游读机读格式、告别脆弱的文字解析，选股产物工程化程度上一个台阶。

## 3. B1 选股提速（先 profile 定位瓶颈）

**① 是什么**
选股曾慢到"5 小时"。先用性能剖析（profile）量化到底慢在哪，再决定怎么提速。核心怀疑对象是"全 A 筛选 + 多因子打分 + 合议"这一段（②screenall）。

**② 目的 / 解决什么痛点**
这是你**很在意**的痛点——选股要快、要当天出。但"哪里慢"目前只有粗测（统筹今晚粗测偏 CPU 吃满），没量化证据。乱改可能改错地方。

**③ 谁做 + 工作量**
角色：一个 profile 专窗。
- profile 本身（**只读、无需拍板即可跑**）：约 **50K–100K token**、**1–2 小时**，产出"时间花在哪"的火焰图/耗时表。
- 提速改法（**要拍板**，视 profile 结果而定）：若瓶颈是 CPU 计算 → 向量化/并行/缓存；若是 LLM 调用等待 → 加并发/减调用。量级 **150K–400K token**、**3–6 小时**。

**④ 你要在什么之间选 + 各选项差异**
- A. **开 profile 专窗先量化**（只读、零风险），拿到证据再回来拍具体提速方案。
- B. **不 profile、凭直觉直接改**——快但可能改错地方、白费档期。
- C. **暂不动**——继续忍受当前耗时。

**⑤ 统筹推荐 + 理由**
推荐 **A（先 profile）**。理由：遵循"遇 bug/性能问题先诊断再动手"——profile 是只读、无副作用、无需拍板即可开跑的诊断步；拿到"CPU-bound 还是 LLM-I/O-bound"的定量结论后，提速改法才有的放矢。注意：富集并行化（0410aad）已合、治了一部分**串行**瓶颈，所以现在的"慢"未必还是老瓶颈，更需要重新量化。

**⑥ 拍板后能否立即执行 + 预期收益**
profile **可立即开跑**（不用等你拍）。你真正要拍的是"拿到 profile 结果后走哪种提速改法"。收益：把"选股当天出"从愿望变成有据可依的工程目标。

## 4. Phase-2 数据根解耦（STOCK_DATA_ROOT 环境变量）

**① 是什么**
用一个环境变量 `STOCK_DATA_ROOT` 统一指定"数据放哪"，让所有模块都从同一个真实数据根读写，彻底解决"选股读不到当天闭环产出"的根因。

**② 目的 / 解决什么痛点**
根因是：生产任务把数据写在 dailyjob 的工作副本里，而分析/选股在主仓读——两处**数据位置分裂**，导致选股读不到刚产出的结果。Phase-1（把产出镜像回写主仓，610e4fc）已经**止血**；Phase-2 是**根治整类**问题（含 breadth 回写、分析会话不再污染生产数据）。

**③ 谁做 + 工作量**
角色：数据线实现窗。因为要改多处读写路径、涉及生产数据安全，属**中等偏上**：约 **300K–500K token**、agent 执行 **5–8 小时**（含设计对齐 + 全量测试锁语义 + 灰度验证）。

**④ 你要在什么之间选 + 各选项差异**
- A. **先出设计文档再拍实施**（改动碰生产数据，先留痕审阅、对齐范围）。
- B. **直接立项开干**——快，但碰生产数据不先设计风险高。
- C. **不做、维持 Phase-1 止血**——选股已能读到产出，但根因还在，将来 breadth/其它闭环产物可能再犯同类病。

**⑤ 统筹推荐 + 理由**
推荐 **A（先出设计文档再拍）**。核实结论：`STOCK_DATA_ROOT` 目前只有"大盘预测"一个模块（`tools/analysis/market_forecast/dataroot.py` + 几个回测脚本）在用，**并未全局铺开**——Phase-2 名副其实还没做。原始修复设计（`docs/计划/2026-09-10_选股读不到闭环产出_修复设计.md`）里已把方案E 列为 Phase-2。因为它动生产数据读写路径，按"非 trivial 改动先写计划文档审阅完再执行"的纪律，应先出设计文档。

**⑥ 拍板后能否立即执行 + 预期收益**
拍"先出设计"后，可**立即开设计窗**（1–2 小时出文档），实施等你审完设计再拍。收益：根治"数据位置分裂"整类隐患，分析会话不再污染生产、闭环产物稳定可读。

## 6. 盘中 confirmed 读 scoping：挡住"盘中伪收盘价"

**① 是什么**
主档 K 线在盘中会先写一个"临时收盘价"（provisional，收盘后再覆盖成真收盘价）。已经给主档加了标记和一个"只读已确认 bar"的接口 `get_master_kline_confirmed()`，但**下游还没人用**。这一项=先摸排"哪些消费方在盘中会读主档"，再定要不要让它们改读已确认接口。

**② 目的 / 解决什么痛点**
收盘后再读的消费方（EOD 复盘等）读到的是真收盘价，**没问题**；只有**盘中就读主档**的消费方（怀疑是午盘选股）可能读到那个临时伪收盘价，导致盘中判断用了不准的价。注意：伪收盘价永久留存的隐患已被上游（P0-2）堵死，所以这不是紧急项。

**③ 谁做 + 工作量**
角色：一个子 agent 先做 scoping（**只查不改**）。
- scoping（摸排哪些消费方盘中读主档）：约 **50K–100K token**、**1–2 小时**。
- 若确有盘中消费方需改读 confirmed：追加 **80K–150K token**、**1.5–3 小时**。

**④ 你要在什么之间选 + 各选项差异**
- A. **先做 scoping**（只查不改），拿到"哪些消费方盘中读主档"的清单再定要不要改。
- B. **直接假定午盘选股要改**、动手改读 confirmed——可能改了个其实没读盘中主档的地方，白费。
- C. **不做**——赌所有盘中消费方都不受伪收盘价影响。

**⑤ 统筹推荐 + 理由**
推荐 **A（先 scoping）**。核实结论：`get_master_kline_confirmed()` 接口已在 `tools/store/repo.py`（P0-2 衍生），但全仓下游**零调用**。是否有真实风险，取决于"到底有没有盘中读主档的消费方"——这需要先查清楚（只读、零风险），不宜凭猜直接改。

**⑥ 拍板后能否立即执行 + 预期收益**
scoping **可立即开跑**（只读）。收益：用一个便宜的调研把"盘中会不会用到伪收盘价"这件事查实，避免盲改，也避免留一个隐性数据坑。
