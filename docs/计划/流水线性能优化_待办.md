# 流水线性能优化 · 待办(全A 可扩展性)

> 状态:**OPT-1 / OPT-2 已实现**(2026-08-08,分支 feat/two-stage-pipeline)· 来源:全 35/全A 实跑观察 + 用户提出
>
> 实现要点:
> - **OPT-1**(`tools/pipeline/screen_pattern.py`):两阶段采集——阶段①全A 只采 K线经便宜门
>   (形态+RS+量能)筛候选;阶段②只对候选采基本面/公告跑护栏+正向确认。新增 `_cheap_gate`,
>   护栏输入采集从「pass1 对全体」下移到「pass2 仅候选」。view 新增「候选数」「采集」字段。
> - **OPT-2**(`tools/run.py`):新增全A 两阶段流水线入口 `python -m tools.run pipeline [--universe N]`
>   (`run_two_stage`)——阶段①全A 便宜筛得达标池;候选=达标∪自选;阶段②新闻/LLM情绪/事件/
>   多因子/合议**只对候选**。新增 `collect_values_missing`(skip-if-cached 只补缺失,不重采)。
>   `cmd_all`(自选池深挖)保持不变。council 内核未改(非候选票专家自然弃权)。
> - **实测(纯缓存 fetch=False)**:全A 5539 扫描 / 611 有效 → K线 load 5539 次(阶段①),
>   基本面/公告 load **各 1 次**(仅候选),旧流程会对全 611 只各采 → 护栏采集降 ~600×;
>   阶段②候选(达标0∪自选42)= **42 只** → LLM/新闻调用 42 次而非 5539(降 ~130×)。
> 核心矛盾:当前流水线对**全池每一只**都做"重活"(基本面/公告采集、**新闻采集 + LLM 情绪**),
> 且**筛选(screen)排在最后**。自选池(数十只)尚可,但**无法扩到全 A 5539 只**——
> token 和耗时都会爆炸。要把架构改成"**先便宜地筛,再只对选出的少数做贵活**"。

## 现状证据(2026-08-08 实测)

- `tools/run.py::cmd_all` 顺序:`collect_values → collect_message(新闻) → run_sentiment(LLM情绪) → serialize → events → factor → council → panel → **screen(最后)**`。
  → **新闻采集 + LLM 情绪对全部 codes 做,且在筛选之前**。
- `tools/pipeline/screen_pattern.py` 全A扫描:对 **5539 只每只** 顺序采 **K线 + 基本面 + 公告** 三份(实测 collectors.market/fundamental/announcement 各 ~3231 次调用),合计约 **1.6 万次串行 HTTP**。
  - 耗时真凶不是被墙超时(实测告警仅个位数,基本面/公告走百度/同花顺/巨潮是通的),而是**体量 + 串行**。
  - 基本面/公告是给**护栏**用的,却对全 5539 只**提前全采**——其实只有形态+RS 达标的候选(通常几百只)才需要。

---

## OPT-1:两阶段采集——先 K 线筛,再只对候选采护栏数据

**现状**:全A扫描对 5539 只都采 K线+基本面+公告。
**改法**:
1. 阶段① 便宜筛:全A **只采 K 线**(5539 次)→ 算形态 + 双层 RS → 得候选(几百只)。
2. 阶段② 护栏:**只对候选**采基本面/公告 → 跑护栏(PE分位/净利/合规)+ 正向确认 → 达标池。
**收益**:把"1.6 万次请求"压到"5539 次 K线 + 几百次基本面/公告",快数倍、省网络。
**边界**:改 `tools/pipeline/screen_pattern.py` 的采集编排;`pattern_screener` 形态/RS/护栏逻辑不动,只调整"何时对谁采"。

---

## OPT-2:新闻 + LLM 情绪只对"选出的"做(最贵一步后置)⭐

**现状**:`cmd_all` 对全部 codes 先采新闻 + 跑 LLM 情绪,**再** screen。新闻+LLM 是全流程**最耗时、最烧 token** 的一环。
**改法**:把流水线重排为"**筛选优先、深挖后置**":
1. 便宜阶段(可全A):行情 → 形态/RS/护栏 → **达标池/合议初筛**(不含新闻、不含 LLM)。
2. 收敛:取达标池 / 自选池的**最终候选(~10–40 只)**。
3. 贵阶段(只对候选):**新闻采集 + LLM 情绪 + 事件精数值 + 完整 8 专家合议**,只跑这几十只。
**收益**:LLM 调用量从 O(全池/全A) 降到 O(数十),token 成本与耗时**降一到两个数量级**;这是全A 可扩展的前提。
**边界**:重排 `cmd_all` 步骤 + 让 `run_sentiment`/`run_events`/新闻采集接受"候选子集"入参;`screen`/达标计算前移到新闻/LLM 之前。
**注意**:合议里"情绪三层""事件驱动"两专家依赖新闻/事件数据 → 它们的完整发声也自然只在贵阶段(候选)才有;初筛阶段的合议用不含情绪/事件的专家子集(或让这俩弃权),达标后再补全。需在合议层明确"两阶段合议"口径(与 F3 council owner 对齐)。

## 建议实施顺序 + 归属

1. **OPT-2 优先**(省 token 最狠、且是全A 可扩展前提):重排 cmd_all + 子集入参 —— 归 run.py/pipeline owner(远端域窗口或形态选股窗口),需与合议 owner 对齐"两阶段合议"。
2. **OPT-1 次之**:screen_pattern 两阶段采集 —— 归形态选股窗口。
3. 两者可合并成一条"全A 可扩展流水线"改造:**全A 只 K线 → 形态+RS 筛候选 → 候选采护栏+新闻+LLM → 达标池 + 完整合议**。

## 预期效果(验收锚点)
- 全A 一轮:LLM 调用 ≤ 候选数(几十),而非 5539;
- 全A 采集请求量:~5539 次 K线 + O(候选) 次基本面/公告/新闻,而非 ~1.6 万+;
- 时间从"数十分钟且不可扩"降到"可全A 常态盘后跑"。
