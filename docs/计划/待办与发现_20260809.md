## 2. 🔴 store 读写日期不对称 bug(已咬到,须修)
**现象**:`load_kline(code)` → `store.get_raw(kind, code, date="latest")`,`"latest"` 解析为 `data/raw/` 下**最新日期目录**;但若该最新目录**只有部分 kind**(如 2026-08-09 只有 board_kline/index_kline、无 kline),`load_kline` 就在空目录里找不到 kline 而报"历史不足/无数据",**不会回退到有数据的前一日**。
**触发**:本地跑 S01 全A 选股时,2026-08-09(周日,某次真跑抓了 board/index)成了 latest,5206 只全A raw kline 在 2026-08-08 却读不到 → 5493 只误判"历史不足"、入选 0。挪走 2026-08-09 空目录后恢复(有效 5124、入选 4)。
**根因**:写用 `active_date`、读用 `"latest"`,两者口径不一致;且 `"latest"` 不按 kind 判断该日是否真有该数据。
**影响面**:不止 S01——**每日闭环跨交易日**也会中招(新交易日目录先被某步建出、kline 未采时,`load_kline` 读空目录失败);之前"远端数据仓库方案"§一已预警过此不对称。
**修法(择一,待排期)**:
- (a) `get_raw` 的 `"latest"` 改为"含该 kind 的最新日期"(按 kind 找最近有数据的日期);或
- (b) `load_kline` 等读取尊重 `active_date`(编排设了就用它,而非盲取 latest);或
- (c) 至少:latest 目录缺该 kind 时**回退前一日**。
建议 (a)+(b) 组合。**这是数据层健壮性红线,优先级高于新功能**。

## 3. 远端 CPU 飙高事件(2026-08-09)
**现象**:远端服务器 CPU 非常高、SSH 连不上,需重启。
**最可能原因(按嫌疑排序,待重启后 `journalctl`/`top` 证实)**:
1. **`stock-fetch.timer` 每 30min 对全A做重活**:`sync_master` 若走 spot 增量 → `update_master_from_spot` 要**读+concat+写 ~5206 个 parquet 主档文件**,每 30min 一轮,持续高 CPU/IO;若误判覆盖不足触发 **baostock 全量回填(5539 只)**则更重。
2. **主窗 `/pull` 大请求压测**(1000 只/批):服务端要读 1000 个 parquet + 序列化数百 MB JSON,我连发数批(已 kill),可能贡献了 CPU/内存尖峰。**如实记:我的压测是诱因之一。**
**即时缓解(已写进重启命令)**:**停用 `stock-fetch.timer`**(掐掉持续来源),远端先纯展示;`/pull` 不再发大请求(改小批,见待办)。
**根治(待排期)**:
- 采集定时器降频 + 增量只 append 当日一根(避免全档重写);spot 失败别退全量回填。
- `/pull` 加**服务端分页 / 客户端小批(≤200)**,杜绝单请求大 payload。
- 上远端跑采集前,先压测评估资源;或采集与展示分进程/限 CPU(systemd `CPUQuota=`)。
