# 展示端与数据同步（远端只读展示 + DB + 上传/收录接口 + 传输安全）

> 状态：**待审** · 日期：2026-08-07 · 分支：`feat/display-sync`（拟）
> 一句话：把 web 展示端搬到远端服务器、用数据库存展示数据，由本地端把每日分析产物**签名上传**、展示端**验签+验时效**后收录并只读展示——本地算、远端看，两端分离。

## 一、原始需求（负责人原话，忠实转述）

负责人提出（2026-08，口头需求，尚未实现）：

- 原话 1：想在**远端服务器**拉起一个**展示端**——只读数据、拉起页面、实现 web 展示。
- 原话 2：展示端需要一个**数据库**来存储要展示的数据；目前本地是文件存储，转 SQL 数据库"还在计划开发中"。
- 原话 3：展示端要**开放一个接口**，收录本地端上传的数据，并**验证时效**、**更新数据**。
- 原话 4：本地端要有**上传数据**的功能。
- 原话 5：注意数据传输**安全**问题；数据要有来源的**"钢印"**——即来源可信标记、防篡改防冒充。
- 原话 6：先**分析需求、找不足、捋清**，再写需求文档，**不是马上实现**。

> 本文只做需求分析与方案设计，**不含任何功能代码**。落地待负责人审阅第八节「待澄清清单」拍板后再排期。

## 二、要实现哪些功能（可验收的功能点）

分五组。每条给验收标准（可判断"做没做完"）。

### A. 展示端数据库（DB）
- [ ] A1：设计展示端 DB schema，按 **日期 × code** 组织，覆盖现有全部展示所需数据：个股中心记录（`record`）、按票视图（`chart`/`news_ai`/`sentiment`）、池级视图（`panel`/`screen`）。（验收：给定任一 `(date, code)`，能从 DB 取回与现文件后端**语义等价**的对象；给定 `date` 能取回 `panel`/`screen`。）
- [ ] A2：给 `tools/store` 增加一个 **DB 后端实现**，与现文件后端**同签名**（`get_record`/`put_record`/`get_view`/`put_view`/`get_code_view`/`put_code_view`/`iter_records`/`list_dates`），后端由配置切换。（验收：`web/data_access.py` 与 `web/app.py` **零改动**即可指向 DB 后端跑通四页。）
- [ ] A3：DB 支持"按日期留历史快照"，与现 `data/analysis/<日期>/` 分区语义一致，且为回测 BT.2 的历史时点快照打基础。（验收：写入两天数据后，`list_dates()` 返回两天，可分别读取。）

### B. 展示端收录接口（ingest API）
- [ ] B1：展示端新增 HTTP `POST` ingest 接口，接收本地端上传的"某日产物包"。（验收：本地端 POST 一个合法包，接口返回 2xx 且数据落 DB。）
- [ ] B2：接口做**鉴权**（API Key / Bearer Token，密钥走环境变量、不入库、不进 git）。（验收：无 token / 错 token 返回 401；正确 token 放行。）
- [ ] B3：接口做**验签**（数据来源"钢印"，见第五节）。（验收：篡改载荷任一字节后签名不匹配 → 拒绝 400/403；未篡改放行。）
- [ ] B4：接口做**时效验证**——校验产物日期 / 生成时间在允许窗口内，拒绝过期或"未来"日期数据。（验收：上传日期早于窗口下界或晚于服务器当天 → 拒绝并给明确错误码；窗口内放行。）
- [ ] B5：接口做**幂等 upsert**——同 `(date, code/view)` 重复上传按策略覆盖或拒绝旧版本，不产生重复/半截数据。（验收：同一包上传两次，DB 结果一致、无重复行；旧 `generated_at` 覆盖新数据的请求被拒。）
- [ ] B6：接口有**审计记录**——每次 ingest 落一条日志（时间、来源标识、日期、条数、验签结果、处理结果）。（验收：一次成功 + 一次失败上传后，审计表/日志各有一条对应记录。）

### C. 展示端 web 读 DB
- [ ] C1：展示端 web 通过 store DB 后端读数据，行为与现文件版一致（四页 + 历史日期下拉 + 新闻详情）。（验收：同一份数据下，DB 版页面与文件版页面渲染结果一致。）
- [ ] C2：保留展示层"**只读、不算、不触网**"约束（架构 §9.3 / §10 体检结论）。（验收：展示端代码不 `import` 任何 analysis 分析器、无外网请求。）

### D. 本地端上传工具
- [ ] D1：本地端新增上传工具（CLI），打包指定日期的分析产物（record + 各视图）。（验收：`python -m tools.sync.upload --date YYYY-MM-DD` 生成一个包含该日全部展示数据的载荷。）
- [ ] D2：上传工具对载荷**签名**（钢印）并携带**时间戳 + nonce**，`POST` 到展示端 ingest 接口。（验收：展示端能验签通过并入库；重复 nonce 被展示端拒绝。）
- [ ] D3：上传工具支持**失败重试 / 断点续传**（分片或分票上传，部分失败可重发失败项）。（验收：人为让第 3 票失败，重跑只补第 3 票，不重传已成功项。）
- [ ] D4：上传结果有本地回执/日志（成功票数、失败票数、服务端返回）。（验收：跑一次上传后本地有一份可读回执。）

### E. 传输安全（贯穿 B/D，详见第五节）
- [ ] E1：传输走 **TLS/HTTPS**。（验收：ingest 接口只在 HTTPS 下可用，HTTP 明文被拒/重定向。）
- [ ] E2：**来源钢印**——载荷经共享密钥 HMAC-SHA256（或非对称）签名，展示端验签确认"来自授权本地端且未被篡改"。（验收：见 B3。）
- [ ] E3：**防重放**——时间戳 + nonce，展示端拒绝过期时间戳与重复 nonce。（验收：重放同一请求被拒。）
- [ ] E4：密钥全部走**环境变量**、不入库、不进 git（沿用现有 `LLM_API_KEY` 等"禁硬编、禁入库"约定，见 `tools/config/settings.py`）。（验收：全仓 grep 无明文密钥；缺环境变量时启动即报错。）

## 三、架构方向：本地 push → 展示端 ingest（不是 pull）

**结论：采用 push（本地端主动上传），不采用 pull（展示端主动拉取）。** 理由：

1. **数据源在本地、且不宜公网直连**。采集/分析（唯一外部 I/O 边界 + LLM 调用）都在本地端跑，本地端是可信数据生产者。若用 pull，展示端要能反向访问本地端的数据目录或开一个本地端服务对公网暴露，等于把"生产环境"挂到公网，攻击面更大。push 让本地端只出站、不入站，本地端无需开任何公网端口。
2. **时序天然由本地端触发**。产物是本地端 `run.py` 每轮跑完才产生的；"跑完即推"比"展示端定时来问有没有新数据"更简单、更实时，也免去 pull 的轮询与"数据是否就绪"竞态。
3. **钢印语义更顺**。push 模式下，"谁生产谁签名"，展示端只需持有验签公钥/共享密钥做被动校验，职责清晰。
4. **展示端保持纯被动**。展示端只做两件事：被动收录（ingest）+ 只读展示，不主动外联，符合架构对展示层"只读、不触网"的定位。

两端分离后的数据流：

```
本地端（采集+分析+组装，唯一外部 I/O）
  run.py → data/analysis/<日期>/{code}.json + 视图(chart/news_ai/panel/screen…)
        │
        ▼  tools/sync/upload.py：打包某日产物 → 签名(钢印)+时间戳+nonce → HTTPS POST
        │
        ▼
展示端（远端服务器，纯被动）
  ingest API：鉴权 → 验签 → 验时效 → 幂等 upsert → 写 DB（store DB 后端）
        │
        ▼
  web(FastAPI 四页) ── 经 store DB 后端只读 DB ──► 浏览器
```

## 四、实现计划

### 4.1 分期 / 步骤

分四期，**每期可独立审阅、独立验收**，前一期是后一期的地基：

- **P1 — store DB 后端 + 展示端只读 DB**（地基，风险最低）
  给 `tools/store` 加一个 DB 后端实现（与文件后端同签名），后端由配置切换；展示端 web 指向 DB 后端跑通四页。此期**不涉及网络与安全**，纯本地可验证（本地起 DB、写入、web 读）。这是"换 DB 实现、上层零改动"承诺的兑现（见 `tools/store/repo.py` 文件头 + 架构 §5 演进建议）。
- **P2 — ingest API + 钢印 + 时效**（展示端收录能力）
  展示端新增 ingest 接口，实现鉴权 + 验签 + 时效验证 + 幂等 upsert + 审计。此期先用测试客户端灌数据验证，不依赖本地端真实上传。
- **P3 — 本地端上传工具**（打通端到端）
  本地端 `tools/sync/upload.py`：打包 + 签名 + POST + 重试/续传 + 回执。跑通"本地跑完 → 一键上传 → 远端可见"。
- **P4 — 部署 / 运维**（上线）
  展示端部署（HTTPS 证书、反向代理、环境变量注入密钥、DB 持久化与备份、ingest 审计日志留存、数据保留天数清理策略）。补 `docs/参考/部署说明.md`。

### 4.3 接口 / 契约（若涉及）

**契约不变原则**：展示数据的 schema 仍以 `tools/contracts/` 的中心记录契约为唯一真源。DB 后端只是**换存储介质**，不改记录结构；ingest 只是**换传输方式**，入库前仍应过 `validate_record`。这样展示端读到的对象与本地端文件版**逐字段等价**。

拟定新增签名（示意，非最终）：

```
# store 后端接口（文件后端 / DB 后端都实现这一组，上层零感知）
get_record(code, date="latest") -> dict
put_record(rec, date=None) -> str
get_view(name, date="latest"); put_view(name, obj, date=None)
get_code_view(name, code, date="latest"); put_code_view(name, code, obj, date=None)
iter_records(date="latest"); list_dates(root="analysis")

# 签名/验签（钢印）
sign_payload(payload: bytes, key: str, ts: str, nonce: str) -> str   # HMAC-SHA256
verify_payload(payload: bytes, sig: str, key: str, ts: str, nonce: str, window_s: int) -> bool

# ingest 请求信封（HTTPS POST body）
{
  "meta": {"date": "YYYY-MM-DD", "generated_at": <iso>, "source": "<本地端标识>",
            "ts": <iso>, "nonce": "<uuid>", "sig": "<hmac>"},
  "records": {<code>: <record dict>, ...},
  "views":   {"panel": {...}, "screen": {...}},
  "code_views": {"chart": {<code>: {...}}, "news_ai": {<code>: [...]}, ...}
}
```

拟定 DB schema（示意，选型见第八节 Q1）：

```
snapshot(date PK-part, generated_at, source, ingested_at)          -- 每日一批
record(date, code, json, PRIMARY KEY(date, code))                  -- 中心记录
view(date, name, json, PRIMARY KEY(date, name))                    -- panel/screen
code_view(date, name, code, json, PRIMARY KEY(date, name, code))   -- chart/news_ai/sentiment
ingest_audit(id, at, source, date, rows, verify_ok, result, msg)   -- 审计
seen_nonce(nonce PK, at)                                           -- 防重放
```

> 记录/视图直接整体存 JSON 列（Postgres `jsonb` / SQLite `text`），换 DB 不改字段拆分，保"零改动"最省。需要横向查询（如按趋势得分排序）时再对热点字段建生成列/索引。

## 五、安全 / 钢印设计（重点）

四道关，逐层收窄攻击面：

1. **传输层 TLS/HTTPS（E1）**：ingest 只在 HTTPS 暴露，杜绝明文窃听与中间人；证书 + 反代（如 nginx/caddy）在 P4 落地。
2. **接口鉴权（B2/E4）**：请求头带 API Key / Bearer Token，服务端比对环境变量里的令牌；错/缺一律 401。令牌只证明"调用方持有令牌"，**不**证明"数据未被篡改"——所以还需第 3 关。
3. **数据来源钢印 = 载荷签名（E2）**：
   - 本地端用**共享密钥**对"规范化后的载荷字节 + 时间戳 + nonce"做 **HMAC-SHA256**，签名随请求发出。
   - 展示端用同一密钥重算并比对——通过即证明"来自持有密钥的授权本地端 **且** 一字节未改"。
   - **对称（HMAC）vs 非对称（Ed25519/RSA 签名）** 的取舍见第八节 Q6：单一本地端 → 对称最简；未来多方上传或不愿在展示端存签名密钥 → 非对称（展示端只存公钥，泄露公钥无害）。**建议对称起步、接口设计上给非对称留位（`meta.sig_alg` 字段）。**
4. **防重放（E3）**：`meta.ts` 时间戳 + `meta.nonce` 一次性随机数。展示端拒绝 `|now-ts| > 窗口`（如 300s）的请求，并记 `seen_nonce`、拒绝重复 nonce。

**时效验证（B4，与"钢印"是两件事，别混）**：钢印管"数据真不真"，时效管"数据新不新"。展示端校验 `meta.date` / `meta.generated_at`：
- 拒绝 `date` 晚于服务器当天（未来数据）；
- 拒绝 `date` 早于允许窗口下界（如超过保留天数的老数据）；
- 幂等：同 `date` 已有数据时，按 `generated_at` 决定覆盖（新数据覆盖旧）或拒绝（旧数据不许覆盖新）。

**密钥管理（E4）**：签名密钥、鉴权令牌全部走环境变量（沿用 `tools/config/settings.py` 里 `LLM_*` 的"禁硬编 url/key、禁入库"既有约定）；密钥轮换策略见第八节 Q7。

## 六、找到的不足与风险（Top 3 + 其余）

**最大 3 个不足 / 风险：**

1. **DB 迁移是完全空白地，没人在写、也没设计**。全 git 无任何 DB/SQL 代码；远端合作者分支 `feat/stock-pool-management` 做的是**票池管理界面**（增删股票 UI），与 DB 无关。`tools/store/repo.py` 只在文件头**口头承诺**"规模化后换 DuckDB/SQLite、上层零改动"，但**从未验证过这个抽象真的成立**——现文件后端把"按日期分区"和"latest 解析"逻辑直接写死在函数里，抽后端时可能发现抽象泄漏，"零改动"承诺有落空风险。**这是本需求最大的地基不确定性**，建议 P1 先做一个最小 DB 后端 + 等价回归测试来证伪/证实。
2. **公网暴露 ingest 接口 = 引入项目第一个"入站"攻击面**。此前整个系统只有采集器"出站"访问外部数据源，展示层被明确约束"不触网"。开 ingest 后，展示端要长期在公网收 POST，需求里的"安全"若只做到 token 就远不够——必须 TLS + 验签 + 防重放 + 限流 + 审计齐全，否则令牌一旦泄露，攻击者可灌入伪造分析数据污染展示（投资相关数据被污染后果不小）。**安全不是附加项，是 P2 的核心验收项**。
3. **展示端与本地端 store 的 DB 关系未定，易埋"两套 schema 打架"的坑**。`repo.py` 文件头说的是给**本地端** store 换 DuckDB/SQLite 作查询层（文件仍是真相源）；而本需求要的是**展示端**独立 DB（很可能 Postgres/SQLite，且要能被 web 并发只读、可能公网）。这两个 DB 目标、部署位置、并发模型都不同。若不明确"两者是同一套后端抽象的两个实例，还是各写各的"，未来极易出现 schema 双头维护、契约漂移。**建议：统一走 store 后端抽象，展示端 = store 的一个 DB 后端实例，schema 真源仍锚定 `tools/contracts/`。**

**其余风险：**
- **无历史快照工程与本需求耦合**：BT.2 选股回测也卡在"只存最新一份记录"。展示端 DB 天然按日期存历史，正好可与 BT.2 的历史快照需求合流，别各修各的。
- **合作者分支协调**：票池管理若改动 `web/` 或 config 票池结构，与本需求的 web/config 改动可能冲突，需在 P1 前对齐改动边界（谁动 `web/app.py`、谁动 `settings.py`）。
- **上传原子性**：一批数据部分入库后中断，展示端可能显示"半天"数据。需按 `snapshot` 事务提交或加"就绪标记"，web 只读已就绪的 date。

## 八、待澄清清单（请负责人拍板，编号对应问题台账）

> 这些开口不定死，P1 无法开工或会返工。逐条给"建议默认值"，负责人可只改需要改的。

1. **展示端 DB 选型？** SQLite（单文件、零运维、够小规模）／ Postgres（并发/公网/多连接更稳、可 `jsonb`）／ DuckDB（分析型、并发写弱）。**建议：SQLite 起步（P1 快、够单机只读展示），接口按后端抽象写，规模/并发上来无痛换 Postgres。**
2. **展示端要公网多用户访问吗？要登录鉴权吗？** 内网自用 vs 公网。**建议：先内网/受限访问、只读页面不做用户登录；ingest 接口独立鉴权。若要公网，P4 加访问控制 + 限流。**
3. **同步是全量还是增量？多久一次？保留多少天？** **建议：按"每日一批全量 upsert"（简单、幂等好做），每轮 run 跑完推一次；保留天数默认 90 天（够看季度 + 喂 BT.2），可配。**
4. **展示端 web 直接读 DB，还是加一层缓存？** **建议：直接读（数据量小、只读），先不加缓存，慢了再说。**
5. **展示端 DB 与本地端 store 是否共用同一套后端抽象与 schema？** **建议：共用后端抽象（同签名），schema 真源锚定 `tools/contracts/`；展示端 = store 的一个 DB 后端实例。**（对应风险 3）
6. **钢印用对称（HMAC，简单）还是非对称（Ed25519/RSA，可多方、展示端不持私钥）？** **建议：对称 HMAC-SHA256 起步，`meta.sig_alg` 留位，将来多个本地端或更高安全要求时切非对称。**
7. **密钥分发与轮换怎么做？** **建议：起步手工在两端环境变量各配一份共享密钥；轮换支持"双密钥并存窗口"（新旧都验通过一段时间）平滑切换。**
8. **上传失败 / 部分失败的重试与回滚策略？展示端要不要审计日志？** **建议：本地端按票分片、失败项可重发；展示端按 `snapshot` 事务提交（要么整批可见、要么不可见），并强制记 `ingest_audit` 审计。**

补充确认项（倾向已明确，仅需负责人点头）：
- **展示端纯展示、不跑分析**（不 import 分析器、不触网）——沿用现有展示层约束。**（建议：确认为纯展示。）**
- **同步方向为 push（本地→展示端）**，理由见第三节。**（建议：确认 push。）**
- **与合作者票池管理分支不打架**：约定本需求先不动票池 UI 相关文件，只在 store/ingest/sync 三处新增；web/config 的改动在 P1 前与合作者对齐。
