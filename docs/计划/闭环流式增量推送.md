# 闭环流式增量推送（模块化·抗断点）

> 目标：把每日闭环从"全部跑完才统一 upload"改成"**每个策略/每批 record 产出就立即增量推**"，任一步失败不再导致**全天数据不推**。⚠️ 非投资建议工具的工程改造。

## 一、痛点（真实事故）
现状 `ops/launchd/pull_refresh.sh`：`采集 → screenall(各 screener 依次) → ③ 最后统一 upload 509 分片`。
- 任意前置步骤断（如 2026-08-31 夜网络卡在资金流 129/363）→ **到不了 ③ upload → 一整天数据全不推**，已跑完的策略结果全白费。

## 二、目标
1. **抗断点**：每个策略 view 跑完立即推；某策略/某数据/某网络失败，**已推的保留**、不回滚。
2. **增量可见**：远端逐策略、逐批 record 更新，不必等全链路。
3. 保持**完整性兜底**：末尾仍做一次统一 upload 补漏（幂等，不重复传已成功分片）。

## 三、现状机制（探查结论）
- **upload 层已具备增量能力**（关键，不用大改）：
  - `tools/sync/upload.py::upload_date(date, ..., only_shards=set|None)`：`only_shards` 过滤后只传指定分片（L212）。
  - CLI `--only-view 名`：只补传指定 view 分片（L253）。
  - 幂等：`receipt`（回执）记录每分片 ok/fail，非 `--force` 时跳过已 ok；`_shard_hash` 防重复。
  - 429 限流退避重试（不丢分片）、`min_interval` 节流。
  - 凭证：`settings.SYNC_INGEST_URL / SYNC_INGEST_TOKEN / SYNC_SIGNING_KEY / SYNC_SOURCE_ID / SYNC_KEY_ID`（从 env / sync.env 读）。
- **分片 key 约定**：view 分片 = `f"{VIEW_SHARD_PREFIX}{视图名}"`（`__view__:策略0合议`）；record 分片 = `code`。
- **闭环产出时序**（`tools/run.py::run_screen_all`）：
  - 步骤② screener 循环（L737+）：每个 `_safe(fn)` 产出一个策略 view 并 `put_view` 落盘 → **此刻该 view 已可推**。
  - 步骤⑤ `run_serialize(llm_subset)`（L823）后 → record 完整（含 council/财报/逐笔）→ **此刻 record 可推**。

## 四、设计

### 层1 · 策略 view 增量推（screener 循环内）
在 `run_screen_all` 的 screener 循环里，每个策略 `_safe(fn)` 产出 view 后，立即调用增量推：
```python
view = _safe(f"{label} 全A筛选", fn)
...
_push_incremental(as_of, {f"{VIEW_SHARD_PREFIX}{view_name}"})   # best-effort,失败不炸
```
- 各策略选股清单（策略0/2/4/5/S03/S04/S05/10/11）**跑完一个推一个**。

### 层2 · record 分批增量推（serialize 后）
`run_serialize(llm_subset)` 后，按批（每 `STREAM_RECORD_BATCH=50` 只）推 record 分片：
```python
run_serialize(llm_subset, as_of)
for batch in _chunks(llm_subset, STREAM_RECORD_BATCH):
    _push_incremental(as_of, set(batch))   # record 分片 key = code
```
- 某批网络失败 → 只该批待补，其余已推。

### 兜底 · 末尾统一 upload（保留）
`pull_refresh.sh ③` 的 `python -m tools.sync.upload --date` **保留不动**：作为"补漏"最后一次全量（幂等：已成功分片跳过，只补增量推时失败/遗漏的）。

### 新增 helper（`tools/run.py`）
```python
def _push_incremental(date: str, shard_keys: set[str]) -> None:
    """best-effort 增量推指定分片(view 名前缀 or record code)。
    凭证缺失(如直接 screenall 未加载 sync.env) → 跳过降级,不炸闭环;
    末尾统一 upload 兜底补漏。网络/429 由 upload_date 内部退避处理。"""
    if not _stream_push_enabled():        # settings.STREAM_PUSH 开关(默认 True)
        return
    from tools.config import settings
    if not (settings.SYNC_INGEST_URL and settings.SYNC_INGEST_TOKEN and settings.SYNC_SIGNING_KEY):
        return                            # 无凭证 → 跳过(直接 screenall 场景)
    try:
        from tools.sync import upload
        upload.upload_date(date, url=..., token=..., ..., only_shards=shard_keys,
                           receipt_path=_receipt_dir()/f"{date}.json")
    except Exception as e:
        logger.warning("增量推 %s 失败(降级,末尾兜底):%s", shard_keys, e)
```

### 开关（可回滚）
`tools/config/settings.py`：`STREAM_PUSH = os.getenv("STREAM_PUSH","true")...`（默认开）。关掉 → 完全回退旧的"末尾统一 upload"行为，零风险回滚。

## 五、查缺补漏（写计划过程中识别的坑）
1. **幂等/回执一致**：增量推与末尾兜底**必须用同一 `receipt_path`**（`_receipt_dir()/f"{date}.json"`），否则兜底会重传已增量推的分片。→ helper 与 pull_refresh ③ 都走默认 receipt 路径,天然一致。
2. **build_shards 开销**：`upload_date` 内部 `build_shards(payload=当日全量)` 再 filter。增量推每策略调一次 → 重复读磁盘 build。→ 可接受（读 JSON 不慢，一天 ~10 策略）；若慢，后续可让 `upload_date` 接受预构造 payload。**本轮先接受，注释标注**。
3. **view 推时 record 未就绪**：screener 阶段 record 还没 serialize（在步骤⑤）。`only_shards={__view__:X}` 只推 view 分片，build_shards 读到的 record 是上一轮 stale/或无 → 被 filter 掉，不误推。✓ 无副作用。
4. **失败隔离**：`_push_incremental` 整体 try/except + best-effort；单策略推失败只 warning，不中断 screener 循环、不中断闭环。
5. **凭证缺失场景**：`python -m tools.run screenall`（不经 pull_refresh、无 sync.env）→ helper 检测无凭证跳过，闭环照常，只是不增量推（要推另跑 upload）。
6. **429 限流叠加**：增量推 + 末尾兜底都可能撞 120/60s 限流。upload_date 已有退避+节流；增量推分散在时间轴上（各策略间隔跑）反而**比末尾一次性传 509 分片更不容易撞限流**（正收益）。
7. **run_two_stage 对称**：`run_two_stage` 也是 serialize 闭环，同样加 record 批推（与 run_screen_all 对称，避免另一路径遗漏）。
8. **pool_ack 不动**：方案2 的 `--pool-ack` 仍只在末尾兜底那次带（增量推不带，避免中途误清 pending）。

## 六、层3（演进方向·本轮不做）
"数据模块拉完就触发依赖它的策略"的**依赖图 + 调度器**（策略1/2/3 数据就绪即并行跑）。工作量大（要建 数据→策略 依赖声明 + 就绪触发 + 并行编排），而层1+2 已拿到"增量推+抗断点"约 80% 价值。留作后续；本轮聚焦层1+2。

## 七、测试
`tests/test_screenall.py`（复用 hermetic stub）加：
1. **每策略产 view 后调了增量推**：mock `_push_incremental`（或 upload），断言每个 screener 后被调用一次、参数是该 view 分片 key。
2. **失败隔离**：`_push_incremental` 抛错 → 闭环不崩、后续策略照跑、末尾照常。
3. **凭证缺失跳过**：无 SYNC_* 时 `_push_incremental` 直接 return，不调 upload、不炸。
4. **开关**：`STREAM_PUSH=false` → 完全不增量推（回退旧行为）。
5. record 批推：serialize 后按 batch 调增量推、批大小正确。

## 八、风险与回滚
- 风险低：增量推是**新增的 best-effort 加速层**，末尾统一 upload 兜底保证完整性；出任何问题 `STREAM_PUSH=false` 一键回退旧行为。
- 防未来函数：不涉及（纯推送时序改造，不碰选股/预测逻辑）。

## 九、落地步骤

3. `tests/test_screenall.py` 加 5 类测试。
