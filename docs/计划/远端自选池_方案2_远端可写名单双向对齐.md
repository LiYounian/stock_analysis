# 远端自选池 · 方案2 · 远端可写名单 + 本地远端双向对齐

> 一句话定位:让**远端展示页也能加/删自选票**,并让本地与远端的自选**名单**双向对齐;但**采集与产物重建仍全部回本地做**,远端只登记名单、不采集不重建——从而绕开"远端 reset 抹改动"和"远端无 raw 致 panel 收缩"两个坑。
>
> 日期:2026-08-26 · 状态:方案稿(待用户拍板)· 定位:中等改动

---

## 〇、与方案1 / 方案3 的关系

| 方案 | 谁能加自选 | 谁采集/算 | 实时能力 | 改动量 |
|---|---|---|---|---|
| **方案1(统筹进行中)** | 只本地 | 本地 | 本地对自选池盘中盯盘;远端纯展示不动 | 最小 |
| **方案2(本文)** | **本地 + 远端** | **仍只本地** | 不涉及(实时仍看方案1) | 中 |
| **方案3(完整双向节点)** | 本地 + 远端 | 本地 + **远端自采** | 远端也实时+盯盘 | 大 |

- **方案1 做了什么**:在本地机上对自选池做盘中实时监控/盯盘(复用现有采集与 `tools.sync.pull` 增量拉取链路),远端服务器保持"纯展示"现状——不改远端写入路径。方案1 解决的是"我(本地)能实时看自选",没解决"人在外面、本地没开机时,想在远端网页上顺手加一只票"。
- **方案2 在方案1 之上的增量**:把"加自选票"这个**写操作**也开放给远端网页,并保证两端名单最终一致。代价是引入一条"远端名单 → 本地"的回传半环 + 冲突合并策略。**实时能力不在方案2 范围**,仍由方案1 承担。
- **方案3 是方案2 的超集**:见 `远端自选池_方案3_远端完整双向节点.md`。方案2 可视为方案3 的"只对齐名单、不搬采集"最小前置。

## 一、现状与痛点(基于真实代码)

### 1.1 当前架构(证据)

- **本地(Mac)= 生产**:`ops/launchd/pull_refresh.sh` 盘后跑 `screenall`/`sepa`/记分卡 → `tools.sync.upload` 签名上传。
- **远端(39.105.83.174)= 展示**:`ops/remote_update.py` 每 5min 一轮 `git fetch` + `merge --ff-only`,数据经 `tools.sync.ingest`(8802)签名直入 DB,`web/app.py`(8801)只读展示。

### 1.2 痛点一:远端网页加自选会被 5 分钟一次的 reset 抹掉

自选名单真源是 **git 跟踪文件** `config/stock_pool.json`(`tools/config/stock_pool.py:22` `_STORE = .../config/stock_pool.json`,`add_stock`/`remove_stock` 直接回写该 JSON)。

而远端 autoupdate 的更新逻辑(`ops/remote_update.py:161-164`):

```python
rc, _ = runner(["git", "-C", cfg.repo_dir, "merge", "--ff-only", f"origin/{cfg.branch}"])
if rc != 0:
    logger.warning("ff-only 合并失败(远端分叉/本地改动),reset --hard 到 origin/%s", cfg.branch)
    runner(["git", "-C", cfg.repo_dir, "reset", "--hard", f"origin/{cfg.branch}"])
```

只要远端本地对 `config/stock_pool.json` 有未提交改动,下一轮(≤5min)`git merge --ff-only` 因工作区脏而失败 → 触发 `reset --hard origin/main` → **远端刚加的自选被无声抹掉**。这是设计使然:展示端被定位为"跟随 origin、不留本地改动"。

### 1.3 痛点二:远端就算加成了,重建也会把 panel 打瘪

`web/app.py:192` 的 `POST /api/pool` 委托 `pool_service.add_and_collect`(`tools/pool_service.py:83`):

```
add_stock() → collect_one()  # 联网采集该票 K线/基本面/公告/资金流
            → rebuild_artifacts()  # 读 raw 缓存,重建 serialize/chart/panel/screen
```

- `collect_one` 需联网采集(远端在境内,东财/新浪可达性大概率好于本机,但**未在真机验证**——见 §六 待确认)。
- `rebuild_artifacts`(`pool_service.py:27`)对**全池** codes 跑 `serialize_all`/`write_charts`/`write_panel`,再 `repo.put_view("screen", ...)`。而 `put_view` 是**整表替换**(`backend_db.put_view`),不是增量 merge。
- 远端**不积累 raw 缓存**(远端只被动收 upload 的 analysis 产物,`data/master/`、`data/raw/` 不在远端生产)。故远端跑 `rebuild_artifacts` 时,`write_panel(codes)` 只能就手头零星数据重算 → **整张 panel 视图被一份收缩后的结果覆盖**,展示页面板塌陷。

**结论**:直接让远端复用现有 `/api/pool` 写链路,两条路都堵死。方案2 的核心就是"**远端只记名单增量,采集与重建一律回本地**"。

## 二、目标与非目标

**目标**
1. 远端展示页可提交"加自选/删自选"请求,且该请求不被 autoupdate 的 reset 抹掉。
2. 本地与远端的**自选名单**最终一致(双向对齐)。
3. 新增票的采集 + 全部产物重建 + 上传,仍由**本地**完成(避免 panel 收缩),远端拿到本地回推的完整产物后正常展示。

**非目标(明确划走)**
- 不让远端采集 K线/基本面/资金流(那是方案3)。
- 不让远端跑 `rebuild_artifacts` / 任何分析器(远端保持"只读不算不触网",与 `ingest.py` 头部注释一致)。
- 不做盘中实时/盯盘(方案1 负责)。
- 不改动 `stock_pool.py` 的读接口签名(上层 run/analysis/collectors/web 不受影响)。

## 三、设计

方案2 = 三段:①**自选名单挪出 git-reset 的火线**;②**远端→本地名单回传通道**;③**冲突/合并策略**;④**本地侧消化(采集+重建+上传)**。

### 3.1 自选名单持久化改造(把名单挪出 reset 火线)

要点:远端对名单的改动必须存在**一个不会被 `reset --hard` 抹掉**的位置。给两个选项比较。

#### 选项 A:名单额外落 DB 表(远端权威副本存 DB,JSON 仍是本地真源)

- 远端加票时**不写 `config/stock_pool.json`**,而写一张新 DB 表 `pool_pending`(远端 DB 不受 git reset 影响)。
- 结构建议:`pool_pending(code, name, industry, sector, market, op ENUM(add/remove), source='remote', requested_at, status ENUM(pending/consumed))`。
- 本地定期(或盘后闭环开头)经既有 `/pull` 通道**拉走 pending 名单**,消化后回推产物,并把该行标记 consumed(或本地上传时带回执覆盖)。
- 优点:与现有"DB 不随 git、只随 upload/ingest"的数据面一致;远端网页改动天然持久;审计可复用 `ingest.py` 的审计表口径。
- 缺点:要新增一张表 + 一个只读拉取路由(`/pull?kind=pool_pending`);名单"真源"暂时二元(本地 JSON + 远端 pending),需靠 §3.3 合并收敛。

#### 选项 B:把 `config/stock_pool.json` 移出 git 跟踪 + autoupdate 排除

- 让名单文件不再被 `reset --hard` 波及:`git rm --cached config/stock_pool.json` + `.gitignore`,或在 remote_update 里对该文件做 `git stash`/`checkout --ours` 保护。
- 优点:改动面看似小,不新增表。
- 缺点(**不推荐**):①名单脱离 git 后,本地/远端各持一份文件、无版本历史,冲突更难追;②`stock_pool.py:99` `_load()` 缺文件会用 `_SEED` 重新初始化(34 只种子),远端首次缺文件会**悄悄回退到种子池**,危险;③破坏"展示端跟随 origin、无本地改动"的干净模型,后续别的跟踪文件也可能被同类需求侵蚀;④remote_update 里加针对单文件的特例分支,是给一个通用编排塞脏逻辑,可维护性差。

> **推荐:选项 A**。DB 表天然不随 git reset,与现有数据面模型自洽,冲突可控、可审计。选项 B 的"名单脱离 git"副作用(种子回退、无历史)风险高于收益。

### 3.2 远端 → 本地 名单回传通道(复用现有 /pull 半环)

**不新增端口、不新增服务**,复用 `ingest.py` 已有的 `GET /pull`(8802,同一把 HMAC 密钥)。现状 `/pull` 只支持 `kind=kline`(`ingest.py:194 PULL_KINDS = ("kline",)`),方案2 扩一个 kind:

- 远端 `ingest.py`:`PULL_KINDS += ("pool_pending",)`,新增 `_pull_pool_pending()` → 读 §3.1 的 DB 表,返回 `status=pending` 的行(**只返名单元数据,绝不返任何密钥/配置**,与现有 `/pull` 安全红线一致)。
- 本地 `tools/sync/pull.py`:现在客户端 `if kind != "kline": return 不支持`(`pull.py:174`)。扩一个分支 `kind=pool_pending` → 落到本地一个"待消化"缓冲(如 `data/sync_receipts/pool_pending.json`),供本地闭环读取。
- 鉴权/防重放/时效**完全复用**现有 `_check_pull_sig`(HMAC 签 GET 要素 + 时间戳窗口),零新增安全面。

> 为什么复用 `/pull` 而非新加端点:`/pull` 的鉴权/限流/验签/审计已完整(`ingest.py:302`),多一个 kind 是最小侵入;新加端点要重做一遍这套门禁,得不偿失。

### 3.3 冲突 / 合并策略(谁权威、两端都改怎么合)

名单是**集合语义**,冲突比行内容易收敛。采用 **"两端并集 + 操作日志裁决删除"**:

- **加(add)**:并集。任一端 add 的票进入最终名单(幂等,重复 add 无副作用,`add_stock` 对重复码抛 ValueError,本地消化时 try/except 跳过即可)。
- **删(remove)**:以**操作时间戳**裁决。远端 pending 里 `op=remove` 且 `requested_at` 晚于本地该票最近一次 add → 执行删除;否则忽略(防"本地刚加、远端旧删记录误删")。
- **权威归属**:消化后,**本地 `config/stock_pool.json` 恢复为唯一真源**(经本地上传→远端 DB 展示,远端 pending 表清空/标记 consumed)。即"远端 pending 是**提案队列**,本地是**裁决者与真源**"。这样避免双写真源。
- **幂等键**:pending 行以 `(code, market, op, requested_at)` 去重;本地消化后写回执,重复拉取不重复执行。

### 3.4 本地侧消化(复用现有 pool_service + upload 链路)

在本地盘后闭环(`ops/launchd/pull_refresh.sh`)最前面(或独立 launchd 任务)加一步"消化远端名单提案":

```
① python -m tools.sync.pull --kind pool_pending      # 拉远端待办名单到本地缓冲
② 对每条 add:  pool_service.add_and_collect(code,...) # 复用!联网采集 + 全池重建(本地有 raw,不塌)
   对每条 remove:pool_service.remove_and_cleanup(code) # 复用!
③ python -m tools.sync.upload --date <today>          # 复用!把重建后的完整产物 + 新 panel 推回远端
④ 回执:标记远端 pending 行 consumed(经一条轻量写路由,或下轮 upload 附带已消化清单)
```

- **关键**:采集与 `rebuild_artifacts` 发生在**本地**(本地有 `data/master/`+`data/raw/`,panel 不会收缩),远端只是在下一次 ingest 收到完整 panel 后刷新展示。§1.3 的坑被绕开。
- 时延:远端加票 → 本地下次闭环消化(默认盘后一次)。**不是实时**。若要"加完几分钟就采",需给本地加一个更频繁的轮询 launchd(代价:本地需较常开机——与方案1"本地在盘中开着盯盘"可共用一个常驻进程)。

## 五、风险

1. **名单真源二元期的一致性**:远端 pending 与本地 JSON 在"消化窗口"内并存;若本地消化失败(采集报错)且未正确回执,pending 可能反复重试。缓解:消化步骤幂等 + 失败保留 pending 下轮再试 + 告警。
2. **远端加票非实时的预期管理**:用户在远端点"加",要几十分钟到盘后才见数据。必须在 UI 明说,否则体验落差。
3. **删除裁决的时钟依赖**:靠 `requested_at` 时间戳裁决删除,依赖两端时钟大致同步(阿里云/Mac 均 NTP,风险低,但需注明)。
4. **回执路由的写权限**:标记 pending consumed 是一次"远端写",要么复用 ingest 的签名写(推荐,鉴权现成),要么下轮 upload 附带——别裸开一个无鉴权写口。
5. **并发**:本地消化与远端继续入队并发;pending 表用 `status` + 事务保证"取出即锁定",避免重复消化。

## 六、需远端实机确认的推断点(诚实标注)

- **远端联网采集可达性**:方案2 采集在本地,故**方案2 本身不依赖远端能采**;但若将来想缩短时延让远端预采,需先在真机 `curl` 东财/新浪确认(境内大概率好于本机,**未实测**)。
- **远端是否已部署 ingest(8802)**:部署记录 `docs/参考/远端自动更新与自愈.md` 的"B 期"描述了 ingest 部署步骤,但**A 期实配记录明确"只跑 stock-web、未部署 ingest"**。方案2 的 `/pull pool_pending` 回传通道**依赖 ingest 在远端已起**。落地前须确认远端 ingest 实际运行状态(见 §八 findings)。
- **远端 DB 写权限**:`pool_pending` 表要能被 web 进程(stock-web,用户 admin)写。现状 web 是"只读展示",给它开一张表的写权限需评估(是否与 ingest 争 SQLite 写锁)。

## 七、工作量估算(agent 视角)

| 阶段 | 内容 | 预估 token(in+out) | agent 执行(含审阅来回) |
|---|---|---|---|
| 设计定稿 | 本文审阅 + 拍板选项 A/B | 低(~15–25K) | 0.5–1h |
| DB 表 + 入队 | schema + `enqueue_pending` + web 分流 | 中(~60–90K) | 0.5 天 |
| 回传通道 | `/pull pool_pending` + client 分支 + 回执路由 + 鉴权复用 | 中(~80–120K) | 0.5–1 天 |
| 本地消化 | 闭环加步骤 + 合并/裁决逻辑 + 幂等 | 中(~60–100K) | 0.5 天 |
| 测试 | 并集/删除裁决/幂等/鉴权单测 | 中(~50–80K) | 0.5 天 |
| 远端联调 | 真机部署 + 端到端(依赖用户上机执行) | 低(agent 侧)+ 人工 | 0.5 天(多为人工上机) |

**合计**:约 2–2.5 个 agent 工作日、token 量级"中"(全程约 30–50 万 in+out,取决于联调往返)。**大头在回传通道 + 本地消化的合并逻辑与测试**,不在采集(采集全复用)。

## 八、推荐决策路径

- **什么时候不需要方案2**:如果"人在外面临时想加票"的诉求很低频、且能接受"回本地机上加",那么**方案1(仅本地可写 + 本地盯盘)已够**,方案2 不必做。
- **什么时候值得上方案2**:当"离开本地机、只在手机/远端网页上顺手加自选"成为常态需求,且能接受"加完到盘后才见完整数据"的时延——方案2 用中等改动、零新增服务/端口、全复用采集链路,把这个诉求补上,且**不引入远端采集的运维复杂度**(那是方案3 的代价)。
- **与方案3 的取舍**:若你**只**要"远端能加名单",到方案2 即止,最划算;若你还要"远端自采 + 远端实时盯盘 + 本地不常开",才升方案3。方案2 的 DB pending 表 + 合并策略在方案3 里可原样复用,不是白做。
