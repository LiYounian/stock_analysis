# 选股产物结构化与流水线程序化 · 设计方案

> ⚠️ **非投资建议**：本项目所有内容为测试环境研究模拟，用于迭代分析思路与策略数值，不构成任何真实交易推荐。
> **本文只是方案，不改任何生产代码 / SKILL / 定时任务。** 待统筹审阅拍板后另开实现窗执行。
> 作者：结构化方案设计窗 · 2026-09-09

---

## 0. 背景与三个诉求

当前"每日选股"流水线是**纯 Agent（大模型自由写 md）+ 散代码操作**，缺固定存储格式与程序化环节，暴露三个问题（对应用户诉求 4/5/6）：

| # | 诉求 | 现状痛点 |
|---|---|---|
| 4 | **结构化选股产物** | 远端 web 展示的选股只有股票**代码**、没有名称与详情。选股结论散落在 `选股/<date>.md` 的两张表格里，靠 `tools/selection_summary.py`（409 行正则）从 md 反解析成 `selection_analysis` 视图，版式一飘就丢字段。 |
| 5 | **日期索引与命名规范** | "今日写的复盘，复盘的是昨天"——`复盘/D.md` 实际复盘的是 `选股/D-1.md` 的票，用户觉得乱。今日选股若没出（闭环未就绪）时的占位语义不统一。选股/日内/复盘/经验四类产物的"执行日 vs 归属日"没有无歧义规范。 |
| 6 | **流水线程序化** | 该固化成代码的（结构化落盘 / 格式校验 / 投送远端）仍靠 Agent 手写 md + 事后正则解析，格式不恒定、易出错。 |

**核心设计取向**：**Agent 只负责"分析研判"（不可程序化的判断），"结构化落盘 + 格式校验 + 投送"全部交给一段固定代码（Tool）**。md 保留给人读，但**权威机读源改为代码按 schema 写的 canonical JSON**。

## 1. 现状架构盘点（已核实）

### 1.1 数据层字段供给（写 schema 的底料）

- **中心记录 record**：`tools/analysis/serialize.py:285` `build_record(code, as_of) -> dict`（`SCHEMA_VERSION="1.0"`，缺块降级 None 不抛错）。顶层块：`meta / snapshot / valuation / fundamental / financial / signals / prediction / sentiment(+events) / fundflow / chip / consensus / holder / tick / lhb_veto / financing / events / provenance / council`。
  - **名称/行业/收盘价/涨跌幅都在 record 里**：`meta.name`、`meta.industry`（细分）/`meta.sector`（大类）、`snapshot.close`、`snapshot.pct_chg`。
- **名称来源链**：自选票 `config/stock_pool.json`（`stock_pool.get(code).name`）→ 全A 离线表 `config/code_name.json`（实测 5539 条，`serialize._code_name`）→ 回退代码本身。`build_record` 已把结果固化进 `meta.name`。2026-09-09 `name_fallback.json` 显示 557 票**全部命中、零回退**，覆盖良好。
- **行业来源链**：自选票 `stock_pool` 的 `industry/sector` → 全A `config/code_industry.json`（实测 5206 条，申万一级）。`record.meta.industry` 对**全A 票为 None**，展示层行业列靠 `code_industry.json` 回退；去前视历史行业在 `meta.industry_asof`。
- **策略视图**：`data/analysis/<date>/<策略名>.json` 是**池级 view**（dict，非裸数组），榜单在 `入选清单/top` 等子键。**普遍只可靠给 `code`**；`策略0合议`、`半导体多因子` 自带 `行业`，但**名称基本缺失（null）**、也没有 close/pct。→ 给榜单补名称必须 join record 或 config 映射表。

### 1.2 落盘与投送链路（已核实）

- **产物枚举口径**：`tools/sync/import_to_db.py:70` `collect_date(analysis_dir, date)` 枚举 `data/analysis/<date>/`：
  - 文件名匹配 `^\d{6}$`（6 位代码）→ `records[code]`；
  - **其余顶层 `*.json` → `views[文件名]`**；
  - 子目录 `<name>/<code>.json` → `code_views[name][code]`。
- **投送**：`tools/sync/upload.py` `upload_date()` 把 payload 切分片（每票一片 + **每个池级 view 独立成片** `__view__:<name>`），逐片签名 + HTTPS POST 到远端 ingest，带**指数退避重试 / 429 限流退避 / 断点续传（回执 `data/sync_receipts/<date>.json`）/ NaN 清洗**。
- **已有的"报告容器视图"先例**：`tools/sync/publish_report.py` 把 `data/reports/选股分析/*.md` 装进单个容器 view `选股分析报告 = {"reports": {name:{name,title,date,md}}}`，随日期上传、远端 web 读该 view 展示。**这就是"新增一个 view → 免改传输层即可上远端"的现成范式。**
- **已有的 md 反解析**：`tools/selection_summary.py` `build_selection_view(date)` 从 `选股/复盘 md` 抽 `selection_analysis` 视图（排序表 + 记分表 + 方向 + 经验标题），`collect_date` 在无同名 json 时注入。`enrich_view_cross_refs()` 已实现"D 选股 ↔ D+1 复盘"按 code 交叉引用（复盘结果三态：待复盘 / 命中 / 未命中）。**这是本次要"翻面"的对象**——从"md→正则解析"翻成"代码→canonical JSON（权威）→（可选）渲染 md"。

### 1.3 生成方与日期语义（已核实）

- 生成 SKILL：`~/.claude/scheduled-tasks/daily-stock-selection/SKILL.md`。**机读锚点硬要求**：md 第一行 `<!-- PICKS: 代码1,代码2,... -->`（跳过时 `PICKS: none`），是 `intraday_snapshot.parse_pick_codes` 识别"昨日选股"的权威源。
- 三个定时任务（`docs/每日分析/README.md`）：
  | 任务 | 时间 | 产出 | 归属 |
  |---|---|---|---|
  | daily-stock-selection | 18:36 | `选股/D.md` | 选 D 日票、预测 D+1 |
  | daily-stock-intraday-check | 10:33 | `选股/日内_D.md` + `复盘/D.md`（盘中核实节） | 跟踪 **D-1** 选票 |
  | daily-stock-eod-review | 15:10 | `复盘/D.md`（盘尾复盘节）+ `经验沉淀/vD.md` | 复盘 **D-1** 选票 |
- **日期语义（`每日选股分析机制.md` §3 已明确）**：某交易日 T 的"选股+预测"在 **T 日收盘后**做（对 T+1）；其"盘中核实/盘尾复盘"在 **T+1** 做。所以 `复盘/D.md` 复盘的是 `选股/D-1.md` 的票——**这不是 bug，是流程内禀**（今天只能复盘昨天选的票）。用户的"乱"来自**命名没显式声明归属日**，而非流程错。

## 2. 诉求 4：结构化选股 JSON schema

### 2.1 设计原则

1. **受控枚举**：表态 / 方向 / 情绪质量等用**固定枚举**，保证远端表格整齐、可排序、可校验，杜绝自由文本飘。
2. **客观字段由代码回填、Agent 不手打**：名称 / 行业 / 收盘价 / 涨跌幅 / 命中策略分值，一律代码从 record + 策略视图 join，**Agent 只提供研判字段**（表态 / 方向 / 理由 / 风险 / 盯点）。这直接根治"远端只有代码没名称""手打错价"。
3. **防未来函数自证**：`meta.as_of` 锚定数据时点，与 record 的 `as_of` 对齐。
4. **跳过态是一等公民**：闭环未就绪 → `status="skipped"` + 空 `picks` + `skip_reason`，**不是留空、不误挂**（对齐诉求 5 的"结果未出显式占位"）。
5. **与 PICKS 锚点/复盘可对账**：`picks[].code` 全集 == md 的 PICKS 锚点；预留 `review`（复盘回填）块。

### 2.2 Canonical schema（`每日选股` view，v1）

顶层：

```jsonc
{
  "schema_version": "1.0",
  "meta": {
    "pick_date":   "2026-09-09",      // D：选股执行日（=收盘信息定稿日）
    "predict_for": "2026-09-10",      // D+1：预测目标交易日
    "as_of":       "2026-09-09",      // 防未来锚点：数据只用 ≤ 此日
    "generated_at":"2026-09-09T20:15:03+08:00",
    "generator":   "daily-stock-selection", // 生成方：SKILL名/人工/中小模型
    "status":      "ok",              // 枚举：ok | skipped | partial
    "skip_reason": null,              // status!=ok 时必填（如"闭环未在门控窗口内完成"）
    "market_regime":"权重护盘伪涨市/二八分化/个股普跌", // 市场环境定性（自由文本，展示用）
    "market_forecast_ref": null,      // 有 market_forecast.json 时填其 T+1/T+5 p_up 摘要，缺则 null
    "picks_count": 5,
    "source_md":   "docs/每日分析/选股/2026-09-09.md",
    "drift_note":  "cron 18:36 / 实际 18:31:44 / DRIFT ok"
  },
  "picks": [ /* 见 2.3，按 buy_rank 升序 */ ],
  "review": null                       // D+1 复盘回填块，选股时为 null，见 2.4
}
```

### 2.3 `picks[]` 单票 schema

```jsonc
{
  // —— 客观字段：代码回填，Agent 不填 ——
  "code": "601061",
  "name": "中信金属",                  // meta.name（回填）
  "industry": "有色/金属贸易",         // meta.industry ?? code_industry.json（回填）
  "close": 12.18,                      // snapshot.close（回填）
  "pct_chg": 4.91,                     // snapshot.pct_chg（回填）
  "strategies": [                      // 命中策略及分值（从策略视图 join 回填）
    {"name": "策略0合议", "rank": 1, "score": 0.7107},
    {"name": "最大范围选股", "rank": 171, "score": null}
  ],

  // —— 研判字段：Agent 提供 ——
  "type": "买入候选",                  // 枚举：买入候选 | 检验样本 | 规避
  "buy_rank": 1,                       // 买入排序表序号（整数，1 起）
  "stance": "买入",                    // 枚举：买入 | 可参与 | 观望 | 规避
  "stance_qualifier": "首选",          // 修饰词自由文本：首选/小-中仓/不建仓/可小仓…（可空）
  "dir_1d":  "偏多",                   // 枚举：偏多 | 偏空 | 中性 | 低波待动 | 不给方向
  "dir_1d_conf": "中",                 // 枚举：高|中高|中|中低|低|-（不给方向时 "-"）
  "dir_5d":  "偏多",
  "dir_5d_conf": "中高",
  "sentiment_quality": "ok",           // 枚举：ok | partial | unknown | missing（硬纪律，见下）
  "key_reason": "净利+84.55%真利好+PE14.5低估+主力连续6日净流入+放量反包",
  "key_risk":   "铜价回调；已涨2日部分price-in",
  "alpha_beta": "α=铜价景气+主力吸筹相对强度；β=有色板块次要驱动", // 可空
  "watch_points": [                    // 盯点（单问化，每条可用是/否/无数据回答）
    "明日主力是否维持净流入？",
    "收盘是否站稳MA5≈11.63？"
  ],
  "detail_anchor": "选股/2026-09-09.md#1-601061-中信金属" // 指向 md 深度分析锚（人读详情）
}
```

**字段来源映射表**（校验/回填据此）：

| 字段 | 来源 | 谁负责 |
|---|---|---|
| code | Agent 给的选票清单 | Agent |
| name | `record.meta.name`（stock_pool→code_name.json→code） | 代码回填 |
| industry | `record.meta.industry` ?? `config/code_industry.json[code]` | 代码回填 |
| close / pct_chg | `record.snapshot.close` / `.pct_chg` | 代码回填 |
| strategies[].{name,rank,score} | 各策略 view 的 `入选清单/top` 里按 code join | 代码回填 |
| type / buy_rank / stance / stance_qualifier | Agent 研判 | Agent |
| dir_1d(_conf) / dir_5d(_conf) | Agent 研判 | Agent |
| sentiment_quality | Agent 从 `record.sentiment.质量`/`provenance.sentiment` 抄，代码可交叉校验 | Agent+代码校验 |
| key_reason / key_risk / alpha_beta / watch_points | Agent 研判 | Agent |
| meta.* | pick_date=D、predict_for=下一交易日（代码查交易日历）、as_of、status… | 代码/Agent 混合 |

### 2.4 `review` 复盘回填块（D+1 由复盘任务写）

选股时 `review=null`。D+1 复盘任务对 `选股/D.json` 回填（不改 picks，只加 review）：

```jsonc
"review": {
  "review_date": "2026-09-10",
  "review_status": "ok",             // ok | pending（复盘未出时占位，对齐诉求5）
  "market_beta": "全A等权 +0.12%",
  "scorecard": [
    {"code":"601061","alpha_pp": 1.23, "dir_1d_hit": true,  "note":"放量兑现，站稳MA5"},
    {"code":"600356","alpha_pp":-0.17, "dir_1d_hit": false, "note":"造纸弱，走平"}
  ],
  "hit_summary": "方向命中 3/5，等权α +0.4pp"
}
```

> 复用现有 `selection_summary.enrich_view_cross_refs` 的三态思路（待复盘/命中/未命中），但改为**代码直接回填结构化字段**，不再从 md 正则抽。

### 2.5 跳过态示例（诉求 5 的"结果未出"占位）

```jsonc
{
  "schema_version":"1.0",
  "meta":{"pick_date":"2026-09-09","predict_for":"2026-09-10","status":"skipped",
          "skip_reason":"闭环未在门控90分钟窗口内完成","generator":"daily-stock-selection",
          "picks_count":0, "generated_at":"...", "as_of":"2026-09-09"},
  "picks": [],
  "review": null
}
```

对应 md 仍写 `<!-- PICKS: none -->` + "跳过留痕"行——**JSON 与 md 语义一致**，远端据 `status` 显式渲染"今日选股结果未出"，不误挂昨日。

## 3. 诉求 5：日期索引与命名规范

### 3.1 无歧义术语

- **执行日（write date）**：文件被写出来那天 = 文件名里的日期。
- **归属日 / 标的日（subject date）**：文件"讲的是哪个交易日的选票"。
- **预测目标日**：选股预测的 D+1。

### 3.2 各产物日期归属表（规范核心）

| 产物 | 路径 | 文件名日期 | 归属日（讲谁） | 预测/复盘目标 | 顶部必写元数据 |
|---|---|---|---|---|---|
| **选股** | `选股/D.md` + `选股/D.json` | D=执行日 | **D**（当天选的票） | 预测 D+1 | `pick_date=D, predict_for=D+1, status` |
| **日内研判** | `选股/日内_D.md` | D=执行日 | **D-1**（跟踪昨日选票） | 当日盘中 | `subject_pick_date=D-1` |
| **复盘** | `复盘/D.md` | D=执行日 | **D-1**（复盘昨日选票） | 复盘 D-1 的预测 | `review_date=D, subject_pick_date=D-1` |
| **经验沉淀** | `经验沉淀/vD.md` | D=版本日 | 累积（截至 D） | — | changelog（相对上一版改了啥） |
| **结构化选股 JSON** | `data/analysis/D/每日选股.json` | D=pick_date | **D** | D+1 | `meta.pick_date / predict_for / status` |

### 3.3 三条命名/落位规则（要用户拍板）

1. **保持现有文件名按"执行日"命名，不改历史文件**（`复盘/D.md` 仍是 D，避免破坏 `parse_pick_codes`、autopush 白名单、README 时间线、42 篇存量 md）。**歧义靠"文件顶部显式声明归属日 + 标题带箭头"消除**，而非重命名。
   - 选股标题：`# D 选股分析（收盘后选股 → 对 D+1 预测）`（现状已如此，保留）。
   - 复盘标题**建议**统一成：`# 复盘 · D（复盘 D-1 选票 → 对 D 实际）`（现状 `# 复盘 · D（周三）` 未点明归属，建议补 `复盘 D-1 选票`）。
   - 日内标题**建议**：`# 午盘研判 · D（跟踪 D-1 选票）`。
2. **"今日选股 vs 对昨日复盘"物理分离已满足**：选股在 `选股/`、复盘在 `复盘/`，本就分目录。规范只需**强制两者各自在顶部声明归属日**，杜绝"打开一个复盘文件不知道它复盘的哪天"。
3. **"结果未出"显式占位**（硬规则）：
   - 选股任务跳过 → **仍落 `选股/D.md`（`PICKS: none` + 跳过行）+ `选股/D.json`（`status=skipped`）**，不留空目录。
   - D+1 复盘时若 `选股/D.json` 是 skipped → 复盘直接标"D 无选股，无可复盘"，不硬凑。
   - 结构化 JSON 的 `status` ∈ `ok/skipped/partial` 是远端判"是否有今日结果"的唯一开关。

### 3.4 索引文件（可选增强）

新增 `data/analysis/选股索引.json`（或 view `选股索引`），代码维护，一行一天：

```jsonc
{"2026-09-09": {"status":"ok","picks_count":5,"predict_for":"2026-09-10","reviewed":false},
 "2026-09-08": {"status":"ok","picks_count":8,"predict_for":"2026-09-09","reviewed":true}}
```

给远端一个"哪天有选股 / 哪天跳过 / 哪天已复盘"的总账，免逐日翻。

## 4. 诉求 6：流水线程序化架构

### 4.1 该从"Agent 自由写 md"改为"代码按 schema 写 JSON"的步骤

| 步骤 | 现状 | 改为 |
|---|---|---|
| 选票客观信息（名称/行业/价/涨跌/命中策略分值） | Agent 手打进 md 表 | **代码从 record + 策略视图回填** |
| 机读锚点 PICKS | Agent 手写第一行 | **代码据 picks 生成，与 JSON 同源** |
| 结构化落盘 | 无（靠事后正则解析 md） | **代码写 canonical `每日选股.json`** |
| 格式/枚举/防未来校验 | 无 | **代码校验（枚举成员/必填/code 格式/情绪质量闸门/PICKS 一致性）** |
| 投送远端 | md 反解析成 `selection_analysis` 上传 | **`每日选股.json` 作 view 随现有 upload 分片上传** |
| 深度分析正文、市场研判、我vs系统、退出纪律 | Agent 写 md | **保持 Agent 写 md**（这些是判断，不程序化） |

**边界**：Tool 只固化"客观回填 + 结构化落盘 + 校验 + 生成锚点"；**一切研判仍是 Agent 的活**。md 不废弃（人读 + 深度详情锚点目标）。

### 4.2 Tool 接口设计（推荐：轻量 Python CLI，非 MCP）

放 `tools/analysis/write_picks.py`（`tools/analysis/` 已存在，serialize.py 同级）。核心函数：

```python
def build_picks_json(
    pick_date: str,                 # D
    analysis: list[dict],           # Agent 的逐票研判结论（见下"输入契约"）
    *,
    status: str = "ok",
    skip_reason: str | None = None,
    market_regime: str = "",
    generator: str = "daily-stock-selection",
    as_of: str | None = None,       # 默认=pick_date
    analysis_dir: Path | None = None,
) -> tuple[dict, list[str]]:
    """
    回填客观字段 + 组装 canonical dict + 校验。
    返回 (canonical_json, errors)。errors 非空即校验未过（调用方据此决定是否落盘/告警）。
```

### 4.3 校验规则（代码固化，替代人工纪律靠记）

1. `code` 格式 `^\d{6}$`、去重；`picks[].code` 全集 == md PICKS 锚点集合（不一致报错）。
2. 枚举成员：`status/type/stance/dir_*/sentiment_quality/dir_*_conf` 必须在受控集合内。
3. 必填非空：`name/close/pct_chg`（回填后仍缺 → 报错，防"远端只有代码"复现）。
4. **情绪质量闸门（硬纪律代码化）**：`sentiment_quality ∈ {unknown, missing}` 时 `stance` 不得为 `买入` 且 `stance_qualifier` 不得含"首选"（对齐机制 §4 规则7，把"最强表态封顶"从人工纪律变成代码断言）。
5. `status=skipped` → `picks` 必须为空且 `skip_reason` 非空；`status=ok` → `picks_count==len(picks)>0`。
6. 防未来：`meta.as_of <= pick_date`；回填的 record 的 `as_of` 不得晚于 `pick_date`（晚了报警，防抓到更晚数据）。
7. `buy_rank` 连续无重复；`dir_*=不给方向` 时 conf 必须 `-`。

### 4.4 与现有链路的衔接（关键：免改传输层）

- **落盘位置** `data/analysis/D/每日选股.json`（非 6 位文件名）→ `collect_date` **自动**归入 `views["每日选股"]` → `upload.py` **自动**切成分片 `__view__:每日选股` → 现有签名/重试/断点续传/NaN 清洗全复用。**upload.py / import_to_db.py 零改动。**
- **`selection_analysis` 视图**：短期**两者并存**——`每日选股.json` 是新权威结构化源；旧 `selection_summary.build_selection_view`（md 正则）降级为**历史 md 的兜底**（存量 42 篇老 md 没有 JSON，仍靠它）。远端优先读 `每日选股` view，缺则回退 `selection_analysis`。
- **远端 web**（本仓外）：新增 `每日选股` view 的渲染页/列（带名称/行业/表态/方向）。**属远端改动，本方案只约定 schema 契约，不含远端实现**。
- **PICKS 锚点**：`render_picks_md_tables` 生成的锚点与 JSON 同源，`parse_pick_codes` 行为不变（仍认锚点）。

### 4.5 分析师 SKILL 提示词怎么改（诉求 6，仅描述改法，不改文件）

在 `daily-stock-selection/SKILL.md`【产出】段**增加一步**（描述性写法，不塞具体 case）：

> 【结构化产出·调用 Tool】完成逐票研判后，把每只票的**研判结论**（表态/方向/置信/情绪质量/关键理由/关键风险/盯点/命中策略提示）整理成一个 analysis JSON，调用 `python -m tools.analysis.write_picks --date <今天> --analysis <该文件>`。
> - 名称/行业/收盘价/涨跌/命中策略分值**不要手打**，由 Tool 从 record 回填。
> - Tool 会写 `data/analysis/<今天>/每日选股.json` 并做格式/枚举/情绪质量闸门校验；**校验不过（非零退出）必须按报错修正研判 JSON 后重跑**，不得带错落盘。
> - md 仍写（人读 + 深度分析），其"选股结果表/买入排序表 + PICKS 锚点"用 Tool 的 `render_picks_md_tables` 输出贴入，保证 md 与 JSON 同源。
> - 跳过时：`--status skipped --skip-reason "<原因>"`，Tool 落 `status=skipped` 空 picks，md 照写 `PICKS: none`。

同理，复盘 SKILL 增"调用 `write_picks --review` 回填 `review` 块"（D+1）。

### 4.6 为什么用轻量 Tool 而非 MCP（方案取舍）

| 方案 | 优 | 劣 | 结论 |
|---|---|---|---|
| **A. Python 模块 + CLI**（`python -m tools.analysis.write_picks`） | 与现有 tools 调用范式一致（task_guard/upload 都这么调）；零额外常驻进程；易单测；SKILL 一行 bash 即用 | 需 Agent 会拼 analysis JSON | **推荐** |
| B. MCP server | 多 agent/多窗口标准化调用、参数带 schema 校验 | 要常驻 + 注册 + 维护；本场景单机单任务，收益低 | 暂不做，留作后续多协作者接入时升级 |

先落 A；若将来中小模型/合作者 agent 也要程序化产出，再把 A 的 `build_picks_json` 包一层 MCP（逻辑复用，不重写）。

## 6. 风险与兼容（存量 md 不破）

| 风险 | 应对 |
|---|---|
| 破坏 `parse_pick_codes`/存量 md | **不重命名、不改历史 md**；PICKS 锚点机制不变；新增 JSON 是**旁路增量**。 |
| 新旧视图双源冲突 | `每日选股` view 为新权威，`selection_analysis`（md 正则）降级兜底；远端读取优先级明确（新→旧）。存量 42 篇老 md 无 JSON，仍走旧路，不受影响。 |
| 回填字段缺失（次新股/池外票 record 不全） | 回填缺 name/industry 时按来源链回退（stock_pool→code_name→code / code_industry），并在校验里对**仍缺的必填字段报错**而非静默落空。 |
| Agent 拼 analysis JSON 出错 | Tool 校验非零退出 + 明确 errors；SKILL 硬要求"校验不过必须修正重跑"。 |
| 情绪质量闸门误伤 | 闸门只封"买入/首选"上限，不改方向判断；与机制 §4 规则7 一致，属加固非新规。 |
| 上传体积/限流 | `每日选股` 单片仅几只票，远小于 sentiment_policy，走现有分片/节流/429 退避，无新增超时风险。 |
| 交易日历（predict_for/D-1 推算） | 用项目已有交易日历工具推 D+1、D-1；无则退化为"下一自然工作日"并标注。 |

**兼容底线**：本方案**只增不改**（新增 JSON 产物 + 新增 Tool + 可选渲染），传输层（upload/import_to_db）零改动，历史 md 与锚点机制完全保留。

## 7. 需统筹拍板的点

1. **日期命名策略**：确认采用"**文件名仍按执行日、靠顶部归属日声明消歧**"（§3.3 规则1），而非重命名历史文件。（推荐：是——重命名代价大、破锚点。）
2. **view 命名**：结构化产物 view 名定 `每日选股`（中文，随 collect_date 自动成 `__view__:每日选股`）还是英文 `daily_picks`？（推荐中文，与现有 `选股分析报告` 等中文 view 一致。）
3. **新旧视图取舍**：远端读取优先级"`每日选股` 新 → `selection_analysis` 旧兜底"是否认可？旧 `selection_summary` 是否保留长期兜底（历史 md）还是限期迁移。
4. **Tool vs MCP**：确认先落轻量 Python CLI（§4.6 方案 A），MCP 留后续。
5. **情绪质量闸门代码化**：把"`unknown/missing` 不得给买入首选"从人工纪律升为**代码硬断言**（校验不过即拒绝落盘）是否认可。
6. **实施排期**：P1–P3+P5 是否本轮做，还是先只落 P0 骨架 + P1 Tool、观察一个交易日再接生产。
7. **远端 P4**：需不需要本轮就协调远端窗做 `每日选股` view 渲染，还是先在本地/DB 存着、远端后跟。
