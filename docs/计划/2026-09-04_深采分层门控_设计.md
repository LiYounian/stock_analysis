# #23 · 打破深采循环盲区 —— 设计（方案 A，已拍板）

> 日期：2026-09-04。来源：选股文档 §9.6b #23。用户 2026-09-04 拍板走**方案 A（把 two_stage 三层门控移植到 screenall）**。
> ⚠️ 非投资建议，研究模拟。设计/实现窗对接文档。

## 一、问题（循环盲区）

生产日常入口 `ops/launchd/pull_refresh.sh:89 → python -m tools.run screenall`。深采票池由 **`tools/run.py:1099`** 一处集合运算决定：

```python
llm_subset = _dedup(union_picks + watch)   # union(各策略选出并集) ∪ 自选池
```

严格二值：`code ∈ union∪自选` → 全套深采；否则该票当日深采 0 文件。**循环**：未选中 → 深采缺 → 合议专家弃权多 → 软收缩降权 → 更不被选中 → 更不被深采。

### 复盘表述的两处纠偏（Explore 核实，影响方案与预期）
1. **不是"8 类全 0"**：真正受 `llm_subset` 门控的是 **6 类数值面深采**（fundflow / chip / holder_num / block_trade / tick / consensus）。**lhb / margin 是全市场按日采、不受门控**（`run.py:1140` 传全A codes_all；`margin` 由 `pull_refresh.sh:86` 独立全市场拉）→ 天然稀疏，不是选股门控产物。"191/193 ⊆ union" 是相关不是因果。
2. **弃权本身不直接拉低综合分**：弃权专家 `置信度=0`，在"置信度加权分母"下**自动退出、不稀释在场专家**（`council.py:130,137`）。真正压低的是**软收缩** `_confidence_and_shrink`（`council.py:37-95`）：参与专家过少 → 收缩系数<1 → `综合分_收缩 = S×系数`。**且收缩默认是附加字段、不改 `综合分/综合方向`**（`council.py:167-170`），是否进排序取决于二级开关。

→ **前置验证（实现第一步）**：确认"软收缩是否真的喂了选股排序"（那个二级开关的实际取值）。若没喂，循环强度弱于复盘所述，方案收益需重估——但门控盲区本身（6 类数值面缺）仍成立，仍值得修。

## 二、方案 A：移植 two_stage 的三层门控到 screenall

**关键利好：分层采集范式项目里已有、已验证**——`run_two_stage`（`tools/run.py:913-935`）已用：

```python
near_codes   = [接近达标票]
llm_subset   = _dedup(qualified + watch)              # 新闻/LLM 只对达标∪自选(控 token)
analysis_set = _dedup(qualified + watch + near_codes) # 数值面深采含接近达标
```
`analysis_set`（含接近达标）拿全套**数值面深采**（`collect_values_missing/collect_lhb/collect_ticks/serialize/events/factor/council`，`run.py:922-935`），只有最贵的**新闻/LLM 情绪**仍限 `llm_subset`。设计注释 `run.py:896-899` 明说"接近达标票拿技术/因子类合议分，其情绪/事件专家因无新闻自然弃权，不额外烧 token"。

**本方案 = 把这个三层门控搬进 `run_screen_all`**：

```
llm_subset   = union ∪ 自选               # 保持不变:新闻/LLM 情绪仍只对选中集(控成本)
analysis_set = union ∪ 自选 ∪ 边缘候选     # 新增:6 类数值面深采覆盖到边缘候选
```
6 类数值面深采（fundflow/chip/holder_num/block_trade/tick/consensus）的入参从 `llm_subset` 改为 `analysis_set`；新闻/LLM 情绪保持 `llm_subset`。

### 2.1 "边缘候选"怎么定义（screenall 无现成"接近达标"）
two_stage 的"接近达标"来自其达标逻辑；screenall 的 screener 只产 `入选清单`。需让票池构造额外产出一个**有界的边缘集**：
- **排序型策略**（council/momentum/半导体/反转/条件化）：取入选之外的 **top-(K+M)** 那段（如入选 top-20，边缘 = 21–50）；
- **信号型策略**（S01/S02/箱体/S03/S04/S05）：取**差一个条件**的票（各 screener 已算子级判定，暴露"过 N−1 个条件"的集合）；
- **合并去重**成 `边缘候选`，并**设总量上界**（如各策略边缘 top-50 封顶、全局 ≤ M_max）。

### 2.2 成本约束（硬约束，不能对全A深采）
Explore 实测：串行 `FETCH_SLEEP_SEC=0.5`、`FETCH_WORKERS=1`，**单类源全A ≈ 5552×0.5s ≈ 46 分钟**，6 类 ≈ 数小时——这正是"只对 llm_subset 深采"的成本动因（`run.py:1120` 注释）。故：
- 边缘候选**必须设上界**（数值面增量 = 边缘票数 × 6 类，控制在可接受的墙钟内）；
- 新闻/LLM 情绪**坚决不扩**（最贵），仍限 `llm_subset`；
- 复用既有新鲜度门控省量（consensus 5 天、holder_num 28 天，`settings.py:81-82`）——边缘票同样吃缓存跳采。

## 三、方案落点（Explore 核实的锚点）
- 票池构造：`tools/run.py:1080-1099`（union/watch/llm_subset）+ 新增边缘集构造。
- 深采派发：`tools/run.py:1111,1118,1122`（把 6 类数值面的入参从 llm_subset 换 analysis_set；新闻/LLM 保持 llm_subset）。
- 范式样板：`tools/run.py:913-935`（two_stage 的 analysis_set 三层，直接照搬结构）。
- 上界配置：进 `tools/config/settings.py`（如 `SCREENALL_EDGE_TOPK` / `SCREENALL_EDGE_MAX`）。

## 四、可选补充（二级，非本方案主体）
**弃权即时补采钩子**：`enrich_candidates([code], as_of)`（`run.py:466`，幂等/skip-if-cached）可在合议专家因缺数据弃权前现补一票再重读。**但单用无效**——未选中票根本进不到合议（合议只跑已 serialize 的选中集），故它只能作为"某票被点名深看时现补"的补充，不替代方案 A 的分层预采。首版可不做，留接口。

## 五、预期效果
- 边缘候选（接近入选的票）拿到 6 类**数值面深采** → 其资金流/筹码/事件等专家不再因"无数据"弃权 → 拿到公允综合分（不被软收缩降权）→ 真好票浮出到并集，断开"未选中→缺数据→降权→更不选中"的环。
- 成本可控：数值面比 LLM 便宜、边缘集有界、吃缓存跳采；新闻/LLM 不扩。
- lhb/margin 本就全市场采，不受影响。

## 六、测试与开放项
- **测试（守则6）**：断言边缘候选进 `analysis_set` 且拿到 6 类数值面深采；断言新闻/LLM 仍只对 `llm_subset`（成本不失控）；断言边缘集受上界封顶；构造一个"接近入选、原本弃权"的票 → 断言补数据后其数值面专家发声。
- **前置验证**：先查软收缩二级开关是否喂排序（§一纠偏2），据此定预期收益与是否需要同时调收缩策略。
- **开放项**：边缘"top-(K+M)"的 M、信号型"差一个条件"的具体口径、全局上界 M_max，均实现时按全A分布与墙钟预算标定、写进 settings + 测试。

- **前置验证结论**：软收缩**确实喂了 council 选股排序**（`screen_council.py:156` 用 `综合分_收缩` 驱动排序分，

- **上界**：`SCREENALL_EDGE_TOPK`（每策略，默认 20）+ `SCREENALL_EDGE_MAX`（全局，默认 300）；
  `EDGE_MAX=0` 一键回退旧二值门控。
- **默认值 20/300 实测安全（2026-09-04 隔离测量）**：全A ~5552 主档跑全部 screener，4 个排序型边缘产出方
  各命中 TOPK=20 → 80 只原始，去重 + 剔除已在 llm_subset 后 **edge_candidates = 60 只**（远未触及全局
  封顶 300）；`analysis_set = 651`（= llm_subset 591 ∪ 边缘 60）。60 只边缘票的 09-04 四类 daily 数值面
  （fundflow/chip/tick/block_trade）全 cache-miss = 240 次请求 × ~1.1s ≈ **净墙钟增量 4.4min**（holder/consensus
  多命中缓存跳过）。理论打满 300 封顶亦仅 ~22min。**结论：默认 20/300 不会让全A墙钟暴涨，无需调参**，
  "墙钟预算封顶"按设计生效。测量方法：monkeypatch 尾部深采/落盘为 no-op、财报采集 no-op，只跑 screener
  取 `edge_candidates` 规模 + 缓存缺口估算，零污染（未落 analysis 产物）。⚠️ 非投资建议。
