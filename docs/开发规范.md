# 开发规范(本项目宪法)

> 状态:**生效中** · v1.0 · 更新 2026-08-06
> 本文与 [架构设计.md](架构设计.md) 是项目**两篇必读权威文档**。任何人(含新模型/新同事/Agent)开工前**先读这两篇**。
> 目的:让项目**稳定、良性、可持续、可多人/多 Agent 并行**推进 —— 靠文档而非记忆交接,靠规则而非临场发挥。
> 分工:本文管"**怎么做事**"(流程/边界/接口/协作);架构设计管"**系统长什么样**"(分层/模块/数据契约)。

## 一、开发规则(约法)

沿用全局协作守则(约法十四条),落地到本项目的硬约束。按重要度排:

### 1. 动手前先写计划、审阅完再执行(留痕第一)
非 trivial 改动(不止一两行)**开工前先在 `docs/计划/` 写计划文档**,与用户审阅对齐后再执行。
留痕是为了**可交接** —— 换人/换模型时读文档就能接上,不靠翻 memory、翻 commit。
> **严禁**把项目级的约定/进度/决策写进模型 memory(不可移交)。这些只进 `docs/`。

### 2. 遇 bug 先诊断再动手
固定顺序:**读日志 → 划问题范围 → 找根因 → 出方案 → 写明预期效果 → 再执行**。
"预期效果"= 修复生效后应看到的现象,先跟用户对齐再改。**绝不跳步直接改代码**。
每个 bug 的诊断过程记入 `docs/问题/`(见第三章)。

### 3. 选方案先比较再拍板
让用户选时,先列候选方案优劣 + 给推荐 + 说理由,再请用户拍板。不直接按某方案闷头做。

### 4. 编程先框架再实现
顺序:**定目标 → 划分脚本/函数 → 定每个的输入输出 → 再填实现**。
本项目 P0 已按此做:`tools/` 全部骨架 + I/O 契约就位,函数体 `NotImplementedError`,审完契约再填。

### 5. 开发完写测试,断言锁语义
每个功能/优化/修复完成后配测试,**断言要锁住"为什么改"的语义** —— 防未来重写时无意删掉规则。
典型:数据接口降级不能静默返回空(要抛错)、口径决策(如"差1天算不算")要有测试钉死。

### 6. 完成后立刻维护文档
功能/优化/修复一完成,**立刻**写 `docs/日志/开发日志.md` + 更新受影响的架构/README。不拖到下一轮(记忆会衰减)。

### 7. 分步 commit,方便回滚
每完成一个步骤 commit 一次;整轮完工再合并 main。回滚/二分排查时方便。
commit message **不加** `Co-Authored-By: Claude` / `🤖 Generated with Claude Code` 署名(用户要求)。

### 8. push 前脱敏 + 隐私自查
push 前扫一遍:手机号/身份证/真实姓名/API key/token/个人邮箱。
**本项目特有**:`data/` 下的自选股截图暴露个人持仓,若仓库公开则不入库(见 `.gitignore` 与问题台账)。

### 9. 日志按模块划分
`tools/` 各模块(collectors/analysis/report)的运行日志按命名空间分开,便于定位错误来源。新增模块同步加 logger。

### 10. 简单但耗 token 的子任务外包 qwen
读大文件/跨文件搜索/批量改写/长文总结/情感批量打分 → 外包 `qwen-delegate`(走 内部网关,不烧主额度)。
Claude 留下需拍板和上下文连续的部分。本项目 `analysis/sentiment.py` 的情感打分即走此路。

### 11. 分支工作流(每个 P 阶段一条分支)⭐
每个开发阶段(P1/P2/P3/P4…的每个可交付子步)**必须走独立分支**,顺序固定:
1. 从 `main` 建分支:`git checkout -b feat/P3.x-简述`;
2. 在分支上开发 + **自测自验**(跑 `pytest`、必要时浏览器/接口实测);
3. **分步 commit** + **push 到远端同名分支**:`git push -u origin feat/P3.x-...`;
4. 在**开发日志**记录本阶段(做了什么/决策/验证/遗留);
5. 合回 main:`git checkout main && git merge --no-ff feat/P3.x-... && git push origin main`;
6. 再开下一个阶段 → 回到第 1 步。

**自主开发约定(用户授权)**:进入连续自主开发时**不逐步向用户提问**。遇决策点:
- 记录到相应文档(计划/问题台账/开发日志),
- 按"当前已知信息下的最优判断"先实现(选推荐方案),
- 事后连同结果一起交用户 review —— 基于产出的意见更有参考价值。
纯文档整理/对外方案这类非开发产出,可直接提交 main(不强制走分支)。

### "收工"语义
用户说"收工"= 按序做完:① 维护文档(日志/架构/README) → ② commit + push → ③ 合并 main → ④ 总结本轮/下一步/未决问题。不必每次问,说收工即执行。

## 二、文档体系(docs/ 怎么组织)

**核心区分:计划=将要做(前瞻),日志=已经做(回溯),问题=待决与踩坑(专题台账)。**

```
docs/
├── 开发规范.md      ⭐ 本文,总纲(怎么做事)
├── 架构设计.md      ⭐ 架构介绍(分层/模块/接口契约/目录 §9)
├── 工程进度.md      ⭐ 进度(已做/在做/待做)+ 任务分派 + 模块开发包
├── 设计/           设计与权威参考(信息流转与层职责·需求与目标·大模型调用设计·数据结构说明·项目方案总览…)
├── 参考/           背景/调研/运维(技术指标说明·数据源调研·股票清单·环境说明·部署说明·交接文档…)
├── 计划/           【前瞻】动手前写,一 Phase / 一大特性 一份
├── 问题/           【专题】待决问题 + bug 踩坑闭环(问题台账.md)
├── 日志/           【回溯】开发日志,时间倒序(开发日志.md)
└── 报告/ 个股分析/ 汇总/   分析产出
```

**根目录只放三份核心**(规范/架构/进度);设计参考归 `设计/`、`参考/`;流动过程文档归 `计划/问题/日志/`。

## 三、三类过程文档的定义(a/b/c)

### (a) 计划 —— `docs/计划/`
- **是什么**:一个"**将要做什么**"的前置文档。对应约法第1条,在非 trivial 改动**动手前**写。
- **何时写**:每进入一个新 Phase(P1/P2…)或一个较大特性前。
- **写什么**(模板):
  1. 目标 —— 这一步要达成什么
  2. 拆解 —— 涉及哪些脚本/函数,每个的输入输出
  3. **预期效果** —— 做完后应看到的现象(约法第2条,可验证)
  4. 验收/测试标准 —— 怎么算做完、测试断言锁什么语义
  5. 风险/依赖 —— 卡点、外部依赖、待用户拍板项(→ 登记到问题台账)
- **命名**:`Pn_特性名.md`(如 `P1_技术面打通.md`)。
- **生命周期**:写 → **用户审阅** → 执行 → 完成后在文首标 `✅ 已落地` 并写实际与计划的偏差 → 该 Phase 小结进开发日志。

### (b) 问题 —— `docs/问题/问题台账.md`
- **是什么**:开发中遇到的**待决事项**与**bug 踩坑**,按问题聚合(便于日后查"某个坑当时怎么解的")。
- **两类条目**:
  - **待决(open)**:需用户拍板的开放问题、未解决的技术卡点、外部依赖风险(如 akshare 接口改版、Tushare 停运)。带**状态**:`待拍板 / 待修 / 进行中 / 已解决`。
  - **踩坑(闭环)**:bug 从发现到修复的完整记录,遵循约法第2条诊断链:**现象/日志 → 范围 → 根因 → 方案 → 预期效果 → 结果 → 是否锁进回归测试**。
- **每条含**:编号、标题、状态、时间、内容、关联(计划/日志/代码位置)。
- **与日志的区别**:日志是时间线流水;问题是按主题归档的台账。踩坑在日志里一句话带过,详情落台账。

### (c) 工作日志 —— `docs/日志/开发日志.md`
- **是什么**:**已经发生**的事的流水,**时间倒序**(最新在上)。对应约法第6条"完成后立刻维护"。
- **何时写**:每次功能/优化/修复完成后**立刻**追加一条。
- **每条含**:
  1. 日期 + 本轮标题(如 `P0 框架搭建`)
  2. 做了什么(要点)
  3. **关键决策**(用户拍板的口径,如"重点票按综合规则筛")
  4. 结果 / 产出(文件、数据、commit hash)
  5. 遗留 / 下一步 / 新增的待决问题(→ 同步到问题台账)
- **与计划的区别**:计划答"打算怎么做",日志答"实际做了什么、踩了什么坑、下一步"。

## 五、模块边界与接口契约规范(解耦的硬约束)

> 目标:模块之间**零口头约定、可并行开发、可独立替换**。以下为强制规范,细节见 [架构设计.md](架构设计.md) §1/§3/§6。

### 5.1 依赖方向(强制)
- 只能**上层依赖下层**:`基座(config/contracts/llm) ← 采集 ← 分析 ← 组装 ← 聚合/选股 ← 编排 ← 展示`。
- **严禁反向依赖、严禁环依赖**。基座层不得依赖任何业务模块。
- 跨模块协作**只走两种合法通道**:① 中心数据契约(`data/analysis/{code}.json`);② 明确声明的函数接口(§5.3)。**不得** import 其他模块的内部实现。
- **展示/选股/聚合层只认中心记录**:`web/`、`report/`、`screener/`、`portfolio/` 只经 `serialize.load_record` 读记录,**不 import** `technical/predict/event` 等分析器内部。

### 5.2 契约优先(contract-first)
- 中心记录结构的**单一真源**是 `tools/contracts/`。改记录字段的 PR:**先改 contracts + 过 `validate_record` + 全池回归测试**,再改 serialize / 消费方。
- 采集层是**唯一外部 I/O 边界**;分析层纯计算(文本侧才调 LLM);展示层**只读不算不触网**。

### 5.3 三类接口统一签名
| 类 | 签名 | 约定 |
|---|---|---|
| 采集器 | `fetch_X(codes, **opts)->dict[code,payload]`(落 raw)/ `load_X(code)->payload` | 失败单票跳过记日志;拉到空**抛错**不静默 |
| 分析器 | `compute/analyze/predict/aggregate(inputs)->dict` | 纯计算;数据不足标 `数据不足`/null 不崩 |
| 组装/服务 | `serialize.build_record(code,as_of)->record`(过校验)/ `load_record(code)` | 产出必须过 contracts 校验 |

### 5.4 类型 / 量纲 / 命名统一(取自 `contracts`)
- 代码=6 位字符串;日期=`YYYY-MM-DD`;金额默认元(字段含 `_yi`/亿 为亿);百分比=数值;缺失=null(不拿 0/空串冒充)。
- 方向/评级/结论等**枚举一律取 `contracts.ENUMS`**,不各处写字符串字面量。
- **命名一致性**:新字段的判定结论键统一用中文 `结论`/`评级`/`方向`(现存 `ob_os.verdict` 为历史遗留,已在契约标注,统一改动单独排期)。
- 新增模块**同步加 logger 命名空间**(约法第 9 条)。

## 六、Git 协作与多窗口冲突规避(硬约束 —— 已因并发丢过代码)

> 本项目常有多个窗口/Agent 并发操作同一仓库,已发生**分支被覆盖、提交丢失**(靠 reflog 找回)。以下为铁律:
> 📘 **并行开发完整方法论(主窗口统筹 + subagent + worktree,含 prompt 模板与实操命令)**:见 [参考/并行开发模式.md](参考/并行开发模式.md)。

0. **并行开发用 `git worktree`(根治并发)⭐**:多窗口共享一个工作目录会互相切走 HEAD、提交落错分支(已多次踩坑)。因此:
   - **主窗口**固定在主仓 `projects/stock_analysis/`,**只待在 main 做集成**,不在此开发。
   - **每个新开发任务另开 worktree**,放在 `projects/worktree/<任务名>`,各自独立工作目录 + 独立分支,互不干扰:
     ```bash
     git -C ~/Documents/projects/stock_analysis worktree add \
       ~/Documents/projects/worktree/<任务名> -b feat/<任务名>
     # 在该 worktree 目录内开发/测试/commit/push;完成后回主窗口合并 main
     git worktree remove worktree/<任务名>   # 合并后清理
     ```
   - 好处:各窗口 HEAD 独立,**不再互相打断**;主仓 main 始终干净可集成。
   - 认领任务先登记 [工程进度.md](工程进度.md)「进行中」(含 worktree 路径 + 分支)。
1. **main 只做集成**:禁止任何窗口直接在 main 上开发/提交;改动一律走"分支/worktree → 合并"。
2. **一分支一写者一主题**:`feat/<模块或阶段>-<简述>`;同一时刻**同一分支/同一共享文件只有一个写者**。
3. **不并发编辑共享文件**:`开发日志.md`(top 插入最易撞)、`README`、`strategy.py`、`架构设计/开发规范` 等,约定**串行**编辑;或该轮只新建独立文件。
4. **纯新增优先**:能新建独立文件解决的,不改共享文件(如本次契约=只加 `tools/contracts/`,零冲突)。
5. **每次 git 操作前** `git status`(必要时 `git reflog`)确认;**小步提交、及时 push** 到自己远端分支(丢了能找回)。
6. **合并 main 由单一窗口统一操作**;合并前确认无其他窗口正在写。
7. **靠数据契约解耦**(第五章)→ 模块围绕契约开发,天然减少代码级冲突。
