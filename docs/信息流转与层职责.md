# 信息流转与层职责(架构详解)

> 状态:**待审阅**(v0.1) · 2026-08-06 · 分支 docs/arch-flow
> 定位:[架构设计.md](架构设计.md) 的配套详解 —— 讲清 **①信息怎么流 ②任务怎么跑 ③每层干什么/在处理什么/怎么扩展**。
> 回答本轮三问:各层职责讲透 · 新增**回测层** · **数据存取层**该不该独立成层。
> 本文含**现状**与**规划**(明确标注);规划部分先立设计,不立即大改。

## 1. 两张图先行

### 1.1 信息流转图(数据怎么从源头流到用户)

```
外部源:东财 / 腾讯 / 新浪 / 同花顺 / 巨潮 / 百度 / 新闻站 / 大模型网关
   │  ① 采集(爬取指纹伪装 / 调 API / 检索)
   ▼
┌─[数据采集层 collectors]──────────────────────────────────────┐
│  行情 · 基本面 · 公告 · 资金流 · 新闻 ·(评论UGC · 政策)规划    │  唯一外部 I/O 边界
└───────────────┬──────────────────────────────────────────────┘
   │  ② 只写"原始数据"
   ▼
┌─[数据存取层 store]★规划────────────────────────────────────┐
│  统一管数据的"存"与"取";上层不碰路径/格式(现状=文件,未来可换DB) │
└───────────────┬──────────────────────────────────────────────┘
   ▼  data/raw/{kline,fundamental,announcement,fundflow,news,llm_cache}
   │  ③ 读原始数据
   ▼
┌─[分析/策略层]────────────────────────────────────────────────┐
│  分析器(原子能力):technical · valuation · predict · event(LLM情绪) │  纯计算(+LLM)
│  策略(可扩充):选股 / 评分 / 信号  ← 用户写的策略集成在这,供调用     │
└───────────────┬──────────────────────────────────────────────┘
   │  ④ 产出结构化信号
   ▼
┌─[组装层 serialize + contracts 校验]──────────────────────────┐
│  汇各分析器 → 中心记录;落盘前过 validate_record(契约优先)        │
└───────────────┬──────────────────────────────────────────────┘
   ▼  中心数据契约 data/analysis/{code}.json(层间 API)
   │  ⑤ 只读中心记录
   ├──►[聚合/选股层] panel(横表) · screen(策略选股) → 视图 json
   ├──►[回测层]★规划  用历史原始数据回放策略 → 绩效报告 data/analysis/backtest/
   ▼
┌─[展示层 web(只读) / report]──►  用户
```

**主脉络**:`源 → 采集(写raw) → [存取层] → 分析/策略(读raw写信号) → 组装(中心记录+校验) → 聚合/选股/回测(读记录) → 展示(只读)`。
**铁律**:采集只写 raw;分析读 raw 写信号;组装产中心记录;**消费方(聚合/选股/回测/展示)只读中心记录或历史 raw,绝不重算、不触网**。所有"存/取"经**存取层**(规划)。

### 1.2 任务流程图(任务/管线怎么触发执行)

```
[采集任务 collect]  各 collector 并行拉数 → 写 raw
        │ 依赖
        ▼
[组装任务 serialize]  读 raw → 各分析器算 → 中心记录(过校验) + K线图表视图
        │
        ├─►[聚合任务 panel]   中心记录 → 横向总表
        ├─►[选股任务 screen]  中心记录 + 选股策略 → 候选池
        └─►[报告任务 report]  中心记录 → markdown

[情绪任务 sentiment] (opt-in,LLM,单独调度控成本)  news → LLM 抽取 → 情绪
[回测任务 backtest] ★规划 (按需)  历史 raw + 某策略 → 绩效对比基准
```

- 每个任务 = `run.py` 一个子命令(现状);未来收敛为 `pipeline.py` 的显式 DAG(架构 §8.1)。
- **依赖**:serialize 依赖 collect;panel/screen/report 依赖 serialize;sentiment 独立(控 LLM 成本);backtest 依赖历史数据 + 被测策略。
- **失败隔离**:某任务失败,下游读上次成功产物,不连锁崩。

## 2. 分层职责详解(每层:职责 / 在处理什么 / 对外接口 / 怎么扩展)

> "上层依赖下层"强制(架构 §1);跨层只经**中心契约**或**声明的函数接口**。

### 2.1 数据采集层 `collectors/`(用户的"数据采集层")
- **职责**:项目**唯一外部 I/O 边界**。从各网站**爬取**(curl_cffi 指纹伪装 / 浏览器)或**调 API**(akshare / 直连接口)/ **检索**(WebSearch)拿原始信息,归一,交存取层落 `data/raw/`。
- **在处理什么**:一个 collector 管 **一个内容类型 × 一个数据源**:

  | 内容(信息视角) | collector | 机制(数据视角) | 源 | 状态 |
  |---|---|---|---|---|
  | 行情 K线/量价 | market | 调 API | 腾讯/新浪 | ✅ |
  | 基本面/估值 | fundamental | 调 API | 同花顺/百度 | ✅ |
  | 公告 | announcement | 调 API | 巨潮 | ✅ |
  | 资金流 | fundflow | 爬取(curl_cffi 指纹) | 东财 | ✅ |
  | 新闻 | news | 调 API | 东财 | ✅ |
  | 评论 UGC | ugc | 爬取(浏览器,需登录) | 雪球/东财股吧 | 规划 |
  | 政策 | policy | 检索(WebSearch)+LLM | 财经媒体 | 规划 |

- **"信息采集" vs "数据采集"的关系**(回应用户):是**同一采集层的两个视角**——
  - **信息视角(采什么)**:行情 / 基本面 / 公告 / 资金流 / 新闻 / 评论 / 政策。
  - **数据视角(怎么采)**:爬取(curl_cffi / 浏览器) / 调 API(akshare / 直连) / 检索(WebSearch)。
  - 一个 collector = (内容 × 机制)。**规划**:抽 `fetcher` 机制基类(HttpApiFetcher / ImpersonateFetcher / BrowserFetcher / SearchFetcher),collector 只写"取哪类内容 + 归一",机制复用基类。采集若变复杂(增量/去重/调度),再从本层拆出"采集编排"子层。
- **对外接口(统一签名)**:`fetch_X(codes, **opts) -> dict[code, payload]`(拉+落 raw);`load_X(code) -> payload`(读缓存;规划改为走存取层)。失败单票跳过记日志,**拉到空抛错不静默**。
- **怎么扩展**:加新内容/源 = 新建一个 collector 守签名 + 选一个 fetcher 基类。零改动其他模块。

### 2.2 数据存取层 `store/`(★规划 —— 回应"要不要独立成层")
- **决策**:**建议独立成一个薄层**(理由见 §5)。
- **职责**:统一管理"数据的存与取"——raw 原始数据、中心记录、视图 的读写口径集中一处;上层不关心"数据在哪、什么格式"。
- **在处理什么**:把现在散落各处的文件 I/O(各 collector 的 load、serialize 的读写、web 的读、panel/screen 的读)收敛为统一调用。
- **对外接口(规划)**:`get_raw(kind, code)` / `put_raw(kind, code, payload)`;`get_record(code)` / `put_record(rec)`;`get_view(name)` / `put_view(name, data)`;`iter_records()`。
- **怎么扩展/演进**:现状物理是文件;规模化后(数百票/历史截面查询)只把本层实现换成 **DuckDB/SQLite**,**上层零改动**(呼应架构 §5)。**渐进迁移**:先立接口 + 新代码走 store,旧 load_X 逐步改为薄封装,不做一次性大重构。
- **依赖**:基座层(只依赖 config);被采集/分析/组装/聚合/展示依赖。

### 2.3 分析 / 策略层 `analysis/` + `screener/`(用户的"技术层")
拆成两块澄清(用户口中的"技术层"= 策略容器):

**(A) 分析器 Analyzers —— 原子计算能力(稳定,少变)**
- 职责:纯本地计算,输入数据→输出结构化信号。不触网(文本侧才调 LLM)、不落中心记录。
- 成员:`technical`(指标)· `valuation`(估值开关)· `predict`(止盈止损/情景/买卖倾向)· `event`(新闻→LLM 情绪)。
- 接口:`compute/analyze/predict(inputs) -> dict`;数据不足标 `数据不足`/null 不崩。

**(B) 策略层 Strategies —— 可扩充,用户写的选股/筛选/评分策略集成在此**
- 职责:**组合分析器输出 + 阈值/规则 → 选股/评分/信号**。**支持扩充**:按用户需求或新想法写成程序,注册后供调用。
- **接口规划(回应"不同策略怎么区分")**:定义**策略接口 + 注册表**,按**类型**区分命名空间:

  | 策略类型 | 输入 | 输出 | 现有例 |
  |---|---|---|---|
  | **选股 Screen** | 全池中心记录 | 候选代码列表 | 超跌反弹候选 / 主力吸筹(现 screener 预设) |
  | **评分 Score** | 单票中心记录 | 综合分 + 依据 | 买卖倾向打分 / 组合评分 |
  | **信号 Signal** | 单票时序(历史) | 逐日 买/卖/持 | 均线金叉(规划,供回测) |

  - 每个策略 = 一个**标准签名**的函数/类,用装饰器登记 `@strategy(name, kind, params_schema)` 进注册表;**区分靠 `kind` 枚举 + 注册表命名空间**(与未来 `registry.py` 能力注册对齐,架构 §6.4)。
  - 调用方(选股任务 / 回测层 / Web)按 name 取策略,不关心内部实现 → 可插拔、可并行开发、可独立测试。
- **现状 → 规划**:`screener/` 已有预设**选股策略**(pluggable filters);规划升级为**统一策略注册表**(选股/评分/信号三类),阈值仍集中在 `config/strategy.py`。
- **怎么扩展**:写一个新策略函数 + `@strategy` 注册即用;不改调用方。

### 2.4 组装层 `analysis/serialize` + `contracts/`(已有)
- 职责:汇各分析器输出 → **中心记录**;**落盘前过 `validate_record`**(契约优先,archfix §9.2 已接)。只组装不新算。
- 接口:`build_record(code, as_of) -> record` / `load_record(code)`;产出必须过校验。

### 2.5 聚合 / 选股层 `analysis/panel` · `analysis/portfolio` · `screener/`(已有)
- 职责:**只读中心记录**做跨票聚合(板块强弱/宽度/情绪温度)、横表、选股。不改单票记录、不算指标。
- 说明:`screener` 现承载选股策略,规划归入 §2.3(B) 策略层统一管理。

### 2.6 回测层 `backtest/`(★新增 —— 用户点名的架构缺失)
- **职责**:有了策略要能**验证**——用**历史原始数据回放策略**,给出绩效并与基准比较。
- **在处理什么**:
  - 输入:一个**策略**(选股/信号,取自策略层)+ 历史区间 + 票池 + 参数。
  - 过程:**walk-forward** 按时间前进,每个截面**只用当时可见的数据**(t 及以前)跑策略 → 模拟持仓/信号 → 计未来收益。**严禁未来函数**(测试专门钉死)。
  - 输出:绩效指标——收益 / 胜率 / 最大回撤 / 夏普 / IC/RankIC;对比基准(等权持有 / 现有统计预测);落 `data/analysis/backtest/{策略}.json` + 报告。
- **接口**:`backtest(strategy_name, codes, start, end, **opts) -> 绩效dict`。
- **依赖**:策略层(被测策略)+ 数据存取层(历史 raw)。位于聚合层同级(读数据 + 调策略,不产中心记录)。
- **与 ML 的关系**:回测层是**通用框架**;ML 预测只是其中**一种策略**——原 [P3E ML 计划](计划/P3E_ML预测与回测.md) 的"回测框架先行"就落在本层。**统计策略也先在此回测拿基线**。
- **诚实性**:回测≠未来保证;严格样本外、防未来函数、与基准对比,不达标不上线。

### 2.7 编排层 `run.py`(→ 规划 `pipeline.py`)· 展示层 `web/` `report/` · 基座 `config/` `contracts/` `llm/` `store/`
- 编排:按依赖串任务(现 run.py 子命令;规划 pipeline DAG)。薄壳,不含业务。
- 展示:**只读**中心记录/视图渲染,**绝不重算/触网**(archfix §9.3 已修 web 违规)。
- 基座:被各层依赖,自身不依赖业务(config 参数/阈值、contracts 契约、llm 客户端、store 存取)。

## 3. 数据存取层:独立成层 vs 集成(明确决策)

**问题**:数据的拿取和存储,要不要专门一层?

**决策:建议独立成一个薄的"数据存取层" `store/`**,理由:
1. **收敛口径**:现在"数据在哪、什么格式"散落在各 collector/serialize/web,改存储要改一片。集中后只改一处。
2. **未来换 DB 零痛**:架构 §5 已规划规模化后上 DuckDB/SQLite;有存取层则**只换本层实现,上层不动**。
3. **契约解耦的物理落点**:中心契约是"逻辑 API",存取层是"物理 API",二者配合让上层彻底不碰存储细节。

**不推荐**:把存取散落集成进各模块(现状)——短期省事,长期改存储/上 DB 时全项目大改。

**落地(渐进,不大重构)**:先立 `store/` 接口 + 新代码走 store;旧 `load_X`/`serialize` 读写逐步改为薄封装;物理仍是文件,择机换 DB。**优先级:中(先立接口,再迁移)**。

## 4. 落地建议(现状 / 规划 / 优先级)

| 层 | 现状 | 规划动作 | 优先级 |
|---|---|---|---|
| 数据采集 collectors | ✅ 6 类 | 抽 fetcher 机制基类;补 ugc/policy | 中 |
| **数据存取 store** | ❌ 散落 | **新增薄层,渐进迁移**(文件→未来DB) | 中(先立接口) |
| 分析器 analyzers | ✅ 稳定 | — | — |
| **策略层 strategies** | 部分(screener) | **升级统一策略注册表**(选股/评分/信号) | 中 |
| 组装 serialize+contracts | ✅(校验已接) | — | — |
| 聚合/选股 panel/portfolio | ✅ | screener 归入策略层 | 低 |
| **回测 backtest** | ❌ 缺失 | **新增回测框架**(通用;ML/统计策略都在此验证) | **高(点名,验证策略必需)** |
| 编排 run→pipeline | run.py | pipeline DAG | 规划 |
| 展示 web/report | ✅(违规已修) | — | — |

**建议推进顺序**:①策略层接口(把选股/评分统一成可注册策略)→ ②回测层(有了统一策略就能回测验证)→ ③数据存取层(渐进,支撑前两者取历史数据)。三者环环相扣:**策略可注册 → 回测能通用调用 → 存取层供历史数据**。
