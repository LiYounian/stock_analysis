## 1. launchd 装载(主项 · 照着做)

### 1.0 先搞清楚这一步在解决什么问题(不影响操作,可略读)

现在 9 个定时任务(选股、盘中快照、复盘等)每次触发时,直接跑主仓工作区里的脚本。
问题:主仓工作区经常被其它会话"卡"在旧版本或留着没提交的改动,于是**改了脚本也不会自动生效**,
每次都得人工去手动部署。

这一轮改动把它根治成:定时任务改为先跑一个**装在项目目录之外、位置固定**的"引导脚本",
引导脚本每次都把一个**专用副本目录(deploy worktree)**刷新到最新的线上代码,再去跑那份最新脚本。
这样"跑的到底是哪版脚本"就和主仓乱不乱彻底脱钩了。

代码已经全部合进线上(origin/main),但**"让它在你机器上生效"这一步是纯人工的**,就是下面 1.1–1.4。

权威技术手册在 `docs/参考/部署卫生_launchd装载runbook.md`,本节是它的"照着做"版本。

### ⚠️ 安全提示(务必先读)

- 这一步动的是**全部 9 个生产定时任务**,风险高、不完全可逆——所以有第 1.4 节回滚兜底。
- **卸载(unload)一个正在运行的任务,会立刻把它杀掉(SIGTERM)**。所以每动一个任务前,必须先查它是不是正在跑。
- **挑安静窗口做**:最好选没有任何 com.stock 任务在跑的时间。各任务的触发时点见 1.1 的表,
  周末或交易日盘前/深夜通常最安全。
- 下面命令里,**只有极少数可能弹系统密码**(见每步标注);弹密码的只能你本人操作,agent 代不了。

### 1.1 第一步:查有没有任务正在跑(每次动手前都查)

在终端里跑:

```bash
launchctl list | grep com.stock
```

- 看**第一列**:是数字=**正在跑**,是 `-`=没在跑。
- 只要有任何一个在跑,就**等它跑完**,或换个时段再做。
- 各任务触发时点(交易日):盘中 10:30 / 午盘 11:31 / 午盘选股 11:32 / 盘中盯 13:00 /
  宽度 15:05 / 拉取刷新 15:40(盘后可能跑 ~1 小时)/ 复盘 17:00 / 最强刷新 20:00 /
  文档提交 11:20–22:20 每小时。→ **深夜(23:00 后)或周末最安全。**

> 说明:此命令是只读的,随便跑。

### 1.2 第二步:一次性准备(建专用副本 + 装引导脚本)

```bash
bash ~/Documents/projects/stock_analysis/ops/launchd/provision_deploy.sh
```

- 这一步**幂等**,重复跑也安全;它只碰专用副本目录,**绝不动你主仓的代码/未提交改动**。
- 成功后应能看到这两样东西存在(可跑下面这行确认):

```bash
ls ~/Documents/projects/worktrees/stock_analysis/deploy/.git && ls ~/.local/state/stock/bin/stock-launchd-bootstrap.sh
```

两行都打印出路径=成功。若报 "No such file or directory" 就是没建好,回头看 provision 的输出报错。

> **一般不需要密码。** 这步是建目录和拷脚本到你自己的 home 目录下,不涉及系统权限。

### 1.3 第三步:逐个重装 9 个任务

对**每一个**任务重复同一套动作:卸载旧的 → 用最新配置覆盖 → 重新装载 → 确认。
把下面这段整体复制到终端(它用 `LABEL` 变量,换任务只改第一行):

```bash
LABEL=com.stock.pullrefresh
SRC=~/Documents/projects/stock_analysis/ops/launchd/$LABEL.plist
DST=~/Library/LaunchAgents/$LABEL.plist

launchctl unload "$DST" 2>/dev/null || true   # 卸载旧的(没装过会忽略报错)
cp -f "$SRC" "$DST"                            # 用最新配置覆盖
plutil -lint "$DST"                            # 校验格式(应显示 OK)
launchctl load "$DST"                          # 重新装载
launchctl list | grep "$LABEL"                 # 确认已装载(能打印出来即可)
```

然后把第一行的 `LABEL=` 依次换成下面每一个,重跑上面这段(**换任务前记得回 1.1 复查是否在跑**):

```
com.stock.pullrefresh
com.stock.breadth
com.stock.strong
com.stock.commitdocs
com.stock.intraday
com.stock.intraday_noon
com.stock.intraday_review
com.stock.intraday_screen
com.stock.intraday_watch
```

> `com.stock.intraday` 和 `com.stock.intraday_noon` 共用同一份脚本,靠各自配置里的时段参数区分,
> 分别装载互不影响,照做即可。
>
> **一般不需要密码。** 这些操作都在你自己的 `~/Library/LaunchAgents/` 下,是当前用户的定时任务,不动系统级设置。
> 如果哪一步意外弹出输密码/授权框,先停下别输,把弹框内容记下来问一下再继续——正常流程不该弹。

### 1.4 第四步:验收

**A. 静态检查**——确认 9 个任务都已指向新的引导脚本:

```bash
for p in ~/Library/LaunchAgents/com.stock.*.plist; do echo "== $p =="; /usr/libexec/PlistBuddy -c "Print :ProgramArguments" "$p"; done
```

每一个都应显示三行:`/bin/bash`、`.../stock-launchd-bootstrap.sh`、`<脚本名>.sh`。
**如果还看到直指主仓 `ops/launchd/xxx.sh` 的旧路径,说明那个任务的 1.3 没生效,重做它。**
(装载前它们本来就是旧路径——这正是现在的状态,核实过。)

**B. 试跑一个低风险任务**——`commitdocs` 幂等、不采集数据,拿它试最安全:

```bash
launchctl start com.stock.commitdocs
sleep 5
tail -n 40 ~/.local/state/stock/commitdocs.out.log ~/.local/state/stock/commitdocs.err.log
```

预期:日志里能看到"把专用副本刷新到最新线上代码"之类的字样,随后脚本正常跑完。

### 1.5 出错了怎么回滚

- **某一个任务出问题**:把它的配置改回直指主仓脚本的旧形态,再 `unload → cp → load` 一遍即可。
  (旧形态长这样:启动路径 = `/bin/bash` + `~/Documents/projects/stock_analysis/ops/launchd/<脚本名>.sh`,没有中间那个引导脚本。)
- **想整体退回**:9 个全按上句改回并重装;已建的专用副本目录和引导脚本可以留着不管(没被引用就没影响)。
- **看到任务退出码 3 或 4**:3=专用副本目录没了,4=目标脚本没找到——都不会偷偷跑旧代码,
  重跑一遍 1.2 的 provision 修复即可。

### 1.6 这轮装的两批改动是什么(背景,可略)

- **部署卫生(引导脚本 + 专用副本 + 改 9 个配置指向)**:就是 1.0 讲的那套,让脚本永远跑最新线上版本。
- **可靠性护栏 A2/A3**(已在最新代码里,装载后自动生效):
  - A2:长任务运行期间**防止 Mac 睡眠**(进程级,不改你的系统电源设置,任务结束自动解除)。
  - A3:**单实例锁 + 陈旧锁自动清理**(避免同一任务重复叠跑;死掉的旧锁超时会自动让位,不会误杀正在跑的)。
  这两项已在 `pull_refresh.sh`、`strong_refresh.sh`、`intraday_screen.sh` 三个脚本 + `ops/launchd/lib/lock.sh` 里,核实存在。

## 2. ff-only 根治(和第 1 节同源,建议一起说/一起做)

### 是什么

日更流程在更新代码时用的是"快进式合并"(`git merge --ff-only origin/main`):它要求主仓工作区是干净的,
一旦工作区里有未提交/未跟踪的文件挡路,合并就会中止,于是**脚本类改动没法自动部署到生产**,
只能人工一个个手动搬(本轮已经手动搬过好几次)。

### 现在卡在哪(已核实)

主仓工作区当前有 **106 个未跟踪文件**(主要是 `data/analysis/<日期>/` 一批分析产出目录),
外加 4 个已改动但没提交的跟踪文件(含 `ops/launchd/commit_analysis_docs.sh`)。
这些就是挡住 ff-only 合并的东西。

### 和第 1 节的关系

第 1 节的引导脚本机制,已经让"**定时任务跑哪版脚本**"这件事和主仓乱不乱脱钩了——
所以装完第 1 节后,ff-only 挡路**不再影响定时任务实际执行**。
但 ff-only 本身(主仓自更这条路)还是脏的,清干净能让主仓状态更整洁、减少将来手动搬运。

### 建议

- **优先级**:第 1 节做完后,这一项就不再紧急,可以从容处理。
- **两个根治方向**(择一,都属于需要你或后续会话动手的清理,本文只说明不代做):
  1. 清理主仓工作区里分析文档的产生源头——弄清 `data/analysis/<日期>/` 和复盘文档为什么会以未跟踪副本留在主仓,从源头不再往主仓工作区写。
  2. 或者:在日更 ff-only 合并之前,先把未跟踪文件安全挪开(stash)。
- **注意**:这 106 个未跟踪文件里可能混着别的会话正在做的东西,**清理前必须先确认没有正在进行的工作**,不能无脑 `git clean`。这一步风险点在这里,建议交给一个专门的会话谨慎处理,不要顺手删。

## 3. 行业反转 / regime 择时(线索,不是现在能动手的操作)

### 来龙去脉

之前做了一个"行业层反转"的轻量探针,结论是**证伪**——没有可检出的选股增量,已经不投产。
但探针跑出一个副产品线索:近端有"越热的行业反而后面跑输"的反转迹象(regime 择时的苗头)。

### 为什么现在推不动

这个方向要成立,**必须先补两样数据**,而这两样现在都没有:

1. **申万一级行业指数的长历史**——现在只有约 1.2 年,太短,做不了稳健的 regime 判断。
2. **真正的"时点准确"(PIT)申万行业成分**——即"某只股票在历史某天属于哪个行业"要按当时的真实归属,
   而不是拿今天的归属倒推(否则会有前视偏差,结论不可信)。

### 所以这一项的性质

它**不是你手动跑几条命令就能推进的**,而是一个"要不要立项去补历史数据源"的决定。
需要的输入:上面两样数据从哪来(数据供应商 / 现成数据集 / 自建)、成本多少、值不值得为一个尚不确定的 regime 线索投入。
**在补齐数据之前,这条线只能挂起。** 建议:先不动,等有明确数据来源了再评估立项。

## 4. 数据源 P2/P3 增强(低优先 · 待排期,不用现在动)

三个小增强,都属于"锦上添花、不急":

- **retry 普及**:给更多数据采集调用加上失败重试,减少偶发网络抖动导致的漏采。
- **批量并发**:把还在串行跑的采集改成并发,进一步提速。
- **归一收口**:把数量级/单位换算(股/万元/元 之类)的归一化逻辑收拢到一处,少几个散落的转换点。

**为什么不急**:核心的数据语义加固(P0)和当日提速(P1)前几轮已经做完并投产,
现在数据链路是可用且正确的;P2/P3 只是可靠性和整洁度的边际提升,没有阻塞任何在跑的流程。
**结论:待排期,现在不用动手。** 将来某轮有富余再排。
