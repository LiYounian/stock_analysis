## §0 背景与目标

### 为什么做（来自乙案效果验证结论）

金字塔选股给闭卷 LLM（DeepSeek/千问）加了「每票新闻 digest + 辩证核对提示词」（W3
加厚），意图是让模型能**辨新闻真伪、看利好利空**。但 2026-09-17 的 A/B 机制验证
（temperature=0 口径）实测发现：

- 决策包实入的 **20 张候选卡里 19 张「0 条新闻/无覆盖」降级**；
- 唯一有量的 1 张（000572）是「近 65 条，利好 0/利空 0/中性 0/**未标注 65**」——
  全部未标注，零真伪信号；
- 归因结论：W3-B 辩证段确实改了模型「怎么说」（诚实标注缺失、不硬凑利好），
  但 W3-A digest **没能改「选什么」，因为根本没有 digest 内容可援引**。

一句话：**digest / 辩证段 / 未来的甲案（function-calling 下钻）全部卡在
「没有个股新闻数据可用」这个地基上**。乙案已判定：

> 当前瓶颈是**数据（news_raw 覆盖率 + 利好/利空标注率）**，不是提示词，更不是取数机制。
> 建议 backlog4 甲案暂缓，先补新闻数据覆盖与标注。

本任务 = 补这个地基。

### 目标

1. **覆盖率**：让金字塔决策包实入的每一张候选卡都能拿到有量的个股新闻（目标：
   决策包 top-N 池的新闻覆盖率从当前近乎 0 提升到 ≥90%）。
2. **标注率**：让有覆盖的票带上可信的**利好/利空/中性**标注（消灭「有量但全未标注」）。

达成后，闭卷 digest 本身就能提供真伪信号，多数场景无需 function-calling 下钻。

## §1 现状诊断（真实数据 + 代码定位）

### 1.1 两条个股新闻链路并存

系统里**同时有两个个股新闻源**，落在两个不同目录，字段与来路完全不同：

| 源 | 目录 | 采集器 | 字段 | 利好/利空标注 | 用途 |
|---|---|---|---|---|---|
| 多源新闻 | `data/raw/<date>/news/<code>.json` | `tools/collectors/news.py`（`fetch_news`，可 `recall=True` 扩召回） | `title/content/time/source/url` | **无** | 旧 `event.py` 净情绪分 + `news_raw` 兜底源 |
| 百度情绪 | `data/raw/<date>/baidu_news/<code>.json` | `tools/collectors/baidu_news.py`（`fetch_baidu_news`） | `title/source/publish_time/publish_ts/benefit_type/benefit_label/abstract/url/news_id` | **有**（百度自带 `benefitType`） | `news_raw` 主源（金字塔 digest） |

金字塔 digest 的读取侧 `tools/pyramid/tools/news_raw_tool.py`：

- **主源 baidu_news**（有 `benefit_label`）→ 缺文件才**兜底 news**（无标签，一律标「未标注」，见
  `news_raw_tool.py:93`）；
- 三态诚实：两源全缺 → `missing`（无覆盖）；文件在但 0 条 → `fresh`（已落盘·0 条）；有条目 → `fresh`。
- 防未来：只保留 `publish_time ≤ as_of` 的条目（`news_raw_tool.py:144-147`）。

关键推论：**`benefit_label` 的「未标注」只可能来自 news 兜底源**——百度源恒有标签
（`baidu_news.py:55-57`，`benefitType` 1/-1/0 → 利好/利空/中性，未知一律归「中性」）。
所以「有量但全未标注」= **这票落到了 news 兜底源，即 baidu_news 缺该票**。

> 附注（另一条独立情绪链路，勿混淆）：候选卡 `data/analysis/<date>/<code>.json` 里的
> `sentiment.三层.新闻`（净情绪/样本数）走的是**旧 `event.py` 净情绪路径、读 news 源**，
> 样本常只有个位数，与 baidu/news_raw digest 不是同一套。本任务聚焦 news_raw digest 链路。

### 1.2 覆盖率实测（2026-09-17，一个交易日）

全市场落盘规模：

| 源 | 文件数（票） | 总条数 | 带 `benefit_label` 条数 | 标签分布 |
|---|---|---|---|---|
| news | 894 | 16,253 | 0 | —（无标注字段） |
| baidu_news | 268 | 28,019 | 27,885 | 利好 12,045 / 中性 12,660 / 利空 3,180 |

- **baidu_news（268 票）是 news（894 票）的严格子集**：626 票只有 news、无 baidu 标注。
- baidu 源的标注**并非失效**——27,885/28,019 条都带标签（缺的少量是无 `benefitType` 的条目）。

### 1.3 覆盖率断层：**「富集池」与「决策池」不是同一批票**（核心根因）

同一个交易日，两个不同的「候选票池」新闻覆盖天差地别：

**（A）午盘全 A 候选池（84 票）——覆盖良好**

`data/intraday/2026-09-17/noon_candidates.json` 记 `候选池规模=84`。实测这 84 张候选卡：

- baidu 覆盖 **83/84**，每票 **200+ 条带标注**条目；
- 缺 both 源 = 0，file-present-but-0 = 0，带 ≥1 标注条目 = 83。

**（B）金字塔骨架 top-N 池（决策包实入·验证用的 20 票）——近乎零覆盖**

乙案验证的决策池是「骨架 top15 分桶实入 20 票」。抽验其中被点名的骨架票：

| code | baidu | news | 有候选卡? |
|---|---|---|---|
| 688175 / 600640 / 300776 / 301551 / 002849 / 301571 / 600847 / 002281 | 缺 | 缺 | 否 |
| 000572 | 缺 | 65 条（全未标注） | 否 |

即 **8/9 两源全缺 → `missing`「无覆盖」，1/9 落 news 兜底 → 65 条全「未标注」**，
与乙案「19/20 空、1×65 未标注」完全吻合。

**为什么会断层——两个池由不同标准选出、互不对齐：**

1. **新闻富集集** = `collect_message(codes)` 采（`tools/run.py:302`，同时跑 `news.fetch_news`
   + `baidu_news.fetch_baidu_news`）。它的 `codes` 是：
   - 收盘两阶段：`llm_subset = 达标(qualified) ∪ 自选(watch)`（`run.py:1077`，注释「关键省 token」）；
   - 午盘：全 A 午盘候选池（84 票，故 A 覆盖好）。
2. **金字塔决策池** = `d2_package.build_package` 里 `C.build_skeleton(as_of)` 遍历
   **召回池 `shared_pool_tool.pool_with_labels`**（`d2_compose.py:178-189`），再
   `select_top(排序, top_n)` 按**骨架分**（五基石加权，其中「策略共识」仅权重 0.20，
   `d2_compose.py:20`）取 top-N。
3. 于是 **骨架 top-N 的票很多不在 `达标∪自选` 富集集里**（骨架分高 ≠ 形态筛达标 ≠ 自选），
   → 它们从未被 `collect_message` 采过新闻 → baidu/news 双缺 → 决策包 digest 全空。

> 一句话根因：**采新闻的池（达标∪自选）≠ 喂给 LLM 决策的池（骨架 top-N），二者不对齐。
> LLM 真正要研判的票，恰恰是没被富集新闻的票。**

### 1.4 次要断点

- **baidu ⊂ news 的原因**：`news.fetch_news(recall=True)` 会按行业主题词**扩召回**额外票
  （`collectors/news_recall.py`），baidu 不扩召回 → news 票数天然更多；此外 baidu 对港股
  直接落空（`baidu_news.py:301`）、反爬/限流单票降级（`baidu_news.py:320-322`）也会掉票。
- **baidu 标签质量未经校验**：`baidu_news.py:40-42` 注释明确「`benefitType` 1/-1/0=利好/利空/中性
  是**按分布推断、未逐条人工核**；生产接入前应抽样校验」。当前直接采信。
- **已有个股级 LLM 研判能力但只用在板块龙头**：`tools/analysis/sector_forecast/news_catalyst.py`
  已实现「定向抓龙头股新闻 → LLM 按 rubric（可信度/影响程度/执行度/来源）判利好/利空/强度」，
  复用 `event._cached_extract` + `POLICY_SCORE_SCHEMA`（带缓存、真 LLM 走内部网关）。**这是一套
  现成的、可下沉到个股的标注管线**，目前只在板块级消费。

## §2 需求

### 需求① 提升个股新闻覆盖率（先对齐池，再扩源）

- **①-a 池对齐（最高优先·根因直击）**：决策包 top-N 池实入哪些票，就先给哪些票补新闻。
  即在金字塔 `build_package` 组卡**之前**，对 `select_top` 选出的骨架 top-N 票做一次
  **定向 baidu_news 补采**（缺则采、有则复用新鲜度门控），保证「要研判的票」都有覆盖。
- **①-b 覆盖扩源/补票**：诊断 baidu ⊂ news 的掉票（港股/反爬/未扩召回），对决策池票必要时
  叠加 news 兜底与其他源，减少 `missing`。
- **①-c 定时前向累积**：确认 `BAIDU_NEWS_COLLECT` 每日盘后稳定跑（前向增量并集，越早累积越好），
  并对决策池票做一次盘后定向兜底。

### 需求② 建/修个股级利好利空标注管线

覆盖上来后，要保证「有量」→「有标注」：

- **②-a 采信并校验 baidu 标签**：对 baidu 源，抽样人工/规则校验 `benefitType→利好/利空/中性`
  映射质量（当前未验证），达标即直接采用（零额外 LLM 成本）。
- **②-b 兜底票的标注**：对只有 news 兜底（无标签）的票，**下沉板块级 rubric 研判到个股**——
  复用 `news_catalyst.py` 的 rubric + `event._cached_extract`，对个股新闻做「利好/利空/中性 +
  可信度/影响程度/执行度」文字档标注，只对**决策池内、baidu 缺失**的票跑（控 LLM 成本）。

## §3 实现计划（分阶段·可交 Cursor 逐段执行）

> 通用防未来铁律（每阶段都适用）：只用 `publish_time ≤ as_of` 的条目，绝不用采集日冒充发布日、
> 绝不回填未来新闻；前向增量并集幂等（已由 `baidu_news._merge_incremental` 保证）。
> 通用验收铁律：每阶段带断言测试，锁住语义（覆盖率/标注率不回退）。

### 阶段 1 · 池对齐（骨架 top-N 定向补新闻）—— 根因直击、ROI 最高

- **目标**：决策包 top-N 池的新闻覆盖率从近乎 0 → ≥90%，「无覆盖」降级基本消失。
- **接口契约（统筹审定 2026-09-20·关键边界：补采绝不无条件内联进 build_package）**：
  `build_package` 现被两类读方复用——① `get_canonical_package` 在 miss/rebuild 时调（canonical
  钉死）、② SKILL/库内临时调用。**若把 scraping 内联进 build_package，canonical 读与库内调用都会
  触发联网，污染 build_package 纯度且被反爬拖慢**。因此：
  1. **补采做成独立、显式开关的步骤**：独立函数如 `ensure_topN_news(top_codes, as_of)`，或
     `build_package(..., 补采_topN=False)` **默认关**；**绝不无条件内联 scraping**。
     补采实现复用 `baidu_news.fetch_baidu_news(top_codes, skip_fresh=True)`（现成新鲜度门控，
     缺则采、新鲜则跳过），把文件写进 `data/raw/<as_of>/baidu_news/`，让 `news_raw` 主源命中。
  2. **canonical 读方永不触发补采**：LLM 合成层 `collect_package → get_canonical_package`
     **默认关补采**，只消费钉死包；`news_raw_tool` 读取路径/三态语义**一字不改**。
  3. **生产顺序钉清楚**：**每日决策包生成入口**先带补采（必要时 `--rebuild`）构建 →
     把补采后的 digest **一次性固化进 canonical 钉死包** → 下游（DeepSeek/千问/SKILL）只读这份
     钉死包。这样 canonical 钉死与补采**天然一致、不冲突**（补采只在生成入口发生一次）。
- **数据与防未来**：补采只取 `publish_time ≤ as_of`、**绝不回填未来**（最高优先）；补采即当日快照
  的前向增量并集，`fetch_baidu_news` 已按 `publish_ts` 落盘、`news_raw` 读时再按 `as_of` 切片，无前视。
- **验收/测试**：
  - 单测：断言 `build_package` **默认不触发任何联网补采**（canonical 读方纯净）；仅显式开启
    （`补采_topN=True` 或调 `ensure_topN_news`）时才对 top-N 全体 code 触发补采（mock `fetch_baidu_news`）。
  - 防未来断言：补采落盘后经 `news_raw` 切片，**无任何 `publish_time > as_of` 的条目进入 digest**。
  - 端到端：每日生成入口带补采 `--rebuild` 后，断言钉死包 top-N 卡 `missing` 比例 <10%、
    带标注条目卡 ≥90%；下游读同一钉死包不再联网。
- **工作量估**：input ~15–25K token（读 build_package/collect 链路 + 写补采钩子 + 测试），
  output ~3–5K token；agent 执行 ~0.5–1 小时（含真跑一次决策包重建校验，走内部网关 env）。

### 阶段 2 · 覆盖扩源/补票（消化 baidu ⊂ news 掉票）

- **目标**：把决策池内 baidu 缺失（落 news 兜底或 missing）的票尽量补成 baidu 有标注；
  港股/反爬掉票有明确降级路径与告警。
- **改哪些文件/接口契约**：
  - 诊断 `baidu_news._fetch_raw` 掉票分布（限流/结构漂移/港股），必要时对决策池票加重试预算
    或第二采集通道；对确实无 baidu 的票，保证 news 兜底至少有量（对齐 `news.fetch_news`
    的池到决策池）。
  - 可选：把 `collect_message` 的新闻富集集从 `达标∪自选` 扩展为 `达标∪自选∪骨架top-N`
    （与阶段 1 二选一或叠加；阶段 1 更省，因只补 top-N 而非全召回池）。
- **数据与防未来**：同上；扩采不改防未来切片。
- **验收/测试**：断言决策池票 `missing` 率 <5%；港股/失败票有 WARNING 日志与降级标记，
  不静默、不阻断闭环。
- **工作量估**：input ~20–30K token，output ~4–6K token；agent ~1–1.5 小时（含抓包核 baidu
  掉票原因）。

### 阶段 3 · 个股级利好利空标注（校验 baidu + 下沉 rubric 兜底）

- **目标**：有覆盖即有可信标注；消灭「有量全未标注」。
- **改哪些文件/接口契约**：
  - ②-a：写一个**抽样校验脚本**（放 `tools/experimental/` 或 `tools/eval/`），对 baidu
    `benefitType→标签` 抽样比对（人工小样本或与 news_catalyst LLM 研判交叉），产出准确率报告；
    达标则维持现映射，不达标则调整 `_BENEFIT_LABEL` 或改走 ②-b。
  - ②-b：新增**个股级 rubric 标注器**（复用 `news_catalyst.py` 的 RUBRIC +
    `event._cached_extract` + `POLICY_SCORE_SCHEMA`），接口
    `annotate_stock_news(code, as_of) -> [{条目, 方向, 可信度, 影响程度, 执行度}]`；
    只对**决策池内、baidu 缺失、落 news 兜底**的票跑（控成本）。`news_raw_tool` 增加读取
    这份标注的能力（优先级：baidu 原生标签 > LLM rubric 标注 > 未标注）。
- **数据与防未来**：LLM 只判 `≤as_of` 已发布新闻；带缓存幂等（`_cached_extract`）。
- **验收/测试**：断言兜底票标注后「未标注」占比大幅下降；rubric 输出全为文字档（无裸数值，
  对齐 `news_catalyst` 口径）；缓存命中不重复烧 token。
- **工作量估**：input ~25–40K token，output ~6–10K token；agent ~1.5–2.5 小时
  （②-b 含真调 LLM 走内部网关、抽样校验来回）。LLM 调用成本随决策池 baidu 缺失票数线性增长。

### 阶段 4 · （可选·待前三阶段达标后）重估甲案 function-calling

- 数据覆盖/标注达标后，用乙案搭好的**同一套只读 A/B 开关 + driver**
  （`tools/experimental/ab_verify/`）真正衡量「按需下钻 vs 闭卷 digest」的增量，再决定是否做甲案。
- 工作量：沿用现成框架，input ~15K token，output ~3K token；agent ~1 小时（主要是真跑 A/B）。

## §4 风险 / 依赖表

| 风险/依赖 | 说明 | 缓解 |
|---|---|---|
| 百度接口反爬/限流 | `finance.pae.baidu.com/vapi/sentimentlist` 免登录但可能限流；决策池定向补采会短时集中打接口 | 复用 `BAIDU_NEWS_STALE_DAYS=0.5` 新鲜度门控跳过重拉、`FETCH_SLEEP_SEC` 节流、单票 `_safe` 降级；触发限流可 `BAIDU_NEWS_COLLECT=0` 临停 |
| 百度结构漂移 | 返回 JSON 层级/字段改名 | `_extract_list` 已防御式兜底取不到返回 `[]`；加结构漂移告警 |
| 港股无此接口 | baidu 对港股落空 | 港股走 news 兜底或明确弃权，不当缺失误报 |
| **baidu 标签质量未验证** | `benefitType` 1/-1/0 映射是按分布推断、未逐条核 | 阶段 3-a 抽样校验为前置门槛；不达标改走 rubric 标注 |
| LLM 标注成本 | 阶段 3-b 对兜底票真调 LLM，成本随缺失票数线性增长 | 只对「决策池内 ∩ baidu 缺失」跑；`_cached_extract` 缓存幂等；决策池 top-N 规模小（~15-20）本身即天然限流 |
| 标注质量/口径漂移 | LLM 研判可能与 baidu 标签、人工判断不一致 | 全文字档（无裸数值）、带可信度/来源一手性；`news_raw` 保留三态诚实，缺数据绝不编造 |
| **防未来（最高优先）** | 补采/标注任何环节误用采集日或回填未来新闻会污染回测 | 全链路只用 `publish_time≤as_of` 切片；补采走前向增量并集；每阶段测试断言无前视 |
| 决策包 canonical 钉死 vs 补采联网（统筹审定） | 若把 scraping 内联进 `build_package`，canonical 读方与库内临时调用都会触发联网，污染纯度、被反爬拖慢 | 补采做成**独立显式开关步骤**（`ensure_topN_news` 或 `build_package(..., 补采_topN=False)` 默认关）；**canonical 读方永不触发补采**；只在**每日生成入口**带补采（必要时 `--rebuild`）构建并把 digest 一次性固化进钉死包，下游只读钉死包 → 钉死与补采天然一致、不冲突 |
| 池对齐副作用 | 对齐后 top-N 覆盖上来，可能改变 digest 内容→影响选股（这正是目标，但需评估） | 用乙案 A/B 框架在数据达标后复测「digest 内容是否真改选股」，与本次「无内容可援引」对照 |
