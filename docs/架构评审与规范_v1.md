## 二、需求与架构合理性分析

### 2.1 现状架构盘点(已落地)
- **采集层** `collectors/`:market(行情)/fundamental(基本面)/announcement(公告)/fundflow(资金流)/news(新闻)。

- **展示** `web/`(4 页)+ `report/`(markdown)。
- **配置** `config/`:stock_pool / settings / strategy(阈值+公式单一真源)。
- **编排** `run.py`:collect/serialize/panel/screen/sentiment/report/all。

- **采集与分析解耦**、**策略配置数据化**(strategy.py 单一真源)、**结构化记录 + 横向总表**、**诚实性内建**(概率非预言)、**留口子接口**(screener/financial_report)。这些是好的架构决策,继续保持。

### 2.3 不足与"还能做什么"(功能路线)
- **规范化缺口**:schema 契约、编排、调度、Agent 工具契约(见第三~七章)。
- **功能补全**(按价值排序):
  1. **情绪面并入超买超卖/选股**(现 event 已产情绪分,尚未并入 predict 的买卖倾向与 screener)。

  3. **财报深挖**(N2:杜邦/现金流质量,LLM 抽取)。

## 三、模块如何协调(核心:以"结构化记录"为集成契约)

**关键架构思想:所有模块不直接互相耦合,而是围绕一份中心数据契约协作。**

```
                    ┌─── 采集层(各自独立,可并行)───┐
   行情 market ─┐   基本面 ─┐  公告 ─┐  资金流 ─┐  新闻 ─┐
                ▼          ▼        ▼         ▼        ▼
              data/raw/*(源形态缓存:parquet / json)
                │          │        │         │        │
                ▼(各分析器独立读 raw,互不依赖)
   technical / valuation / predict / event(LLM) ── 各产出信号
                          │
                          ▼
        ★ serialize:汇成中心契约 data/analysis/{code}.json ★
                          │  (这是"层与层之间的 API")
        ┌─────────────────┼───────────────────┐
        ▼                 ▼                   ▼
   panel(横向表)    screen(选股)        web / report(展示)
```

- **中心契约** = `data/analysis/{code}.json`(schema 见第七章)。生产者(各分析器经 serialize)写它,消费者(panel/screen/web/report)读它。
- **协调 = 数据契约 + 编排顺序**,不是模块互相 import 调用链。→ 任一模块只要遵守契约,就能独立替换/并行开发。
- **编排**:当前 `run.py` 子命令;建议抽象为显式 pipeline(第五章)。

## 四、定时任务与触发设计

**分层任务**(不同频率、不同触发、产出不同):

| 任务 | 频率/触发 | 内容 | 产出 | 成本 |
|---|---|---|---|---|
| **T1 盘后全量** | 每交易日 15:30(cron) | collect(行情/基本面/公告/资金流) → serialize → panel → screen → report | 全套结构化 + 选股 + 报告 | 中(网络) |
| **T2 情绪/新闻** | 每 2 小时 / 盘后(cron) | news 采集 + event LLM 抽取(缓存命中免重复) | sentiment/{code}.json | 中(LLM 费用)→ 单独调度控成本 |
| **T3 盘中轻量**(可选) | 交易时段每 5–15 分钟 | 增量 kline + fundflow → serialize(轻) | 刷新快照 | 低 |
| **T4 低频基本面** | 每周 / 财报季 | fundamental 全量 | 估值/财务更新 | 低 |
| **T5 兜底补数** | 每日夜间 | 重试 T1 中失败的票(如资金流限流) | 补全缺口 | 低 |

**触发机制**:cron 条目 → `python -m tools.run <子命令>`。**不同 cron = 不同 pipeline**。示例:
```cron
30 15 * * 1-5   cd <proj> && <py> -m tools.run all        >> logs/t1.log 2>&1   # 盘后全量
0  */2 * * 1-5  cd <proj> && <py> -m tools.run sentiment  >> logs/t2.log 2>&1   # 情绪(独立,控LLM成本)
0  22 * * 1-5   cd <proj> && <py> -m tools.run collect --retry-failed >> logs/t5.log  # 兜底
```
**触发链**:T1 内部是 DAG(collect → serialize → {panel, screen, report});建议 pipeline 显式声明依赖,失败某步不污染下游(下游读到的是上次成功产出)。

## 五、数据流转与存储

### 5.1 三层数据(职责清晰)
| 层 | 位置 | 形态 | 谁写 | 谁读 |
|---|---|---|---|---|
| **原始缓存** | `data/raw/{kline,fundamental,announcement,fundflow,news,llm_cache}/` | 源形态(parquet/json) | 采集层 / LLM | 分析层 |
| **结构化记录** | `data/analysis/{code}.json` + `sentiment/{code}.json` | 中心契约 schema | serialize / event | panel/screen/web/report |
| **视图/产出** | `data/analysis/{panel.csv,screen.json}`、`docs/报告/` | 表 / 选股 / markdown | panel/screen/report | 人 / Web |

- **中间过程一律保留**(raw + llm_cache),→ 可审计、可重跑、改下游不重复烧钱。
- Web **只读结构化/视图**,不触发计算 → 响应快、可独立部署。

### 5.2 存储演进建议
- **现在**:文件即可(32 票,规模小)。
- **规模化后**(数百票 / 需历史截面查询 / 多用户):引 **DuckDB 或 SQLite** 作查询层,文件仍为真相源。`panel` 可直接落一张宽表进 DuckDB,支持 `SELECT ... WHERE 拐点评分>50 AND 主力净流入>0`。**不建议现在就上 DB**(过早优化)。

## 七、模块接口规范(解耦 + 并行开发 + Agent 可调用)

**目标:程序调用与 Agent 调用统一;定好入参/出参,模块间零口头约定。**

### 7.1 三类契约(统一签名)
1. **采集器 Collector**
   - `fetch_X(codes: list[str], **opts) -> dict[str, Payload]` + 落盘;`load_X(code: str) -> Payload`。
   - 约定:失败单票跳过并记日志,不中断整批;拉到空**抛错**不静默(约法第 5 条)。
2. **分析器 Analyzer**
   - `compute/analyze(inputs) -> dict`,输出为**文档化 JSON schema**;数据不足标 `数据不足`/`error`,不崩。
3. **服务/工具 Tool**(供 Agent)
   - 见 7.3 注册表。

### 7.2 中心契约:`data/analysis/{code}.json`(层间 API)
字段(已实现,本次固化为 JSON Schema 放 `contracts/`):
```
meta        {code, name, sector, industry, as_of}
snapshot    {close, pct_chg, ma{…}, macd{…}, kdj{…}, rsi{…}, bias20, vol_ratio, vol_state}
signals     {trend{评级,得分,依据}, reversal{拐点标签,拐点评分,…}, ob_os{结论,…}}
prediction  {现价, 近三次放量[], 支撑位[], 压力位[], 持有期建议{1/5/10日{止损位,最大亏损%,止盈位,目标盈利%,风险收益比}}, 情景预测{…}, 买卖倾向{结论,依据}}
valuation   {pe_ttm, pb, mktcap_yi, 报告期, pe_valid, …}
fundamental {营收, 净利, 营收增速, 净利增速, ROE, 毛利率, 净利率, 负债率}
sentiment   {净情绪分, 利好数, 利空数, 样本数, events[]}       # P2-C
fundflow    {今日主力净流入, 今日主力净占比, 近5日主力合计, 主力连续净流入天数}
events      [{date, type, impact, title}]                    # 公告
timeseries_refs {kline, fundflow, announcements}  provenance {…}
```
**约定(类型/量纲统一)**:代码=6 位字符串;日期=`YYYY-MM-DD`;金额=元(展示层换算亿,字段名标 `_yi` 时为亿);百分比=数值(非字符串);方向=`利好/利空/中性`;缺失=`null`。

### 7.3 能力注册表 `registry.py`(让程序与 Agent 都能调)
把每个能力登记为**JSON-in / JSON-out 工具**,带 name / 描述 / 入参 schema / 出参 schema:
```python
TOOLS = {
  "collect_market":   {"fn": market.fetch_kline,   "in": {"codes":"list[str]"}, "out": "{code: kline}"},
  "analyze_technical":{"fn": technical.compute,     "in": {"kline":"df"},        "out": "signals"},
  "predict_stock":    {"fn": predict.predict,       "in": {...},                 "out": "prediction"},
  "screen_pool":      {"fn": screener.run_presets,  "in": {"records":"..."},     "out": "{preset:[codes]}"},
  "get_stock_record": {"fn": serialize.load_record, "in": {"code":"str"},        "out": "record"},
  "sentiment_stock":  {"fn": event.analyze_stock,   "in": {"code":"str"},        "out": "sentiment"},
}
```
- **价值**:① 并行开发——各模块只需实现自己的 fn + 声明契约;② Agent 编排——未来 Agent 读注册表即可发现并调用工具(如"给我筛出主力吸筹且情绪转正的票"→ 依次调 screen/sentiment);③ 测试——按契约 mock。

## 九、Git 协作与冲突避免(重点,针对多窗口/多 Agent)

**已发生:两个窗口并发写同一仓库,分支被覆盖、提交一度丢失。必须立规矩。**

### 铁律
1. **main 只做集成**,禁止任何窗口直接在 main 上开发/提交;合并走"分支→合并"。
2. **一分支一负责人/一窗口/一模块**:`feat/<模块>-<阶段>`;同一时刻**同一分支只有一个写者**。
3. **不并发编辑共享文件**:`README`、`开发日志`、`strategy.py` 等被多方改的文件,约定串行(一个窗口改完提交,另一个再动)或拆分文件。
4. **本文档即示范**:docs 分支 + **只新建独立文件** + 只暂存自己的文件,零冲突。
5. **每次操作前** `git status` + 必要时 `git reflog` 确认,别盲目 checkout/merge。
6. **小步提交、及时 push** 到自己的远端分支(丢了能从远端找回)。
7. **靠契约解耦**:模块围绕第七章的数据契约开发,天然减少代码级冲突。

### 针对当前 fork 场景
- 本窗口(架构评审)= **docs 独立分支,不碰代码、不动 main**,与那个在写 P2-C 的窗口物理隔离。
- 建议:那个窗口把 P2-C 收尾提交并 push 后,再由**单一窗口**统一合并入 main;其余窗口 rebase。

## 十、方案与实施计划

分四阶段,每阶段独立分支、可并行(彼此不改同一文件):

| 阶段 | 内容 | 交付 | 依赖 |
|---|---|---|---|
| **A 规范固化** | `contracts/` 写 record 的 JSON Schema + 校验器;补《接口规范》文档;落地第九章 Git 规范 | 契约文件 + 规范 | 无(可立即) |
| **B 编排与调度** | 抽 `pipeline.py`(显式 DAG,失败隔离);cron 配置(T1–T5);run.py 变薄壳 | 可定时自动跑 | A |
| **C 工具化** | `registry.py` 暴露能力(JSON-in/out);为 Agent 调用铺路 | 能力注册表 | A |
| **D 功能补全** | 情绪并入 predict/screener;政策/UGC;财报(N2);回测+ML(P3.E) | 功能闭环 | B/C |

- **决策(按架构师推荐先行)**:A 最先做(规范是并行开发地基);B、C 可并行;D 最后。
- 每阶段:先写需求/接口文档 → 分支实现 → 自测 → push → 合 main。

## 十一、推荐建议(优先级)

1. **立刻**:执行第九章 Git 铁律(尤其"main 只集成、一分支一写者")——这是当前最大风险,不解决会持续丢代码。
2. **高**:阶段 A 固化 `contracts/` 数据契约 + 接口规范 → 多人/多 Agent 才能真正并行。
3. **高**:阶段 B `pipeline.py` + cron 调度 → 数据自动更新,demo/生产都受益。
4. **中**:阶段 C `registry.py` 工具化 → 为"Agent 调工具"铺路(你明确想要的方向)。
5. **中**:情绪面并入买卖倾向与选股(数据已有,只差接线),让"情绪+技术"闭环。
6. **按需**:DB 查询层、政策/UGC、财报、回测/ML —— 规模或业务需要时再上,不过早优化。

> 一句话:**架构骨架已良好(采集/分析/契约/展示分层清晰)。当前瓶颈不在功能,而在"规范与协作"——把数据契约、编排调度、Git 纪律、工具注册补齐,项目就能从"一个人能跑"变成"多人+多 Agent 可并行演进"。**
